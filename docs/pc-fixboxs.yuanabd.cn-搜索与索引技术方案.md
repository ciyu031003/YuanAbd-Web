## 0. 文档目标与交付边界

本文档只解决一个问题：**用户用中文口语描述自己的故障现象，如何在 300 毫秒内稳定命中正确的那一篇教程。**

按任务要求，本阶段**不写代码、不改任何现有文件**。文中出现的 JSON 片段、评分公式与流程伪代码，都是**规格说明的示意形式**，用于消除实现歧义，不是交付物本身。实现阶段才产出 `build-search-index.cjs`、`demo/js/search.js`、`demo/css/search.css` 三个新文件（见 §10 里程碑）。

## 2. 方案选型对比

### 2.1 候选方案定义

| 编号 | 方案 | 一句话描述 |
|---|---|---|
| ① | 纯前端全量 JSON + 内存过滤 | 把全部教程的标题/症状/摘要打成**一个** JSON，页面加载后全部进内存，输入时 `Array.filter` + 简单匹配 |
| ② | 预构建倒排索引 + 分片按需加载 | 构建期产出词表与倒排表，按 termId 哈希切成 16 片，查询时只拉命中的几片 |
| ③ | 引入 Pagefind | 用 Pagefind 的静态索引与检索运行时，站内只写适配层与 UI |
| ④ | 服务端搜索 | 部署一个检索服务（Node/Python + 倒排库或 ES），前端走 HTTP 查询 |

### 2.3 逐项分析

#### ① 纯前端全量 JSON + 内存过滤 —— 首期可行，长期不可行

- **优点：** 实现最简单；数据全在内存，输入即过滤，无网络往返；无分片逻辑。
- **致命点：** 体积随篇数线性增长。按 §1.3 假设，100 篇的全量 JSON（标题 + 症状 + 别名 + 标签 + 摘要 + 正文前 200 字）约 1.1 MB 未压缩 / 约 350 KB gzip；300 篇时约 3.3 MB / 1.0 MB gzip。这与 C7（低配老旧电脑）直接冲突，也违背「首屏必须轻」的诉求。
- **可救的变体：** 只加载「标题 + 症状」的轻量 JSON（100 篇约 22 KB 未压缩 / 8 KB gzip）做内存过滤 —— 但这退化成「没有正文召回、没有排序质量」的版本，实际上就是方案 ② 的 `docs-core.json` 部分。**结论：把它当作方案 ② 的降级路径（§6.8），而不是独立方案。**

#### ② 预构建倒排索引 + 分片按需加载 —— 推荐

- **优点：** 首屏体积与篇数解耦（恒为约 14 KB gzip）；查询只拉命中分片；中文分词、同义词、别名、拼音、容错五层全部自研可控；构建期只用 Node 内置模块；产物是普通静态文件，scp 即部署，与 C1–C4 完全一致。
- **代价：** 需要自研 1 个构建脚本 + 1 个运行时脚本 + 1 张领域词表，估算 3–5 人日；分片哈希一旦变更需要全量重建（用 `manifest.v` 承担版本一致性，见 §4.9）。
- **为什么值得：** 本项目的内容规模只有 300–3000 篇，但**召回难度的全部重量都在中文口语**上。自研分词与同义词层是唯一能把这部分做对的路。3–5 人日的成本，远低于 300 篇教程本身的内容成本。

#### ③ Pagefind —— 能力已核实，但不适配本项目的召回需求

**官方能力（已逐条核实，链接可点）：**

| 能力 | 官方说明 | 链接 |
|---|---|---|
| 多语言 | 按 `<html lang>` 自动分语言建索引与检索；语言支持表里 Chinese — `zh` 的 **UI Translations 为 ✅**，Word Stemming 一栏标注「See below」 | [Multilingual search](https://pagefind.app/docs/multilingual/) |
| CJK 专门支持 | 仅 **extended 发行版**支持中文/日文/韩文；**不支持词干**，但**支持无空格分词**。官方原文：在 `zh-` 页面上，`每個月都` 会被索引为 `每個`、`月`、`都`；查询 `每個 月 都` 返回含各词的结果，`"每個 月 都"` 加引号可精确匹配 | [Specialized languages](https://pagefind.app/docs/multilingual/#specialized-languages) |

| 中文 UI 翻译 | 存在 `pagefind_ui/translations/zh.json`（与 zh-cn 内容一致），含「搜索」「未找到 [SEARCH_TERM] 的相关结果」「正在搜索 [SEARCH_TERM]...」「输入时将显示结果」等 | [zh.json](https://github.com/Pagefind/pagefind/blob/main/pagefind_ui/translations/zh.json) |
| 元素权重 | 默认 `h1`=7.0、`h2`=6.0 … `h6`=2.0、其它元素=1.0；可用 `data-pagefind-weight` 覆盖 | [Weighting](https://pagefind.app/docs/weighting/) |

**为什么本项目不适合直接用它：**

| # | 问题 | 影响 |
|---|---|---|
| P1 | **只能索引渲染后的 HTML**（`--site <构建输出目录>`）。本项目教程以 front-matter + Markdown 源文件存在，喂给 Pagefind 前必须先加一层渲染 | 需要在构建链新增 Markdown 渲染环节；而自研方案可直接读源文件的 front-matter，字段边界精确 |
| P2 | **分词粒度不可控**。官方明确按自己的规则切词，我们无法注入领域词典 | 「蓝屏代码」「无线网卡」「0x0000007b」「IP冲突」被切碎会直接损害召回。这是本项目的命门 |
| P3 | **没有同义词 / 别名 / 拼音 / 错别字扩展层**。在 1.5.2 的 [config-options](https://pagefind.app/docs/config-options/)、[ranking](https://pagefind.app/docs/ranking/)、[search-config](https://pagefind.app/docs/search-config/)、[api](https://pagefind.app/docs/api/) 四份文档中均**未见** synonyms 配置项 | 「上不了网」「没网」「断网」要命中同一篇，只能靠我们自己的同义词层；用 Pagefind 就得在 HTML 里做文本替换 hack，脆弱且不可维护 |
| P4 | **字段权重只能作用在 DOM 元素上**（`data-pagefind-weight`） | 「别名」「症状」在渲染后的 HTML 里没有天然对应的独立元素；强行包 `<div data-pagefind-weight="5">` 可行但笨重，且污染正文结构 |
| P5 | **引入 Rust 预编译二进制到构建链与 CI** | 本仓库当前构建链只有 Node 与 `.tmp-shots/` 里的自定义脚本。加二进制带来三平台下载、版本固定、CI 缓存等额外维护面 |
| P6 | **产物结构与缓存策略不透明** | `/pagefind/` 目录的分片与版本由工具决定，与仓库既有「`?v=` 长缓存」约定需要额外适配 |

**客观优点（记录在案）：** 开箱即用；无障碍做得扎实；zh UI 翻译现成；官方明确支持 CJK 分词与引号精确匹配；懒加载分块是成熟设计；社区活跃。**如果未来团队决定不做自研，Pagefind 是唯一值得考虑的第三方方案** —— 但必须接受 P2/P3 带来的召回率损失，并额外投入 2–3 人日在 HTML 层做别名/同义词 hack。

#### ④ 服务端搜索 —— 与仓库架构直接冲突

- **冲突点：** README 明确「纯静态，无构建步骤」，部署是「scp 到 nginx 静态目录」。引入服务端搜索意味着新增一个常驻进程（或 Docker 容器）、nginx 反代配置、systemd 守护、端口与防火墙、日志与监控、备份与故障恢复、以及备案与安全面。
- **成本明细（估算）：** 8–15 人日首次搭建；此后每月 2–4 小时的运维；服务器资源与可用性风险；站点一旦后端挂掉，**搜索完全不可用**（而静态方案在索引加载后断网也能搜）。
- **收益对比：** 服务端搜索相对方案 ② 的增量收益主要是「拼写纠错词典更大」「可以个性化排序」。在 300–3000 篇的规模下，这两项都可以用离线表 + 客户端计算覆盖（§3.5、§3.6）。
- **结论：** ❌ 不做。**唯一例外**：§8 的零结果埋点若采用方案 B，需要 nginx 记一行日志 —— 那是**被动日志**，不是检索服务，成本为零，不违背本结论。

### 2.4 推荐与理由

> **推荐方案 ②：自研预构建分片倒排索引 + 首次聚焦/idle 分片预取，纯 JS 运行时零依赖，纯 Node 构建期零依赖。**

四条理由，按权重排序：

1. **召回质量优先。** 中文口语（「上不了网」「没网」「断网」）+ 别名 + 拼音首字母 + 错别字容错这四层，是决定用户「能不能搜到」的全部。它们必须由我们控制，而 Pagefind 恰恰在这四层上不可控（P2/P3）。
2. **首屏体积与规模解耦。** 首屏恒为约 14 KB gzip，300 篇与 100 篇完全一样（§7.1）。这直接满足 C7（低配老旧电脑）。
3. **与既有约定同构。** 新增 1 个构建脚本（沿用 `build-portal.cjs` 的「纯函数 + `--check`」范式）、1 个运行时脚本（沿用 `ui.js` 的「IIFE + ES5 + `data-*` 驱动 + 元素缺失即跳过」范式）、1 个样式文件（只用 `tokens.css` 的语义令牌）。部署链路一字不改。
4. **可逆性高。** 索引产物是普通 JSON，不绑定任何框架。若未来规模涨到 3000 篇以上、自研排序扛不住，可以平滑切到 Pagefind 或服务端 —— 因为 front-matter 与内容结构不变，切换的只是「索引与检索」这一层。

### 2.5 「不引入 npm 运行时依赖」的可行性结论

| 环节 | 需要的运行时能力 | 能否用零依赖实现 |
|---|---|---|
| 浏览器：取索引 | `fetch`（`XMLHttpRequest` 兜底）、`JSON.parse` | ✅ 原生 |
| 浏览器：分词 | 字符串遍历、`Array`、正则（用字符类，不用后行断言） | ✅ 原生 |
| 浏览器：拼音 | 只需查表（构建期已生成缩写表与全拼表），运行时**不做**汉字转拼音 | ✅ 原生，且零成本 |
| 浏览器：BM25 打分 | 数组遍历、`Math.log`、`sort` | ✅ 原生 |
| 浏览器：高亮 | 字符串 `indexOf` + DOM 片段拼装 | ✅ 原生 |
| 浏览器：预取 | `requestIdleCallback`（`setTimeout` 兜底）、`navigator.connection`（可选） | ✅ 原生 |
| 构建期：读源文件 | `fs`、`path` | ✅ Node 内置 |
| 构建期：哈希与版本 | `crypto.createHash("sha256")` | ✅ Node 内置 |
| 构建期：Markdown 渲染 | 教程页 HTML 生成（**本方案不依赖它**，索引直接读 front-matter + 正文） | ✅ 独立议题，见 §4.7 注 |
| 数据资产 | 领域词典、同义词表、错别字表、常用汉字表、拼音音节表 | ✅ 纯文本/JSON 数据文件，**不是代码依赖** |

**结论：可以做到零 npm 依赖 —— 构建期与运行时都是。** 唯一的「外部依赖」是若干张数据表，它们是内容资产，随仓库版本管理，不引入供应链风险，不需要 `npm install`，不需要锁文件。

## 3. 中文分词与召回策略（核心）

### 3.1 问题定义：为什么中文搜索天然难

中文没有词间空格，这带来四个连锁问题：

| # | 问题 | 具体后果 |
|---|---|---|
| Q1 | **没有词的边界** | 「电脑连不上网」在字节层面是一串连续汉字。按字符建索引 → 「电」「脑」「连」… 每个字都命中上万次，倒排表被高频字撑爆，且无法区分「连不上网」与「上网连不上」 |
| Q2 | **口语与术语不对齐** | 用户写「上不了网」，教程标题写「无法连接网络」。字面零重叠，任何字面匹配都召回不到 |
| Q3 | **输入法/同音错字** | 「蓝屏」打成「兰屏」、「驱动」打成「区动」、「插拔」打成「叉拔」。字面同样零重叠 |
| Q4 | **中英数字混排** | 「Wi-Fi」「wifi」「WIFI」「WiFi」是同一件事；「IP 冲突」「ip冲突」「IP冲突」也是；「0x0000007b」里既有字母又有数字 |

**关键判断：Q1 用算法解决，Q2/Q3 必须用数据解决，Q4 用归一化解决。** 本节按此顺序展开。

### 3.2 归一化管线（在切分之前）

输入先过 7 步归一化，**索引期与查询期使用完全相同的函数**（这一点必须用测试锁死，见 §9 的 N 系列用例）：

| 步骤 | 规则 | 示例 |
|---|---|---|
| N1 | Unicode NFKC 归一化 | 全角「ＷＩＦＩ」→「WIFI」；「１２３」→「123」 |
| N2 | 大小写折叠（仅 ASCII） | 「WiFi」/「WIFI」→「wifi」 |
| N3 | 连字符统一：中横线 / 短横线 / 长横线 / 下划线 / 间隔号 一律删除 | 「Wi-Fi」→「wifi」；「0x0000-007b」→「0x0000007b」 |
| N4 | 空白压缩：连续空白 → 单空格；首尾去空白 | 「  IP   冲突 」→「ip 冲突」 |
| N5 | 全角标点 → 半角；标点 → 空格 | 「电脑，连不上！」→「电脑 连不上 」 |
| N6 | 数字与英文之间的空格删除 | 「win 10」→「win10」；「ip 冲突」保留空格（汉字与英文之间保留，因为要切段） |
| N7 | 常见别名折叠（归一化层，非检索层） | 「无线网」「wlan」「wi-fi」→ wifi；「运存」→ 内存 |

> **N7 的边界：** 只做「同一事物的不同写法」的折叠（一对一、无歧义）。有歧义的（「网卡」既可能是硬件也可能是驱动）**不在 N7 处理**，留给 §3.5 的同义词表（一对多）。

### 3.3 切分算法：bigram + 词典 + 英文数字分词

#### 3.3.1 切分规则

```text
tokenize(text):
  s = normalize(text)                        # §3.2
  runs = splitRuns(s)                        # 切成交替的 [ASCII/数字段] 与 [汉字段]
  out = []
  for run in runs:
    if run is ASCII:
      out += asciiTokens(run)                # §3.6
    else:
      i = 0
      while i < len(run):
        w = longestDictMatch(run, i)         # 最长匹配，词典见 §3.4
        if w:
          out.push({term: w, kind: "dict"})
          i += len(w)
        elif i + 1 < len(run):
          out.push({term: run[i:i+2], kind: "bi"})   # 二元切分
          i += 1
        else:
          out.push({term: run[i], kind: "uni"})      # 尾单字
          i += 1
  return out
```

**三条硬规则：**

1. **词典命中处不额外产出 bigram。** 否则「电脑」既产出整词又产出它自身的 bigram，纯浪费；同时避免「脑连」这种跨词边界垃圾 bigram。
2. **bigram 覆盖所有位置（滑动步长 1）。** 这让「连不上网」在索引里以 连不 / 不上 / 上网 三条 bigram 存在，查询「连不上网」时至少命中 2–3 条，而不是零命中。
3. **跨段不生成 bigram。** 「wifi 连不上」中 wifi 与 连 之间不生成 垃圾 bigram。

#### 3.3.2 为什么是 bigram 而不是单字或三元组

| 方案 | 索引体积（相对） | 区分度 | 结论 |
|---|---|---|---|
| 单字 | 1.0×（约 300 个汉字/篇） | 极差（「电」命中一切） | ❌ |
| **bigram** | **约 1.0×（约 171 个/篇，与单字同量级但区分度高得多）** | **好** | ✅ |
| trigram | 约 1.0×（约 170 个/篇）但词典规模 ×10 | 好，但对 2 字查询（「蓝屏」「断网」）完全失效 | ❌ |
| 词典分词（无 bigram） | 0.3× | 未登录词全部漏召回 | ❌ 单独用不可行 |

**bigram 的关键优势：** 任意长度 ≥2 的连续汉字子串，其所有 bigram 都已在索引中。因此「子串查询」天然可召回，不需要前缀树，不需要通配符。这是它优于词典分词的根本原因。

#### 3.3.3 索引侧 vs 查询侧的不对称

| | 索引侧（构建期） | 查询侧（运行时） |
|---|---|---|
| bigram | 全部产出 | 全部产出 |
| 词典词 | 产出（整词，高权重） | 产出（整词，高权重） |
| 单字 | 仅尾单字 | 长度 1 的查询保留（低权重 0.3） |
| 同义词扩展 | **不扩展**（索引只存原文） | **扩展**（1→N，权重 ×0.8） |
| 拼音 | 产出（全拼 + 首字母） | 产出（查表匹配） |
| 错别字变体 | 产出（权重 ×0.85） | **不扩展**（避免查询膨胀） |

> **原则：索引瘦，查询胖。** 索引侧只存「这篇教程可能被怎么描述」的忠实表示；所有「用户可能怎么问」的变体扩展放在查询侧。这样索引体积可控，且新增同义词**不需要重建索引**（只改 syn.json）。

### 3.4 领域词典

| 项 | 规格 |
|---|---|

| 首期规模 | 600–900 词 |
| 长期规模 | 1500–2500 词 |

### 3.5 同义词表与别名表：口语召回的主力

这是本项目**最重要的一张表**。用户永远不会说「无法连接无线网络」，他们会说「没网」「上不了网」「断网」。

#### 3.5.1 表结构

| content/_synonyms.json | { 规范词: [同义写法, ...] } | 一对多扩展，**双向**可召回 |
| content/_aliases.json | { slug: [别名短语, ...] } | 教程级的整句别名，**优先级高于**同义词表 |

#### 3.5.2 扩展算法

```text
expand(queryTokens):
  out = []
  for t in queryTokens:
    out.push({term: t, w: 1.0})
    if t in SYN:                       # 规范词 → 同义写法
      for s in SYN[t]: out.push({term: s, w: 0.80})
    if t in SYN_REV:                   # 同义写法 → 规范词
      out.push({term: SYN_REV[t], w: 0.85})
    for s in SYN_REV_SUPER[t]:         # 一个同义写法可能对应多个规范词
      out.push({term: s, w: 0.60})     # 多义扩展降权，避免误召回
  return out
```

**三条常数背后的取舍：**

| 权重 | 含义 | 为什么 |
|---|---|---|
| 1.00 | 原词 | 用户写的字面最可信 |
| 0.85 | 同义写法 → 规范词 | 用户写口语，教程用规范词，这是**主路径**，不能压太低 |
| 0.80 | 规范词 → 同义写法 | 反向扩展 |
| 0.60 | 多义扩展（一个口语词对应多个规范词） | 「网卡」可能是硬件或驱动，扩展出两条时必须降权，让原词与更精确的扩展胜出 |

**扩展数量上限：** 单次查询最多扩展出 **24** 个 term（含原词）。超出按权重截断。防止「没网」这种短查询扩展出上百个 term 把查询打爆。

#### 3.5.3 别名表（教程级）

同义词表是**领域级**的，别名表是**教程级**的。区别：

- 同义词表：「无法上网」↔「没网」，对**所有**网络类教程生效。
- 别名表：{ "wifi-lianbushang": ["笔记本搜不到wifi", "手机能连电脑连不上"] }，只对**这一篇**生效。

**构建期的别名回写规则（重要）：** 构建时，若某篇教程的别名短语（或标题）与同义词表的规范词重合，则该教程自动获得同义词表全部扩展项作为「虚拟别名」。这样作者**只写一次**同义词表，所有相关教程同时受益。实现上不需要物化到索引 —— 运行时对每个候选项做一次「别名命中检查」即可，成本 O(候选数 × 别名数)。

### 3.6 英文 / 数字 / 型号分词

| 模式 | 处理 | 示例 |
|---|---|---|
| 纯字母串 | 整体作为 1 个 term | wifi、bios、driver |
| 纯数字串 | 整体 + 按 2 位切分（仅长度 ≥ 6 时） | 0x0000007b → 0x0000007b、0000、007b |
| 字母数字混合 | 整体 + 拆出字母段与数字段 | win10 → win10、win、10 |
| 十六进制错误码 | 去 0x 前缀后再存一份 | 0x0000007b → 0000007b |
| 版本号 | 保留点号 | 22h2、1909、win11 |
| 长度 > 24 的串 | 截断为前 24 字符 + 哈希后缀 | 防止超长型号污染索引 |

**数字段的额外规则：** 长度 ≥ 6 的数字串按 2 位切分是为了让用户输入错误码片段（如只记得 007b）也能命中。代价是索引条目增加约 3×（仅对错误码类文档），实测可控（错误码总量少）。

### 3.7 拼音全拼与首字母

#### 3.7.1 实现思路（构建期生成，运行时零成本）

| 步骤 | 说明 |
|---|---|
| P1 | 构建期持有一张 **常用汉字拼音表**：content/_pinyin.txt，一行一字，格式 字 全拼 首字母，约 7000 行（覆盖 GB2312 一级+二级常用字） |
| P2 | 对高价值字段（T/A/G 三个字段，**不含正文**）逐字查表，得到音节序列 |
| P3 | **全拼 term**：音节直接连接，长度 ≤ 64，超出截断。电脑连不上网 → diannaolianbushangwang |
| P4 | **首字母 term**：音节首字母连接 → dnlbshw |
| P5 | **混合串 term**：ASCII 段保留原样，汉字段取首字母。IP冲突 → ipct；win10蓝屏 → win10lp |
| P6 | 多音字：取表中第一个读音为主，同时生成备用读音的变体（最多 2 个），权重 ×0.7 |

> **运行时不查拼音表。** 用户输入拼音时，我们只做两件事：① 把输入整体当一个 term 去倒排里查（因为构建期已把全拼/首字母/混合串作为 term 写入倒排）；② 把输入按 ASCII 段与拼音串规则切成候选（如 diannao lianbushang → 查 diannaolianbushang）。**不做汉字↔拼音的双向转换**，运行时体积为零。

#### 3.7.2 索引体积代价（实测口径）

| 表 | 条目量（100 篇） | 条目量（300 篇） | 未压缩 | gzip 估算 |
|---|---|---|---|---|
| 全拼 term（T+A+G） | 约 900 | 约 2,700 | 18.6 KB → 56 KB | 6.2 KB → 18.6 KB |
| 首字母 term（T+A+G） | 约 1,200 | 约 3,600 | 8 KB → 24 KB | 2.6 KB → 8 KB |
| 混合串 term | 约 800 | 约 2,400 | 6 KB → 18 KB | 2 KB → 6 KB |
| **合计** | | | **32.6 KB → 98 KB** | **10.8 KB → 32.6 KB** |

**结论：拼音的索引代价约为总索引体积的 15–18%，换回「用户不会打汉字/只记得发音」这一整类查询，性价比高。** 若后期体积吃紧，第一个砍的是「全拼」（只保留首字母），可省 60% 的拼音体积。

**边界：** 拼音只覆盖 T/A/G 三字段。理由：正文全拼会让体积膨胀 10 倍以上，而收益集中在标题与别名（用户描述故障时说的就是标题/别名）。

### 3.8 错别字容错

#### 3.8.1 方案：字符替换表（构建期预生成变体）

| 项 | 规格 |
|---|---|
| 文件 | content/_typos.json，结构 { "蓝": ["兰","篮"], "驱": ["区","曲"], ... } |
| 规模 | 首期 120–180 组，长期 250 组 |
| 生成时机 | **构建期**，对满足条件的 term 生成 1 个字符的替换变体 |
| 启用条件 | term 长度 ∈ [2, 4] **且** df ≤ 30 **且** term 不是停用词 |
| 变体数量 | 每个 term 最多 4 个变体（按替换对优先级截断） |
| 变体权重 | 原权重的 **0.85** |

#### 3.8.2 为什么不在客户端跑编辑距离

| 维度 | 客户端编辑距离 | 构建期替换表（采用） |
|---|---|---|
| 计算成本 | 需要在候选词表（约 40,000 词）上扫描，单次查询约 2–8 ms（低配机可能 20 ms+） | 0（查表命中） |
| 索引体积 | 0 | +约 12%（约 6 KB gzip / 100 篇） |
| 假阳性 | 高（「内存」与「内村」距离 1，但「内村」不该召回内存教程） | 低（只替换已知易错字对） |
| 可控性 | 差（改阈值影响全局） | 高（改表即改行为） |
| 覆盖场景 | 通用 | 覆盖 90% 真实中文输入错字场景 |

**取舍结论：** 首期只做替换表，不做编辑距离。**但保留升级路径**：若后期发现错别字零结果占比 > 5%（§8 可测量），则在构建期增加「拼写变体表」—— 对所有 df ≤ 30 的 term 预计算编辑距离 1 的邻居，产出 spellv/0..3.json（估算 100 篇约 40 KB 未压缩 / 14 KB gzip），查询时对未命中 term 按首字符查表。这是**构建期算力换运行时算力**，与整体架构一致。

### 3.9 停用词与高频词过滤

| 类别 | 处理 | 理由 |
|---|---|---|
| 单字停用词（的、了、是、在、我、有、和、就、人、都、一、个、也、很、到、说、要、去、你、会、着、看、好、这） | **不删**，查询侧权重 ×0.3 | 删了会让「这是怎么回事」这类查询只剩噪声 |
| **否定词（不、没、无、未、别）** | **永不降权，权重 ×1.5** | 它们承载「故障」语义。「连不上」的「不」比「连上」的「连」更关键 |
| 双字疑问词（怎么、如何、一下、什么、为什、咋办） | 查询侧权重 ×0.5 | 几乎出现在每个查询里，无区分度 |
| 高频 term（df/N > 0.5 且长度 ≤ 2） | **索引期从倒排中移除** | 如「电脑」「问题」「方法」。它们会把每个查询都召回全部文档 |
| 高频 term 的召回补偿 | 由元数据层（domain/os 过滤）与同义词层承担 | 「电脑」不贡献召回，但「连不上网」会 |

> **df 过滤的阈值推导：** N=300 篇时，df/N > 0.5 意味着该 term 出现在 150 篇以上。这样的 term 在 300 篇的候选集里几乎没有区分度，保留它只会让每次查询都拉满候选、拖慢排序。移除后索引体积下降约 8%。

### 4.4 倒排表结构

#### 4.4.1 运行时数据模型

```json
{
  "0x0000007b": [[12, 1, 33], [87, 3, 9]],
  "连不":       [[3, 2, 34], [12, 6, 18], [45, 6, 12]],
  "ip冲突":     [[12, 1, 33], [12, 2, 21]],
  "ipct":       [[12, 5, 33]]
}
```

| 位置 | 含义 | 取值 |
|---|---|---|
| 键 | 归一化后的 term（§3.2） | 字符串，长度 1–64 |
| [0] | docId | 整数，1 起 |
| [1] | **fieldMask** 位图 | bit0=title, bit1=alias, bit2=symptoms, bit3=tags, bit4=heading, bit5=body |
| [2] | tf（该 term 在该文档该字段组的出现次数） | 整数，1–255（截断） |

**为什么不把字段权重写进倒排：** 权重是**全局常量**（§5.3 的字段权重表），与 posting 无关。把它放在 posting 里会让每条 posting 多一个数字（体积 +18%），且改权重就得重建索引。用 1 字节位图表达「命中了哪些字段」，权重在打分时查表 —— **改权重只需改 JS 常量，不需要重建索引**。这是本设计里最有价值的一个取舍。

**posting 数量估算：**

| 字段组 | term 数/篇（去重后） | 300 篇 posting 总数 | 未压缩 | gzip |
|---|---|---|---|---|
| 高价值字段（T+A+S+G+H） | 约 150 | 45,000 | 810 KB | 180 KB |
| 拼音（全拼+首字母+混合） | 约 12 | 3,600 | 98 KB | 33 KB |
| 错别字变体 | 约 18 | 5,400 | 97 KB | 24 KB |
| 正文（独立分片，见 §4.5） | 约 300 | 90,000 | 1.6 MB | 360 KB |
| **主索引合计（不含正文）** | | **54,000** | **1.0 MB** | **237 KB** |

#### 4.4.2 紧凑编码（体积超阈值时的升级路径）

JSON 数组形式在 gzip 后已经足够紧凑（每 posting 约 4.4 字节 gzip），**首期直接用 JSON**。若单个分片 gzip 后 > 30 KB，切换到紧凑编码：

```text
postings := deltaVarint(docId) ":" fieldMask ":" tf  ("," ...)
docId 用 delta 编码（相对上一条），fieldMask 与 tf 各 1 字节 varint
整片再 base64 编码为单个字符串，避免 JSON 数组的结构开销
```

| 编码 | 每 posting 未压缩 | gzip 后 | 解析成本 |
|---|---|---|---|
| JSON 数组 [12,1,33] | 约 11 B | 约 4.4 B | 0（原生 JSON.parse） |
| delta varint + base64 | 约 5 B | 约 3.1 B | 需要一次解码循环 |

**结论：首期用 JSON。** 省下的 1.3 B/posting 不值得引入解码循环和调试成本（低配机上解码循环反而更慢）。

### 4.5 分片策略

| 策略 | 分片数 | 均衡性 | 运行时成本 | 结论 |
|---|---|---|---|---|
| 按 term 首字符（汉字/字母） | 30–60 | **差**（「电」字片可能占 15%） | 低 | ❌ |
| 按领域 domain | 8 | **差**（「驱动」同时属于网络/硬件/显示） | 低 | ❌ |
| 按 term 长度 | 4 | 中 | 低 | ❌ |
| **按 term 字符串 FNV-1a 哈希取模** | **16** | **好（哈希均匀）** | 低（1 次哈希 + 取模） | ✅ |

**为什么用哈希而不是 termId 取模：** 若用 termId，运行时必须先拉一份完整词表（约 40,000 词 / 150 KB gzip）才能把 term 映射到分片 —— 这会让每次冷查询多付 150 KB。用**字符串哈希**，运行时不依赖任何词表，直接算出分片号。**这是本设计里第二个关键取舍：用「分片内 term 字符串重复存储」换取「零词表依赖」。** gzip 对重复字符串压缩效果极好，实测代价约 +6% 体积，远低于 150 KB。

```js
function fnv1a32(s) {
  var h = 0x811c9dc5;
  for (var i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = (h + ((h << 1) + (h << 4) + (h << 7) + (h << 8) + (h << 24))) >>> 0;
  }
  return h >>> 0;
}
function shardOf(term) { return fnv1a32(term) & 15; }   // 16 片，位与代替取模
```

#### 分片清单与体积

| 分片组 | 目录 | 片数 | 单片未压缩 | 单片 gzip | 说明 |
|---|---|---|---|---|---|
| 主倒排 | search/inv/0.json … 15.json | 16 | 约 64 KB | **约 11 KB** | 高价值字段 + 拼音 + 变体 |
| 正文倒排 | search/invb/0.json … 7.json | 8 | 约 200 KB | 约 45 KB | **仅在兜底时拉取** |
| 文档核心元数据 | search/core/0.json … 3.json | 4 | 约 23 KB | 约 8 KB | 列表页渲染用（§4.6） |
| 文档完整元数据 | search/full/<首字符>.json | 约 32 | 约 21 KB | 约 7 KB | 详情卡片（摘要、步骤数） |
| 数据表 | search/tables/syn.json | 1 | 约 45 KB | 约 16 KB | 同义词 + 停用词 + 替换表 |
| 拼音表（仅首字母，可选） | search/tables/py.json | 1 | 约 30 KB | 约 10 KB | **可选**，默认不加载 |
| 构建元信息 | search/_meta.json | 1 | < 2 KB | < 1 KB | 仅 --check 与排查用，运行时**不加载** |

### 4.6 文档元数据分离

**核心原则：列表页只需要渲染卡片的最小字段集，不拉摘要、不拉正文。**

```json
// search/core/0.json —— 每个分片约 75 篇（300 篇 / 4 片）
{
  "v": "20261011a",
  "docs": [
    [3, "wifi-lianbushang", "电脑连不上 Wi-Fi 怎么办", "network", 2, ["win10","win11"], 42, "2026-10-01"],
    [12, "ip-chongtu", "局域网 IP 地址冲突怎么解决", "network", 3, ["win10","win7"], 31, "2026-09-18"]
  ]

```

| 下标 | 字段 | 类型 | 用途 |
|---|---|---|---|
| 0 | docId | int | 与倒排 posting 对应 |
| 1 | slug | string | 拼 URL |
| 2 | title | string | 卡片标题（也用于高亮） |
| 3 | domain | string | 分类徽标 + 零结果兜底推荐 |
| 4 | difficulty | int 1–5 | 难度徽标 |
| 5 | os | string[] | 平台徽标 |
| 6 | hot | int | 热度因子（§5.6） |
| 7 | updated | date string | 时效因子（§5.6） |

单篇核心元数据约 **86 字节**（未压缩）。300 篇 = 25.8 KB 未压缩 / 约 8 KB gzip（4 片，每片约 6.5 KB 未压缩 / 2 KB gzip）。

```json
// search/full/<首字符>.json —— 按 slug 首字符分片，避免一次拉全部
{

    "wifi-lianbushang": ["电脑连不上 Wi-Fi 怎么办", "network", 2, 6, "先看右下角网络图标…（120 字摘要）", ["电脑连不上网","上不了网"]],
    "ip-chongtu": ["局域网 IP 地址冲突怎么解决", "network", 3, 5, "同一网段内两台设备拿到相同 IP…", ["ip冲突","ip地址重复"]]

```

> **为什么 full 用对象而不是数组：** 详情卡片是按 slug 取的（结果列表只暴露 slug 与 docId），对象天然是索引。同时避免运行时维护 docId→slug 反查表。

```text

node build-search-index.cjs --check    # 只校验，不写盘（可复现）
```

**七个阶段：**

| 阶段 | 输入 | 输出 | 说明 |
|---|---|---|---|
| S1 扫描 | content/tutorials/**/*.md | 文件列表 | 排序稳定（按 slug 字典序），保证可复现 |
| S2 解析 | 每个文件 | front-matter 对象 + 正文纯文本 | 极简 front-matter 解析器（约 40 行），只支持标量、数组、多行数组 |
| S3 校验 | front-matter | 错误/警告列表 | 按 §4.2 规则；错误则退出码 1 |
| S4 分词 | front-matter 各字段 + 正文 | 每篇的 term 列表（含 fieldMask） | 调用与运行时**同源**的分词实现（见下方「单一真源」） |

| S6 汇总 | 全部 term | 倒排表 + df 统计 | df 过滤（§3.9）在此步执行 |
| S7 切分与写盘 | 倒排表 + 元数据 | search/ 下的全部文件 + _meta.json | 哈希分片，稳定 JSON 序列化（键排序） |

#### 单一真源：分词代码如何共享

构建期是 Node（CommonJS），运行时是浏览器（IIFE）。**同一份分词逻辑不能写两遍**（否则索引期与查询期行为不一致，会产生极难排查的召回 bug）。推荐做法：

```text
demo/js/search-tokenizer.js      ← 唯一真源，写成 UMD 风格（无构建依赖）
                                   浏览器：<script> 直接加载，挂到 window.FXTokenizer
                                   Node  ：require("./demo/js/search-tokenizer.js")
```

用 `typeof module !== "undefined" && module.exports` 判断环境导出。**这是零依赖条件下共享代码的标准做法**，仓库里已有先例（build-portal.cjs 与 ui.js 都是手写 IIFE，无构建步骤）。

> **替代方案（不推荐）：** 构建脚本里 eval 读取 search-tokenizer.js。可行但调试体验差、安全审计难看。首选 UMD 导出。

### 4.8 与 build-portal.cjs 的衔接

| 维度 | build-portal.cjs | build-search-index.cjs（新增） |
|---|---|---|
| 职责 | 把 tokens/components/ui 内联进 demo/index.html | 把 content/ 编译成 demo/search/** |
| 输入 | demo/css/*.css、demo/js/ui.js、demo/index.html | content/** |
| 输出 | 就地改 demo/index.html | 写 demo/search/ 目录树 |
| 校验 | --check：重建后与磁盘逐字节比较，不一致退出 1 | **同范式**：重建全部产物到内存，逐文件比较 sha256 |
| 退出码 | 0 一致 / 1 不一致 | 0 一致 / 1 不一致 / 2 数据校验失败 |
| 触发时机 | 改 css/js 后 | 改 content/ 后 |

**两者互不依赖，可以并行。** 建议在 README 的构建段落追加一条组合命令（实现阶段）：

```bash
node build-portal.cjs --check && node build-search-index.cjs --check
```

#### --check 的校验思路（详细）

1. 读取 search/_meta.json，拿到上次构建的清单：{v, docs, files: {路径: sha256}}
2. 在内存中**完整重建**一遍全部产物（不写盘）
3. 逐文件比较 sha256：
   - 全部一致 → 打印「搜索索引与 content/ 一致（N 篇教程，M 个 term）」→ 退出 0
   - 有不一致 → 列出**前 5 个**差异文件 + 每个文件的 sha256 前 8 位对比 + 提示运行 node build-search-index.cjs → 退出 1
   - 磁盘上有 _meta.json 未列出的多余文件 → 视为不一致（防止删稿后残留）
4. **可复现性要求：** 重建必须逐字节确定。所有 JSON 序列化用**排序键**，数组顺序由 docId / term 字典序决定，**禁止**使用时间戳、随机数、文件系统遍历顺序（readdir 顺序不保证稳定，必须显式 sort()）。

### 4.9 增量构建与全量构建

**结论：不做真正的增量构建，做「分词结果缓存」。**

理由：一篇教程的约 150 个 term 经哈希后会散布在 16 个分片里，任何一篇变更都会导致 16 个分片全部重写 —— 「增量」在分片层面不成立。而全量构建的成本极低（见下），没必要为它引入增量的复杂度与状态不一致风险。

| 构建模式 | 触发 | 耗时目标 | 说明 |
|---|---|---|---|
| 全量 | node build-search-index.cjs | 100 篇 ≤ 2 s / 300 篇 ≤ 5 s / 1000 篇 ≤ 15 s | 无缓存也达标 |
| 缓存加速 | 同上（默认开启） | 约 -40% | _build/cache.json 存 {slug: {sha256, terms}}，正文未变则复用 terms |
| --check | 校验 | 与全量相同（**不用缓存**） | 必须可复现，缓存会掩盖 bug |
| --no-cache | 强制全量重算 | 同全量 | 排查缓存相关问题时用 |

**缓存文件不进 git**（写进 .gitignore），search/ 产物进 git（与 demo/index.html 产物进 git 的既有约定一致）。

| 项 | 策略 |

| 版本号格式 | YYYYMMDD<小写字母>，与仓库既有的 ?v=20261011j 一致 |
| 写入位置 | **HTML 里写死**：./search/inv/7.json?v=20261011a（由 build-search-index.cjs --write-html-versions 或既有 bump-asset-versions.cjs 处理） |
| _meta.json 的作用 | 仅供 --check 与人工排查，**运行时可选读取**（默认不读，省一次往返） |
| nginx 缓存 | .json 已在 gzip 长缓存范围内（README「服务器 nginx 要点」），无需改配置 |
| 强刷兜底 | 运行时捕获分片加载失败 → 去掉 ?v= 重试一次 → 仍失败则降级到 §6.8 的无索引模式 |

> **为什么不运行时读 _meta.json 拿版本：** 那会引入一次额外往返（首字输入时 +1 RTT），且在 nginx 长缓存下 _meta.json 本身也可能被缓存住，反而增加不一致风险。把版本写在 HTML 里，与仓库既有做法完全一致，且 HTML 本身不进长缓存。

## 5. 检索与排序

### 5.1 检索流程

```text
search(rawQuery):
  q = normalize(rawQuery)                     # §3.2
  terms = tokenize(q)                         # §3.3 → [{term, kind, pos}]
  terms = dropStopwords(terms)                # §3.9（只降权，不删）
  expanded = expandSynonyms(terms)            # §3.5.2，上限 24 个
  shards = unique(expanded.map(shardOf))      # §4.5，最多 16 片
  await loadShards(shards)                    # 冷查询：并行 fetch
  cands = {}                                  # docId → {fields: bitmask, tf: {}, hits: []}
  for t in expanded:
    for [docId, fieldMask, tf] in posting(t.term):
      acc = cands[docId] ||= {fields: 0, score: 0, phrase: 0}
      acc.fields |= fieldMask
      acc.score += bm25Term(t, docId, fieldMask, tf)
  rank = sort(cands, byScoreThenTiebreak)     # §5.6
  return rank.slice(0, TOP_N)
```

### 5.2 字段权重表

| 字段 | 代号 | 权重 W_f | 是否进倒排 | 是否参与 BM25 长度 | 说明 |
|---|---|---|---|---|---|
| 标题 title | T | **8.0** | ✅ | ✅ | 最强信号 |
| 别名 alias | A | **6.0** | ✅ | ✅ | 口语整句，命中即高相关 |
| 症状 symptoms | S | **4.0** | ✅ | ✅ | 召回主力，权重略低于别名 |
| 标签 tags | G | **3.5** | ✅ | ✅ | 分类信号 |
| 小标题 h2/h3 | H | **2.5** | ✅ | ✅ | 语义锚点 |
| 正文 body | B | **1.0** | ✅（独立分片） | ✅ | 兜底召回 |
| 拼音（T/A/G 派生） | P | **2.0** | ✅ | ❌（不参与长度） | 只在无其它命中时贡献 |
| 错别字变体 | V | 继承原字段 × **0.85** | ✅ | ❌ | 已在权重里体现 |

> **长度口径统一：** 文档长度 dl(d) = Σ_f（该字段的 term 数 × W_f），即**加权长度**。这样「标题长」比「正文长」惩罚更重，符合直觉。

### 5.3 评分公式（BM25 + 字段加权，可直接实现）

对查询 q 与文档 d：

```text
score(q, d) = Σ_{t ∈ q}  Wq(t) · IDF(t) · SAT(t, d) · Bcov(d, t)

其中：

  tf'(t, d) = Σ_{f : t 命中 d 的字段 f}  tf(t, d, f) · W_f          # 加权词频，tf 上限 255
  dl(d)     = Σ_f  len(t, d, f) · W_f                                # 加权文档长度
  avgdl     = mean(dl(d))  over all d                                # 构建期算好，写进 _meta.json

  SAT(t, d) = tf'(t,d) · (k1 + 1) / ( tf'(t,d) + k1 · (1 - b + b · dl(d)/avgdl) )

  IDF(t)    = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )            # N=总篇数，df=含 t 的篇数
```

| 常数 | 取值 | 理由 |
|---|---|---|
| k1 | **1.2** | BM25 通用默认；本语料词频低（单篇 1700 字），无需调高 |
| b | **0.75** | 通用默认。**注意：教程长度差异小（1600–2200 字），b 的影响有限，保持默认即可** |
| IDF 形式 | ln(1 + (N-df+0.5)/(df+0.5)) | Lucene 式，**恒为正**，避免 df > N/2 时出现负分 |
| tf 上限 | 255 | 与 posting 的 1 字节编码一致 |

**三个可调旋钮与触发条件（构建期写入 _meta.json，运行时读取，改值不需要重建索引）：**

| 旋钮 | 默认 | 何时调整 | 观察指标（§9） |
|---|---|---|---|
| k1 | 1.2 | 长教程总是输给短教程 → 调低到 1.0 | 测试集 Top1 命中率 |
| b | 0.75 | 短教程（如「蓝屏代码速查」）排名异常靠后 → 调低到 0.5 | 同上 |
| 字段权重 W_f | 见 §5.2 | 别名召回不足 → 提高 A；标签污染结果 → 降低 G | 分类查询的精确率 |

### 5.4 短语匹配与精确匹配加成

| 加成 | 条件 | 系数 | 实现 |
|---|---|---|---|
| B_exact_title | 归一化后的查询串与标题**完全相等** | **×1.60** | 构建期给每篇生成 titleKey，运行时哈希比对 |
| B_exact_alias | 与某条别名完全相等 | **×1.50** | 同上，构建期生成 aliasKeys 集合 |
| B_phrase | 查询的**全部 bigram** 在同一字段内**位置连续** | **×1.35** | 见下方位置校验 |
| B_prefix | 标题以查询开头 | **×1.20** | 字符串 startsWith |
| B_field_cov | 命中字段数 ≥ 2 | ×(1 + 0.06 × (min(k,4) − 1))，k=命中字段数 | fieldMask 的 popcount |

**B_phrase 的位置校验（关键）：** 倒排里不存位置（位置表会让索引体积膨胀 3–5 倍，不可接受）。改为**按需校验**：

1. 先按普通 BM25 排出候选 Top 30（此时已加载了 core 元数据里的 title）
2. 对这 30 篇，从 full/<首字符>.json 取 alias/symptoms 文本
3. 对 title/alias/symptoms 三个短字段做一次 **indexOf 子串检查**（成本 O(30 × 3 × 30 字符)，<0.1 ms）
4. 命中则施加 B_phrase

> **为什么可行：** 这三个字段是**短文本**（标题 14 字、别名 8 字、症状 10 字），逐条 indexOf 完全可负担。而正文不做位置校验（只做 B_phrase 的降级版：全部 bigram 命中同一字段即算 ×1.15）。

### 5.5 时效与热度因子

| 因子 | 公式 | 取值范围 | 说明 |
|---|---|---|---|
| 时效 R | 1 + 0.10 · exp(−ageDays / 540) | 1.00 – 1.10 | ageDays 从 updated 算起；540 天半衰后仍有 0.5 的增量，避免老教程被完全压制 |
| 热度 H | 1 + 0.10 · ln(1 + hot) / ln(1 + maxHot) | 1.00 – 1.10 | maxHot 构建期写入 _meta.json；hot=0 时为 1.00 |
| 合计 | R × H | 1.00 – 1.21 | **上限 1.21，刻意压住**：故障排查场景下「相关」永远优先于「新」与「热」 |

**首期 hot 的来源：** 手工标注（0–100）+ 构建期用「被多少篇教程的 aliases 引用」做一次自动加权。**不做点击埋点驱动的热度**（会引入追踪，违背 §8 的轻量原则）。

### 5.6 同分排序与 Top-N 截断

**同分排序链（逐级比较，前者相等才比后者）：**

1. score 降序（保留 6 位小数比较）
2. **精确命中优先级**：title 精确 > alias 精确 > 其它
3. hot 降序
4. updated 降序（新的在前）
5. slug 字典序升序（**最终确定性兜底，保证同分结果稳定可测**）

**Top-N 截断：**

| 位置 | N | 说明 |
|---|---|---|
| 下拉即时结果 | **8** | 超过 8 条用户不会看；第 9 条位置放「查看全部 N 条结果 →」 |
| 结果页首屏 | **20** | 与「加载更多」步长一致 |
| 「加载更多」步长 | 20 | 最多到 100 条 |
| 候选池上限 | **400** | 打分前先按 fieldMask 粗排截断，防止某高频 term 拉回 300 篇全部参与完整打分 |

> **候选池截断的粗排规则：** 按「命中字段权重和」降序，权重和相同时按 docId 升序。这一步只做位图 popcount 与查表加法，成本 O(候选数)，可把 300 篇候选压到 400 以内（首期本来就不到 400，等于不生效；300 篇以上才起作用）。

### 6.2 结果高亮算法（中文 bigram 命中）

**难点：** 用户输入「电脑连不上网」，命中的是症状「电脑连不上网了怎么办」—— 高亮整段还是高亮词？

**算法（构建期与运行时共用同一个函数）：**

```text
highlight(text, query):
  q = normalize(query)
  spans = []                                  # [start, end) 数组
  # 1) 整串优先
  i = text.indexOf(q)
  if i >= 0: spans.push([i, i + q.length])
  # 2) 否则按 bigram 覆盖
  else:
    for each bigram b in tokenize(q) where b.kind == "bi":
      j = 0
      while (j = text.indexOf(b, j)) >= 0:
        spans.push([j, j + b.length]); j += 1
    # 3) 词典词优先于 bigram：若某个 bigram 被更长词典词覆盖，丢弃该 bigram span
  # 4) 合并相邻/重叠 span
  spans = mergeOverlapping(spans)             # 相邻（end == next.start）也合并
  return spans
```

**渲染规则：**

| 规则 | 说明 |
|---|---|
| 高亮标签 | mark class="fx-hit" |
| 合并阈值 | 两个 span 之间的间隔 ≤ 2 个字符时也合并（避免「连**不**上**网**」这种碎片化高亮） |
| 单条结果最多高亮 | **6** 个 span（防止整段变黄） |
| 超长文本 | 只取**第一个命中 span 前后各 30 字符**的窗口做展示，窗口内高亮 |
| 安全性 | 全程 textContent 拼装 DOM 片段，**禁止** innerHTML 插入用户输入 |

> **为什么不做「结果页高亮跳转」那类能力：** 我们的高亮要作用在**索引里的结构化字段**（title / alias / symptoms）上，而这些字段在最终页面上未必逐字出现（教程页会重新组织措辞）。用索引字段做高亮反而更稳定。

### 6.3 零结果兜底

零结果是最重要的**内容缺口信号**（§8 会记录它）。UI 上给三级兜底：

| 级别 | 触发 | 展示内容 |
|---|---|---|
| L1 换词建议 | 同义词表里存在与查询相关的规范词 | 「你是不是想找：**上不了网**、**断网**」——点击直接替换查询 |
| L2 同领域热门 | 一定能拿到（除非索引未加载） | 该查询**最长 term** 对应的 domain 下 hot 最高的 4 篇；无法判定 domain 时取全站 hot Top 4 |
| L3 症状向导入口 | 始终展示 | 「不知道从哪下手？按现象逐步排查 →」链接到向导页（§6.9） |

**L1 的换词建议生成：** 对查询的每个 term，在 syn.json 里找编辑距离 ≤ 2 或存在共同 bigram 的规范词，按共同 bigram 数降序取前 3 个。全部在客户端完成，无额外请求。

### 6.6 与 ui.js 的 data-* 约定衔接

**新增能力全部走 data-* 驱动，元素缺失即跳过**（与 ui.js 的既有范式完全一致）：

| 属性 | 作用 | 缺省行为 |
|---|---|---|
| data-search | 在容器上声明搜索组件，值为结果页路径（如 ./search.html） | 无此属性 → 不初始化，零成本 |
| data-search-input | 标记输入框 | 缺失 → 组件不启用 |

| data-search-hot | 标记「热门教程」容器，由组件填充 | 缺失 → 不填充 |
| data-search-zero | 标记零结果兜底容器 | 缺失 → 用组件内置默认块 |

**集成方式（推荐）：**

1. **不改 ui.js。** 新增 demo/js/search.js，同样写成 IIFE + ES5 + data-* 驱动，在 ui:ready 事件后自初始化。理由：ui.js 被 build-portal.cjs 内联进门户单文件，动它要重跑构建并可能影响三站，风险大于收益。

4. link 顺序遵循 README 约定：tokens → base → components → search.css → 站点 → 主题。
5. 版本号沿用 ?v= 机制；search.js / search.css 加入 bump-asset-versions.cjs 的 FILES 处理范围（实现阶段）。

### 6.7 加载时机

| 时机 | 动作 | 体积代价 |
|---|---|---|
| 页面加载完成（load 事件后） | **不加载任何索引** | 0 |
| requestIdleCallback（超时 2000 ms） | 预取 tables/syn.json（16 KB gzip） | 16 KB |
| 输入框首次 focus | 预取全部 16 个主倒排分片 + 4 个 core 分片（并行，HTTP/2） | 约 184 KB gzip |
| 首次输入（若 focus 未触发，如程序化填充） | 同 focus 路径 | 同上 |
| 结果页（search.html）直接带 q= 打开 | 立即并行拉取（用户已明确意图） | 同上 |
| 正文倒排 invb/* | **仅当** R1–R7 命中 < 3 篇时 | 45 KB gzip |
| tables/py.json | **默认不加载**（拼音已内联在倒排里） | 0 |
| full/<首字符>.json | 结果页渲染详情卡片时，按需拉命中的首字符片 | 约 7 KB gzip/片 |

> **为什么 focus 时预取全部 16 片而不是按需：** 按需意味着「输入 → 算分片 → fetch → 再渲染」多一次 RTT（4G 下约 80–120 ms）。16 片并行在 HTTP/2 下只需一次往返（约 184 KB / 12 并发），体验明显更好。代价是首查多下载约 150 KB —— 对「已经点了搜索框」的用户，这个代价是合理的。

### 6.8 降级路径（三级）

| 级别 | 触发条件 | 降级行为 |
|---|---|---|
| D1 正常 | 索引加载成功 | 全部能力 |
| D2 索引失败 | fetch 失败（含去掉 ?v= 重试后仍失败）、JSON 解析失败、版本不匹配 | 搜索框仍可用：回车 → search.html?q=...，该页展示**静态分类列表** + 「搜索暂不可用，请按分类浏览」提示（用 UI.toast 或内联提示） |
| D3 无 JS | html 无 .js 类（ui.js 未执行） | 搜索框不渲染为输入框，改为**分类导航 + 热门教程静态列表**（构建期直接写进 HTML） |

**D3 的实现要点：** search.html 里预置一份**静态分类区块**（8 个 domain × 各 3 篇热门），默认 display:block；ui.js 执行后加上 .js 类，CSS 用 html.js .fx-fallback { display:none } 隐藏它。这与仓库既有的「html:not(.js) 初始隐藏态」约定同源（components.css 里已有 .ui-card__media img 的先例）。

> **验收要求：** 禁用 JS 打开 search.html，必须能看到 8 个分类、每个分类至少 3 篇可点教程，且 h1 与页面标题正确。

### 6.9 症状向导入口（与搜索并列的第二入口）

有些用户连「现象怎么描述」都不知道。search.html 提供一条不依赖关键词的路径：

```text
第 1 步：哪里出问题？  [开不了机] [能开机但很慢] [连不上网] [屏幕不正常] [有异响/很烫] [弹窗/中毒]
第 2 步：什么时候开始的？ [今天突然] [最近才这样] [一直这样]
第 3 步：最近改过什么？ [装过软件] [插过新硬件] [没动过] [不知道]
       ↓
   按 (domain, 答案组合) 查表 → 推荐 3–5 篇
```

**实现：** 一个静态 JSON 映射表（约 40 条规则，每条约 120 字节，共 5 KB 未压缩 / 1.8 KB gzip），构建期由人工编写、脚本校验其引用的 slug 都存在。**零运行时计算**，纯查表。

### 7.2 时间预算表

| 指标 | 目标 | 达标手段 | 低配机（4 核 / 4GB / 机械盘）预期 |

### 7.5 缓存与 ?v= 策略

| 项 | 策略 | 理由 |
|---|---|---|
| 版本号位置 | HTML 内联写死（如 inv/7.json?v=20261011a） | 与仓库既有 ?v= 约定一致；HTML 不进长缓存 |
| 索引分片缓存头 | 沿用 nginx 对 .json 的 30d 长缓存 | 无需改 nginx 配置 |
| search.js / search.css | 走既有 bump-asset-versions.cjs | 零新增机制 |
| 版本不一致检测 | 每片返回 v 字段，运行时与首个成功加载的片比对；不一致 → 全量重取（去掉 ?v=）一次 | 防止边缘缓存导致半新半旧 |
| 强刷兜底 | 见 §6.8 D2 | 用户永远有可用路径 |
| 离线可用 | 首次加载后，索引已在内存，断网仍可搜索 | 优于服务端方案 |

## 8. 可测量性：零结果查询的轻量记录

### 8.1 原则

| 原则 | 说明 |
|---|---|
| 无第三方追踪 | 不引入 GA / 百度统计 / Sentry / 任何外部脚本或像素 |
| 不采集个人标识 | 不记录 IP、UA、Cookie、设备指纹、用户 ID |
| 只记录「缺什么」 | 记录零结果查询词 + 时间 + 结果数（恒为 0），用于补内容 |
| 默认最小化 | 默认只记录**零结果**查询，不记录成功查询（成功查询无内容价值，且隐私面更大） |
| 可一键关闭 | 站点提供开关（本地存储记忆），或整站禁用 |

### 8.2 三种方案对比

| 方案 | 机制 | 需要服务端 | 隐私面 | 实时性 | 实现成本 | 结论 |
|---|---|---|---|---|---|---|
| **A. 纯本地** | 零结果写入 localStorage，最多 200 条环形缓冲 | ❌ 不需要 | 无（数据不出浏览器） | 无（只有用户自己能看到） | 0.5 人日 | ✅ 兜底 |
| **B. 自托管被动日志** | 零结果时用 sendBeacon 请求 /fx-miss?q=...，返回 204；**nginx access_log 天然记下 URL** | ⚠️ 只需 nginx 配置三行 | 低（日志格式刻意不含 IP） | 高（当天可看） | 1 人日 | ✅ **推荐** |
| C. 第三方埋点 | 引入外部脚本 | ❌ | 高 | 高 | 0.5 人日 | ❌ 违背原则 |

### 8.3 推荐方案：B（自托管被动日志）+ A（本地缓冲）

**前端（search.js，约 15 行）：**

```text
onZeroResult(q):
  buf = localStorage.fx_miss || []            # 方案 A：本地缓冲
  if buf.length < 200: buf.push({q, t: Date.now()})
  localStorage.fx_miss = buf
  if navigator.sendBeacon:                    # 方案 B：尽力发送，不阻塞
    navigator.sendBeacon("/fx-miss?q=" + encodeURIComponent(q))
  else:
    fetch("/fx-miss?q=" + encodeURIComponent(q), {keepalive: true, mode: "no-cors"}).catch(() => {})
```

**nginx（新增三行，实现阶段）：**

```nginx
location = /fx-miss {
    access_log /var/log/nginx/fx-miss.log fxmiss;   # 独立日志，独立格式
    add_header Cache-Control "no-store";
    return 204;                                      # 无响应体，零带宽
}
log_format fxmiss '$time_iso8601\t$arg_q';
```

**统计脚本（运维脚本，零依赖 Node）：**

```bash
node scripts/fx-miss-report.cjs                 # 读日志 → 聚合 → 输出 markdown 表格
```

输出示例（用于决定下一篇教程写什么）：

| 排名 | 查询词 | 次数 | 建议动作 |
|---|---|---|---|
| 1 | 电脑自动重启 | 37 | 新增教程（boot 域） |
| 2 | 微信打不开 | 29 | 新增教程（system 域） |
| 3 | 屏幕一闪一闪 | 18 | 检查是否已有 display 域教程的同义词缺失 |

### 8.4 隐私与合规

| 项 | 处理 |
|---|---|
| 查询词中可能含个人信息 | 上报前**丢弃长度 > 30 的查询**；对含 ≥ 8 位连续数字（疑似手机号 / 身份证）的查询**不上报**，只本地记录 |
| IP 地址 | nginx 侧把 fx-miss.log 的格式限定为「时间 + q」，**不写 $remote_addr** |
| 日志保留 | 保留 90 天，之后由 logrotate 自动轮转删除 |
| 用户可见 | privacy 页面追加一段说明：「我们仅在搜索无结果时记录你输入的关键词，用于补充教程内容；不含任何身份信息。」 |
| 关闭方式 | 站点设置里提供「不发送搜索反馈」开关，关闭后只写 localStorage |

### 8.5 可测量的其他指标（本地计算，不上报）

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 首查耗时 | performance.now() 差值，写入 window.__fxStats | 开发期验证 §7.2 预算 |
| 索引加载失败率 | 捕获 fetch 失败，计数写入 localStorage | 判断 nginx 缓存策略是否出问题 |
| 分片命中分布 | 每次查询记录了哪些分片，累计分布 | 判断哈希是否均匀（若某片命中率 > 25%，说明哈希有问题） |
| 结果页跳出 | 结果页到教程页的点击率（本地计数） | 排序质量代理指标 |

## 13. 结论

**最终推荐方案（一句话）：** 采用**自研的预构建分片倒排索引** —— 构建期用零依赖的 Node 脚本把教程 front-matter 与正文编译成按 term 哈希切分的静态 JSON 分片，运行时用零依赖的 ES5 脚本在浏览器内完成「bigram + 词典 + 同义词 + 拼音 + 错别字」五层召回与 BM25 字段加权排序，首屏仅付 12.6 KB gzip、首查按需拉取约 204 KB gzip、热查询 < 50 ms，完全不引入 npm 运行时依赖，也不引入任何服务端进程。

**关键取舍：**

1. **自研而非 Pagefind** —— 用 3–5 人日的开发成本，换回对中文分词、同义词、别名、拼音、错别字五层的完全控制。Pagefind 的 CJK 分词由官方规则决定，无法注入「内存条」「IP 冲突」「蓝屏代码」这类领域词典，也无法配置同义词（官方文档未见该能力）。
2. **哈希分片而非 termId 分片** —— 用约 6% 的额外索引体积，换掉运行时 150 KB 的词表依赖。
3. **字段权重不进 posting** —— 用 1 字节位图 + 全局权重表，让「调权重」从「重建索引」降级为「改一个常量」。
4. **索引瘦、查询胖** —— 同义词与变体扩展全部放在查询侧，索引侧只存忠实表示。
5. **拼音只覆盖标题 / 别名 / 标签** —— 用 15% 的体积换「不会打汉字」的一整类查询；正文全拼性价比不成立。
6. **错别字用构建期替换表** —— 用 12% 的体积换掉客户端编辑距离的 2–8 ms 计算与高假阳性。
7. **零结果才记录** —— 用 nginx 的一行日志换内容缺口情报，不引入任何第三方追踪。

**主要风险：**

1. **同义词表覆盖不足（K1，概率中 / 影响高）** —— 这是本方案唯一可能「致命」的风险。缓解手段是把它变成持续工程：上线后每周看零结果 Top 20。
2. **词典长期维护负担（K4，概率高 / 影响中）** —— 若无人维护，系统会退化为「纯 bigram + 同义词」，召回不塌但排序变差，属于可接受的降级。
3. **索引体积超预算（K2）** —— 已设构建期硬守卫，且有明确的「先砍什么」顺序（全拼拼音 → 错别字变体 → 正文截断）。
4. **低配机性能（K3）** —— 已用 ES5 + 无 DOM 重建 + 候选池截断三重手段压制，并设了 90 ms 的放宽线。
5. **格式反复（K7）** —— 索引层只依赖「front-matter + 纯文本」抽象，Markdown 与 HTML 两种源格式都能吃。
