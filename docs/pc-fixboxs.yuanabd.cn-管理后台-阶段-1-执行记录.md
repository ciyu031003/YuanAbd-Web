## 2. 关键设计决策：为什么没有引入 gray-matter

V2 方案 §3.1 推荐用 `gray-matter` + `eemeli/yaml`。**执行时我改用了自研零依赖实现**，理由如下（这是对方案的一处有意偏离，必须记录）：

**决定性实测**：把 `js-yaml` 装到独立沙箱后实测同一篇文件——
`yaml.load()` **能**正确解析 `sources` 嵌套对象（url 不再丢失），
但 `yaml.dump()` 会把**行内数组改写成块状列表**：

```
os: [Windows 10, Windows 11, macOS 12+]        （原文，行内 flow 风格）
os:                                            （js-yaml dump 输出，块状）
  - Windows 10
  - Windows 11
  - macOS 12+
```

并把 `version: "1.0"` 改写成 `version: '1.0'`。

**后果**：只要后台「保存一次」，30 篇**全部产生 diff** —— 内容没变但历史全乱，
之后 `git log` 再也无法回答「这篇什么时候真的改过」。这正好违反 V2 自己定的
**R8（未改动字段不得产生 diff，逐字节比对）**。

**方案对此已有预判**，§7.3.4 明确写了「实现上建议采用**最小改写**策略」。本实现即按该策略落地：

1. **保留原文行**：未变更的字段**原样输出原文那一行**，不重新生成；
2. 只有值真的变了，才重写那一个字段，且沿用它原本的**形态**（行内数组/块状/标量）；
3. 标量沿用原文的**引号策略**（原文带引号就继续带引号，`version` 因此保持字符串）。

**为什么不用 gray-matter 也能满足要求**：本项目的 front-matter 是**极小的 YAML 子集**——
19 个字段中只有 `sources` 是嵌套结构，形态只有四种（标量 / 行内数组 / 块状数组 / 对象数组）。
自研实现只需覆盖这四种，代码量小、可审计，且**不破坏本仓库「零依赖」的设计契约**
（全仓无 package.json / node_modules，构建脚本只用 Node 内置模块；引入 npm 依赖会要求
lockfile、npm install、服务器侧装依赖，改变整个构建与部署形态）。

> **若日后内容格式复杂到超出该子集**（如引入多行字符串、锚点、注释保留），
> 应改为引入 `eemeli/yaml`（ISC，支持保留注释与键序的 round-trip），
> 并**同步替换** `fx-frontmatter.cjs` 的实现，保持「解析与序列化同源」这一不变量。

## 3. 执行中发现并修掉的一个真实 bug（建库脚本）

初版 `db-init-yuanabd_pc_fixboxs.sql` 用 `DO $$ ... $$` 块创建角色，块内写了 `:'app_password'`。这是**错的**：

> **psql 的变量插值不会在美元引用（`$$ ... $$`）字符串内部发生。**
> 在 DO 块里写 `:'app_password'`，传进去的会是字面量字符串 `:'app_password'`——
> 结果是应用账号的密码变成一个谁都知道的固定串。

**修复**：改用 `\gexec`（先在普通 SQL 里用 `format(%L)` 安全拼出语句，再执行）。
既绕开该陷阱，也天然防注入。脚本内已就地写明原因，避免后来者改回去。

## 4. 一次操作事故与恢复（如实记录）

**为什么没造成永久损失**：该文件当时**尚未入 Git**，但内容由 `v2-account-security` 生成，
我保留了它的任务规格，因此请它按原规格重新生成丢失部分。恢复后 **1512 行**，H2 九章齐全，
且**只做追加**——幸存的 §5/§6 未被改动。

**根因与纠正**：整文件 read→write 是有损风险的。已改为：
- 定位用 `glob`/`grep`，改动用 `edit` 定点替换；
- 确需整文件重写时，先备份；
- **并把 docs/ 纳入 Git**（本次已提交 15 个文档），使其从此受版本保护。
