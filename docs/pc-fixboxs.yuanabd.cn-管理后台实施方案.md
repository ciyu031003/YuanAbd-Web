## 0. 结论先行

| 判断 | 结论 |
|---|---|
| 要不要做后台 | **要做。**「多人 + 网页登录 + 不碰 Markdown/Git」正是工作流方案 §7 的触发条件 #1。更关键的是：**本站自己的内容规范就要求后台级治理**——代理/VPN 类内容必须由第二人复核合规项后才能发布（内容体系 §8.2 规则 7）、超过 12 个月未更新要打过期标记（§7.4）、失效文章「归档而非删除、URL 必须保留」（§7.5）。这些动作在纯 Git 里只能靠自觉，在后台里可以变成硬约束。 |
| 做什么形态的后台 | **「Git 写入型内容后台」**：后台是编辑器 + 流水线控制器，**内容真源仍是 `content/fixboxs/*.md` + Git**；数据库只存账号、会话、审计、媒体元数据、发布任务，**不存正文**。 |
| 与工作流方案的关系 | DSH 的结论「不需要后台」在**单人维护**前提下是对的。前提换成「多人、非技术、网页发稿」后结论翻转——所以不是那份方案写错了，是它的前提被你的新需求替换了。但它指出的两个真实缺陷（**构建静默吞错**、**部署只校验 6 个 URL**）**仍然必须先修**：后台会让内容变更频率上升一个量级，闸门不补等于放大事故。 |
| 与架构评审的关系 | 架构评审 §7 的 N1（后台）/N2（数据库）/N3（RBAC）三条排除项，同样建立在「单人/小团队 + 无需网页发稿」前提上。本方案是对该前提的显式变更；评审对静态管线的其余建议（SEO、检索、聚合页）**不受影响，仍然照做**。 |
| 工作量 | **前置闸门 2–3.5 人日 + 后台 MVP 10–14 人日 ≈ 13–17.5 人日**；含审核流/媒体/回滚/冲突处理的 v1.5 再加 6–9 人日。 |
| 最大风险 | 不在技术，而在**新增的运维责任**：引入常驻服务后，备份、证书、升级、日志、安全从「零」变成「一套」。§9 单列管控。 |

**三条铁律（任何阶段不可让步）**

1. 内容真源永远是 Markdown + Git，**数据库不得成为正文的唯一副本**；
2. 后台只能「写出同样格式的 Markdown」，`build-fix.cjs` 的输入契约一行不改；
3. 前台站点保持纯静态，**运行时不依赖后台**（后台挂掉，站照常访问）。

## 1. 需求拆解与判定依据

### 1.1 你的诉求 → 工程需求

| 你的诉求 | 工程需求 | 对方案的约束 |
|---|---|---|
| 不想「改 MD 再推送」 | 提供网页表单 + Markdown 编辑界面 | 后台必须能读写 `content/fixboxs/*.md`，而不是维护另一套数据 |
| 想让其他人一起加入 | 独立账号体系 + 邀请 + 角色权限 | **不能要求协作者持有 GitHub 账号**（否则只是把 Git 换成 GitHub，摩擦没消失） |
| 更新 + 新增文章 | 文章 CRUD + 草稿 + 预览 + 发布 | 需要草稿态与未发布内容的隔离机制 |
| 「管理后台是必须要做的」 | 一个可长期运营、可审核、可追溯的内容中台 | 需要审核流、审计日志、回滚能力 |

### 1.2 别忘了：本站的内容规范本身就要后台

这是决定「要不要上后台」最强的论据，比「改稿麻烦」更硬：

| 内容规范要求 | 出处 | 纯 Git 能做到吗 | 后台能做到吗 |
|---|---|---|---|
| 代理/VPN 类内容须由**第二人复核合规项**后才能发布 | 内容体系 §8.2 规则 7 | ❌ 只能靠自觉（PR review 要对方会 Git） | ✅ 角色 + 状态机强制 |
| 内容被证明错误时**立即下架正文**并指向正确文章 | §7.5 | ⚠️ 需人工快速改文件 | ✅ 一键下架 + 保留 URL |
| 失效文章**归档而非删除，URL 永久保留** | §7.5 | ❌ 容易误删 | ✅ 归档态 + 归档页/301 |
| 超过 12 个月未更新要显示过期提示 | §7.4 | ⚠️ 需人工统计 | ✅ 构建期自动打标 + 后台提醒 |
| 90 天/季度复核排期 | §7.4、架构评审 P1-⑦ | ❌ 无 | ✅ 待复核列表 |
| 每篇 19 个字段 + 固定 10 段结构 | 内容体系 §5.1/§5.2 | ⚠️ 靠肉眼 | ✅ 表单约束 + 校验拦截 |
| 每篇文章变更留痕（日期/版本/改了什么/谁改的） | §5.2 第 10 段「更新日志」 | ✅ Git | ✅ 由提交信息自动写入 |

**结论**：本站不是「一个可以只靠 Git 的博客」，而是**带合规复核要求的知识库**。这是后台的正当性来源。

### 1.3 前台仍然不做账号

门户设计方案 §2.4「不做用户账号/登录体系」指的是**读者**。本方案的账号体系只服务**编辑者**（预计 2–10 人），前台读者体验、性能预算、零依赖约束完全不变。

## 2. 选型：三条路线

| 路线 | 形态 | 协作者需要什么 | 新增常驻服务 | 内容真源 | 工作量 | 判定 |
|---|---|---|---|---|---|---|
| **A** | Git 后端 CMS（Sveltia / Decap + OAuth 中转） | 一个 GitHub 账号 + 被加为仓库协作者 | 几乎无（仅 OAuth 中转） | GitHub 仓库 | 2–4 人日 | ⚠️ 备选。只在「协作者都能接受 GitHub 账号」时成立 |
| **B** | 自建轻量内容后台（Git 写入型） | **只需浏览器 + 账号密码** | 1 个容器（Web + 发布 worker） | Git 仓库（不变） | 10–14 人日 | ✅ **推荐（目标架构）** |
| **C** | DB-first CMS（Payload / Strapi / Directus） | 浏览器 + 账号 | CMS 服务 + DB | 数据库 | 25–40 人日 | ❌ 否决：正文进库即成唯一副本，违反铁律 1；现有构建/部署链路全部作废 |

### 2.1 为什么推荐 B

1. **完全命中你的诉求**：协作者不需要 GitHub 账号、不需要 Git 知识、不需要本地环境，浏览器登录即用。
2. **最大化复用现有资产**：`content/` 格式、`build-fix.cjs`、`deploy-fixboxs.cjs`、`deploy-fixboxs.sh`、nginx 静态托管全部不动。后台只接在**「写文件」和「触发发布」**两个点上。
3. **可逆**：将来若想回到纯 Git 工作流，删掉后台即可，内容与流水线毫发无伤。
4. **权限可控**：可以精确到「某编辑只能改某个领域」（架构评审 N6 曾指出 GitHub 做不到，正好用后台补上）。

### 2.2 A 什么时候仍然更划算

如果满足**全部**条件，A 是更快的选择，可以先用它跑起来：

- 协作者都能且愿意注册 GitHub 账号；
- 仓库可以设为私有，或能接受协作者对仓库有写权限；
- 你能接受「后台登录 = GitHub OAuth」，账号生命周期由 GitHub 管。

**A 的真实代价**（为什么它不是「免费」）：GitHub 的 OAuth 不能纯前端完成，必须有一个 OAuth 中转（Cloudflare Worker / Vercel 函数）。加上中继后，A 的运维面并不比 B 小多少，只是开发量小。

### 2.3 一个可选的降本思路（在 B 内部做一次技术选型）

「自建后台」不等于「从零手写编辑器」。阶段 1 设一个 0.5 人日的**技术刺探（spike）**，在下面两者间定夺：

| 方案 | 得到什么 | 代价 |
|---|---|---|
| 自建 UI + 成熟 Markdown 编辑器组件（如 CodeMirror 6 / Toast UI Editor） | 完全贴合 19 字段 + 10 段结构，可强制骨架 | UI 代码量最大，约 3–4 人日 |
| 复用成熟 CMS 前端（Keystatic / Decap / Sveltia）+ 自建最小后端与认证 | 列表/编辑/媒体界面近乎白拿，开发量降一半 | 需适配其 schema 与 API 协议；10 段正文骨架的强制力较弱，需用「服务端校验 + 预览」兜底 |

> 决策原则：**谁都不能替代服务端校验**。无论 UI 用什么，发布前一律走 §5.4 的同一套 validator。

## 3. 目标架构

### 3.1 全景

```
编辑者（浏览器，任意网络，含手机）
        │ HTTPS
        ▼
┌──────────────────────────────────────────────────────────────┐
│ nginx （106.55.2.197，现有实例）                               │
│   ├─ pc-fixboxs.yuanabd.cn        → /var/www/fixboxs （静态，不变）│
│   └─ admin.pc-fixboxs.yuanabd.cn  → 127.0.0.1:3020   （新增反代） │
└──────────────────────────────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────────────────────┐
│ 容器 fixboxs-admin （新增）                                    │
│   ├─ Web 进程    认证 / RBAC / 文章读写 / 预览 / 校验 / 审计      │
│   ├─ 发布 worker 单并发队列：commit → build → deploy → verify   │
│   └─ SQLite     账号 / 会话 / 审计 / 媒体元数据 / 发布任务        │
└──────────────────────────────────────────────────────────────┘
        │ 读写共享卷 /srv/fixboxs/repo（YuanAbd-Web 工作副本）
        ▼
   content/fixboxs/*.md  ← 唯一内容真源（不变）
        │ git push（备份到 GitHub，保留评审与异地副本）
        ▼
   build-fix.cjs → demo/fixboxs/ → deploy-fixboxs.cjs → dist/fixboxs/
        │
        ▼
   /var/www/fixboxs （原子切换 + /var/www/fixboxs.prev 回滚）
```

### 3.2 组件清单

| 组件 | 职责 | 是否新增 | 说明 |
|---|---|---|---|
| nginx | 静态托管 + admin 反代 + TLS | 现成，改配置 | 新增一个 server 块与证书；现有 fixboxs 块不动 |
| `fixboxs-admin` 容器 | 后台全部服务端逻辑 | **新增** | Node 运行时；监听 127.0.0.1:3020 |
| 发布 worker | 串行执行提交/构建/部署/校验 | **新增** | 与 Web 同镜像、独立进程，保证单并发 |
| 内容工作副本 | `YuanAbd-Web` 的服务器侧 clone | **新增** | 后台只在这里写 `content/`，再由 worker 提交 |
| SQLite | 账号/会话/审计/媒体元数据/任务 | **新增** | v1 单文件、WAL；不含正文 |
| `content/fixboxs/*.md` | 内容真源 | 不变 | 后台与手写产生完全相同的文件 |
| `build-fix.cjs` | 渲染 + 数据产物 | 基本不变 | 后台的构建步骤直接调用它 |
| `deploy-fixboxs.cjs` / `.sh` | 产物化 + 原子部署 + 校验 | 基本不变 | 可能新增 `--local` 模式（见 §7.4） |
| GitHub 远端 | 备份 + 评审 + 异地副本 | 不变 | worker 负责 push；不依赖它也能发布 |

### 3.3 边界（明确不改什么）

- **前台六壳页 + 30 篇教程的展示层**：不动。
- **内容格式与字段**：不动（阶段 0 只补校验，不新增必填字段）。
- **nginx 的静态 server 块**：不动，只新增 admin server 块。
- **部署方式**：仍是「整目录产物 + 原子切换」，不改成 CDN/对象存储。
- **读者侧**：不引入登录、评论、工单。

## 4. 关键设计决策（逐条给结论）

### D1 内容真源：Markdown + Git（结论：保持）

数据库里的 `articles` 表**不存在**。后台读写的就是 `content/fixboxs/*.md`。这样：

- 后台与手写产出**同一份文件**，可互相接管；
- `git revert` 能回滚内容，`.prev` 能回滚产物，两层保险；
- 将来换任何后台或迁移，内容不需要导出。

### D2 草稿与归档怎么放（结论：目录隔离 + 状态字段）

现有构建脚本用 `fs.readdirSync(SRC).filter(f => f.endsWith(".md"))`，**只扫顶层 `.md` 文件**（已核实），因此子目录天然不进构建。利用这一点：

```
content/fixboxs/
├─ wifi-connected-but-no-internet.md   已发布（构建输入，不变）
├─ _drafts/                            草稿 / 审核中 / 退回修改（不构建）
│  └─ new-article-slug.md
└─ _archive/                           归档（不构建，URL 由归档页保留）
   └─ old-article-slug.md
```

| 动作 | 文件变化 | Git 效果 |
|---|---|---|
| 新建草稿 | 写入 `_drafts/<slug>.md`，`status: draft` | 一次 commit（不入构建） |
| 提交审核 | 同一文件，`status: in_review` | 一次 commit |
| 审核退回 | 同一文件，`status: changes_requested` + `review_notes` | 一次 commit |
| 发布 | `_drafts/<slug>.md` **移动**到 `content/fixboxs/<slug>.md`，`status: published`，更新 `updated`/`published_at` | 一次 commit + 触发构建部署 |
| 归档 | 顶层 md **移动**到 `_archive/`，加 `archived_at`/`superseded_by` | 一次 commit + 触发构建（生成归档页/301） |

> **状态写在文件里，不写在数据库里**。这样状态随仓库一起被 clone、diff、回滚，不会与内容漂移。

### D3 写路径（结论：服务器侧工作副本 + push 到 GitHub）

```
后台 Web 写文件 → /srv/fixboxs/repo/content/...
        ↓
发布 worker：git add / commit -m "content: <标题>（<作者>）"
        ↓
git push origin main        （备份 + 保留 GitHub 上的历史；失败不阻塞发布，后台重试）
        ↓
node build-fix.cjs  →  bash deploy-fixboxs.sh
```

选择这个顺序的理由：

- `build-fix.cjs` 实测 0.11 秒、产物化 0.16 秒，**在服务器本地跑比等 GitHub Actions 快一个数量级**；
- GitHub 只承担「备份 + 评审浏览」，不在发布关键路径上，GitHub 抖动不影响发稿；
- 保留 `git log` 作为内容审计的第二来源。

### D4 发布执行者（结论：单并发队列）

发布是一条**有状态、不可并行**的流水线（构建目录共享，部署是整目录切换）。设计：

- worker 单线程，任务表 `publish_jobs` 按创建时间串行消费；
- 同一时刻只允许一个 job 处于 `running`；
- 连续发布自动排队，UI 显示「排队中 / 构建中 / 部署中 / 校验中 / 成功 / 失败」；
- 失败时**不回滚已提交的内容**（内容可能是对的，问题在部署网络），只回滚线上目录并允许「重试发布」。

### D5 并发编辑冲突（结论：内容哈希乐观锁）

两个人同时打开同一篇是必然的。方案：

- 每篇文章在后台列表里带 `content_hash`（对文件内容取哈希）；
- 保存时提交 `base_hash`，服务端比对：不一致 → 返回 409 + 差异视图，让编辑者选择「基于最新版重新编辑」或「另存为副本」；
- **不做静默覆盖**（会丢内容，不可接受）。

### D6 账号与角色（结论：4 角色，服务端强校验）

| 角色 | 新建/编辑草稿 | 提交审核 | 审核/发布 | 归档 | 管用户 | 看审计 |
|---|---|---|---|---|---|---|
| 管理员 admin | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 编辑 editor | ✅ | ✅ | ❌ | ❌ | ❌ | 仅自己 |
| 审核 reviewer | ❌（可改退回稿） | ✅ | ✅ | ✅ | ❌ | ✅ |
| 观察者 viewer | ❌ | ❌ | ❌ | ❌ | ❌ | ❌（只读列表） |

可选细粒度：把 `domain` 作为编辑者的作用域（如「网络线编辑」只能改 `net-basic`/`ip-dns`/`router`）。

### D7 会话与安全（结论：见 §8 逐项落地）

核心：密码 argon2id/bcrypt；会话 Cookie `HttpOnly + Secure + SameSite=Lax`；写操作全部 CSRF token；登录限流与锁定；管理员强制 2FA 开关。

### D8 预览（结论：服务端渲染，必须）

远程协作者没有本地环境，预览只能由服务端出：

1. 用**真实的** `build-fix.cjs` 渲染逻辑渲染草稿（不是另写一个 Markdown 预览器，避免「预览好看、线上变形」）；
2. 预览页挂在 `admin.` 域下的 `/preview/<slug>`，**登录可见**、`noindex`、不进静态站产物；
3. 编辑器右侧可内嵌 iframe 实时预览，也可新窗口打开；
4. 预览里同时展示「构建校验结果」，错误在预览阶段就暴露，而不是到发布才拦。

### D9 图片与附件（结论：v1 支持上传，但压缩与内容管线解耦）

内容体系 §7.2 已有截图规范（WebP、≤200KB、必须脱敏、必须有 alt）。因此：

- 上传落盘到 `content/fixboxs/_assets/<slug>/`（随内容一起版本化），构建时复制到 `demo/fixboxs/img/<slug>/`；
- 后台只做**大小与类型白名单**校验（拒绝 SVG/HTML 防 XSS；重命名随机化防目录穿越）；
- **不做自动压缩**（与架构评审 N12 一致：压缩工具入构建链是唯一真破例，暂缓）；
- 上传时提示脱敏要求，并强制填写 alt。

> 若要更快出 MVP，D9 可后置到阶段 2；本阶段文章没有截图也能写。

### D10 分类字典（结论：先外置，后台后管）

现状 `DOMAINS`/`CATS` 硬编码在 `build-fix.cjs`（架构评审 D5）。后台要让编辑选领域/分类，就必须先把它外置为 `content/taxonomy.json`——这正好是架构评审 P0-4 的工作，**两件事合并做，不重复投入**。

阶段 1 后台只**读** taxonomy（下拉选项）；阶段 2 再给管理员提供分类树的增删改。

### D11 回滚（结论：两个层级）

| 场景 | 手段 | 触发方式 |
|---|---|---|
| 内容写错 | `git revert <commit>` + 重新构建部署 | 后台「版本历史」里一键回滚到某个提交 |
| 部署出问题（产物坏、切换失败） | 把 `/var/www/fixboxs.prev` 切回来 | 后台「紧急回滚」按钮；也可手工 ssh 执行 |

### D12 与静态站的关系（结论：后台不在前台关键路径）

前台绝不 fetch 后台：搜索索引、文章列表、正文全部是构建期产物。后台的可用性只影响「编辑者能不能发稿」，不影响「读者能不能修电脑」。

### D13 部署位置与域名（结论：独立子域 + 同机容器）

- **推荐 `admin.pc-fixboxs.yuanabd.cn`**，而不是 `pc-fixboxs.yuanabd.cn/admin/`：
  - Cookie 与安全头作用域隔离，后台的 XSS/CSRF 风险不波及静态站；
  - 可以单独做 IP 白名单、限流、`noindex`、独立日志；
  - 静态站产物目录保持纯净（后台代码不进 `/var/www/fixboxs`）。
- 备用方案（更简单但边界更弱）：同域 `/admin/` 路径 + nginx `location ^~ /admin/` 反代。
- 服务器继续用 `106.55.2.197`，复用现有 Docker 与 nginx，不新增机器。
- 备案：`admin.` 子域与主站同主体，随现有 ICP 备案覆盖；需在后台登录页放隐私说明（账号信息用途）。

### 5.2 文章编辑器的字段映射

**左栏：结构字段（表单控件 + 强制枚举）**

| 字段 | 控件 | 约束 |
|---|---|---|
| `title` | 文本 | ≤ 30 汉字；提示「含用户会搜的词」 |
| `slug` | 文本（自动生成 + 可改） | `^[a-z0-9-]+$`；实时查重；发布时全局唯一 |
| `domain` | 下拉 | 取 taxonomy，12 领域 |
| `category` | 下拉（随 domain 联动） | 必须属于所选 domain |
| `os` | 多选 | 固定枚举（Windows 10/11、macOS 12+ 等） |
| `difficulty` | 下拉 | 入门 / 进阶（若扩展出「专家」需同步改校验） |
| `time` | 文本 | 与正文实际步骤量匹配 |
| `risk` | 三选一 | 安全 / 需谨慎 / 有数据风险；非「安全」时**强制生成正文风险提示块** |
| `symptoms` | 标签输入 | ≥3（规范建议 3–8），口语词优先 |
| `keywords` | 标签输入 | ≥5（规范建议 5–15） |
| `aliases` | 标签输入 | ≥2 |
| `prerequisites` | 列表输入 | 可为空 |
| `tools` | 列表输入 | 可为空 |
| `related` | slug 选择器（可搜索） | ≥2（规范建议 3–5）；实时校验存在性 |
| `sources` | 结构化行（title/url/type） | ≥1 条 `official`/`vendor`/`standard`；URL 必须 https |
| `reviewer` | 下拉（审核者）+ 可填团队名 | 发布时必填 |
| `reviewed_at` | 日期 | 发布时自动置当天 |
| `version` | 文本 | 必须存为字符串（YAML 里 `"1.0"` 要带引号，否则被解析成数字） |
| `updated` | 日期 | 仅实质修改时更新（后台提示规则，不自动刷） |

**建议新增（可为空，不阻塞）**：`seo_title`、`seo_description`、`published_at`、`needs_restart`、`modifies_data`。

**右栏：正文（Markdown 编辑器）**

编辑器打开即预置 10 段骨架，并使用**实际在用的小节标题**（已核对 30 篇现状，不要照抄内容体系 §5.2 的抽象名）：

```
一句话结论 / 30 秒快速排查 / 适用 / 不适用 / 开始前确认 /
分步骤 / 怎么确认修好了 / 还是不行？ / 预防 / 相关教程 / 更新日志
```

> 现状细节（实测）：`怎么确认修好了` 出现 29 篇、`怎么确认处理好了` 1 篇；`适用 / 不适用` 的斜杠两侧有空格。validator 应把这组同义标题纳入白名单，而不是强行改写存量文章。`相关教程` 段落由 `related` 字段渲染，正文里不必重复写。

### 5.3 状态机

```
        ┌──────────┐  提交审核   ┌───────────┐  通过并发布   ┌───────────┐
        │  draft   │ ─────────▶ │ in_review │ ───────────▶ │ published │
        └──────────┘            └───────────┘               └───────────┘
             ▲                        │                            │
             │      退回修改           │                            │ 归档
             └────────────────────────┘                            ▼
                     changes_requested                        ┌──────────┐
                                                              │ archived │
                                                              └──────────┘
```

- `scheduled`（定时发布）本期不做，见 §11。
- 状态与 `author` / `reviewer` / `review_notes` 一并写入草稿 md 的 front-matter。
- `archived` 文章 URL 必须保留（归档页或 301），严禁直接删除。

### 5.4 校验规则（后台与构建共用一套）

**这是整个方案的地基**：后台的「保存前校验」与构建的「发布前校验」必须是**同一个实现**（阶段 0 产出的 `content-lint.cjs`），否则必然出现「后台说没问题、构建失败」。

| # | 规则 | 级别 |
|---|---|---|
| V1 | front-matter 可解析（含 BOM 检测，报错文案要可读） | 失败 |
| V2 | 19 个字段齐全且类型正确（`os`/`symptoms`/`keywords`/`aliases`/`prerequisites`/`tools`/`related` 必须为数组，`sources` 为对象数组） | 失败 |
| V3 | `slug` 全局唯一且符合 `^[a-z0-9-]+$` | 失败 |
| V4 | `domain`/`category` 合法且从属关系正确 | 失败 |
| V5 | `risk` ∈ {安全, 需谨慎, 有数据风险}；`difficulty` ∈ {入门, 进阶} | 失败 |
| V6 | 正文 10 段齐全（同义标题白名单） | 失败 |
| V7 | `## 分步骤` 下至少一个 `### 步骤 N`，且每步含「目的 / 操作 / 预期结果 / 失败怎么办」四要素 | 失败（可先警告） |
| V8 | `related` 每个 slug 真实存在 | 失败 |
| V9 | `sources` 非空且 URL 为 https（联网 HEAD 校验默认关闭） | 警告 |
| V10 | 文内锚点 `#...` 有对应标题 | 警告 |
| V11 | `risk` 非「安全」时正文开头存在风险提示块 | 警告 |
| V12 | 代理/VPN 领域文章含合规提示块 | 警告（审核时强制确认） |
| V13 | `reviewed_at` 距今 >180 天 / >12 个月 | 提示（打 `stale`） |

> 来自工作流方案 §3.1 与架构评审 §4.4 的规则并在这里合并。V1–V8 为「保存即拦」，V9–V13 为「提示但可发布」。

## 7. 发布流水线（时序）

### 7.1 正常发布

| 步 | 动作 | 失败处理 |
|---|---|---|
| 1 | 编辑者在后台点「发布」 | 前置：V1–V8 校验必须已通过 |
| 2 | 服务端把 `_drafts/<slug>.md` 移到顶层，写 `status: published`、`updated`、`published_at`、`reviewer`、`reviewed_at` | 文件冲突（已被别人改）→ 409 让编辑重载 |
| 3 | `git add` + `git commit`（信息模板 `content(<domain>): <动作> <标题>（<作者>）`） | 提交失败 → 任务失败，文件保留在工作区，可重试 |
| 4 | `node build-fix.cjs`（未来还会产出 sitemap/robots/JSON-LD/索引） | 构建失败 → **不部署**，把错误回显到发布详情页 |
| 5 | `node deploy-fixboxs.cjs` 生成自包含产物 | 断链自检失败 → 不部署 |
| 6 | `bash deploy-fixboxs.sh`（打包 → 上传 → 原子切换 → 线上校验） | 任一步失败 → 线上目录已被 `.prev` 保护，任务标失败 |
| 7 | 线上全量校验：遍历 `dist/fixboxs/fix/*.html` 逐个探测 200（替代现在只查 6 个 URL） | 失败 → 提示可一键回滚 |
| 8 | `git push origin main`（备份，允许异步重试） | 失败**不阻塞**发布，只在后台标「待同步」 |
| 9 | 写审计日志 + 通知作者/审核者 | — |

### 7.2 预览

草稿保存后即可预览：服务端用同一渲染器生成临时 HTML，挂在 `/preview/<slug>`，登录可见、`noindex`。**不触碰**线上目录。预览里同时显示校验错误与警告。

### 7.3 紧急回滚

- 内容级：后台选一个历史提交 → `git revert` → 走 §7.1 的第 4–7 步重新发布。
- 产物级：把 `/var/www/fixboxs.prev` 切回 `/var/www/fixboxs`（一条 ssh 命令，后台按钮封装）。

### 7.4 与现有 `deploy-fixboxs.sh` 的衔接

现有脚本是「本机 scp 到远端 + 远端原子切换 + curl 校验」。在服务器上跑时，`scp` 到同一台机器是绕路。建议在阶段 1 给脚本增加一个 `--local` 分支（内容不变，只跳过上传、直接在同一台机器上完成原子切换），或者让 worker 直接执行 `deploy-fixboxs.sh` 的远端段。**两条路径必须共用同一段原子切换与校验代码**，避免出现「手工部署」和「后台部署」行为不一致。

## 8. 安全设计

| 面 | 要求 | 级别 |
|---|---|---|
| 传输 | 全站 HTTPS + HSTS；`admin.` 独立证书与 server 块 | 必须 |
| 认证 | argon2id（或 bcrypt cost≥12）哈希；密码长度下限 10 位；管理员强制 2FA | 必须 |
| 会话 | `HttpOnly` + `Secure` + `SameSite=Lax`；空闲 12h / 绝对 7d 过期；改密码即失效全部会话 | 必须 |
| CSRF | 所有写操作校验 token（含发布、回滚、上传） | 必须 |
| 限流 | 登录 5 次/15 分钟/IP + 锁定；发布接口按用户限流 | 必须 |
| 权限 | RBAC 在**服务端每个路由**强制，不在前端隐藏了事 | 必须 |
| 密钥 | 部署私钥仅发布 worker 可见（挂载只读、600、非 root 用户不可读之外的路径）；GitHub token 不进前端 | 必须 |
| 上传 | 类型白名单（拒 SVG/HTML）、大小上限、随机文件名、落盘路径规范化防穿越 | 必须 |
| 注入 | Markdown 渲染沿用构建器的转义；预览与正文都不执行用户 HTML | 必须 |
| 目录 | nginx 对 admin 域禁止访问 `.git`、`.md`、`node_modules`、`*.db` | 必须 |
| 暴露面 | 后台 `noindex`；如协作者 IP 稳定，可加 nginx `allow/deny` 白名单 | 建议 |
| 审计 | 登录、增删改、发布、回滚、改权限全部入库 | 必须 |
| 依赖 | 明确依赖白名单与升级节奏；不引入无人维护的包 | 建议 |
| 隐私/合规 | 后台登录页说明「账号信息仅用于内容协作」，与 ICP 备案主体一致 | 建议 |

> 一句话：后台是**唯一有写入能力**的组件，安全投入应集中在这里，而不是去改已经很好的静态站。

| **合计 v1.5（0+1+2）** | | **19–26.5 人日** | |

### 10.3 依赖关系

- ④ taxonomy 外置**是**⑧ 编辑器下拉与 ⑯ 分类管理的前置；

- ⑬ 媒体不阻塞 ⑫；⑮ 依赖 ⑦ 的哈希设计。

## 11. 不做什么（明确边界）

| # | 不做 | 理由 |
|---|---|---|
| N1 | 不把正文存进数据库当唯一副本 | 违反铁律 1；会让 Git、构建、部署全部失去意义 |
| N2 | 不替换 `build-fix.cjs` / `deploy-fixboxs.*` | 它们是经过验证的资产；后台只在**调用**它们 |
| N3 | 不让前台运行时依赖后台 | 保持纯静态与性能预算；后台故障不影响读者 |
| N4 | 不做读者账号 / 评论 / 工单 | 门户设计方案 §2.4 已排除；需要写入功能时才重新评估 |
| N5 | 不做实时多人协同编辑（OT/CRDT） | 本量级用「乐观锁 + 冲突提示」足够；实时协同是另一个数量级的复杂度 |
| N6 | 不做自动图片压缩/格式转换 | 架构评审 N12：唯一真破例点，暂缓 |
| N7 | 不引入 CDN / 对象存储 | 当前产物 1MB 级，整目录切换已足够 |
| N8 | 不重写现有 6 壳页与 30 篇的展示层 | 架构评审 N9：纯风险无收益 |
| N9 | 本期不做定时发布 | 需求未确认；先留 `publish_at` 字段位，阶段 3 再实现 |
| N10 | 不建微服务 / 消息队列 | 单容器 + 单队列表已足够，避免运维膨胀 |

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 后台写出的 Markdown 与手写格式不一致 | 构建失败或静默丢字段 | 序列化器与解析器**同源**；阶段 0 的 lint 做格式契约；后台保存即校验 |
| 非技术编辑者仍会写出低质内容 | 内容质量下降、合规风险 | 表单强约束 + 校验 + **审核流**（尤其代理/VPN 合规项）+ 内容体系 §7.3 审核清单做成后台勾选项 |
| 常驻服务的运维被低估 | 长期失修、证书过期、无人升级 | §9 明确为「新增责任」；最小化组件数；监控登录页与发布失败 |
| 密钥/账号泄露 | 可被写入恶意内容 | 2FA、限流、密钥隔离、审计、发布前校验（恶意内容无法绕过构建，但会被发布——因此还需要审核角色） |
| 后台故障导致无法发稿 | 内容停更 | 保留手工 Git 通道作为应急（两条路共用同一构建/部署） |
| 一段内容同时被两个人改 | 丢内容 | D5 乐观锁 + 冲突合并界面 |
| 发布把站点改坏 | 线上不可用 | `.prev` 原子回滚 + 全量 URL 校验 + 一键回滚 |
| 引入 npm 依赖带来供应链风险 | 安全与维护成本 | 依赖白名单、锁定版本、每月升级、优先 Node 内置能力 |
