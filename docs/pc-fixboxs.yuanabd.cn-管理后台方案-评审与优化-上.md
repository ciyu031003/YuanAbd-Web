### 1.3 【核心增量】方案未发现的两个致命缺陷

> 这两条是本评审相对被评审方案的最大增量。两条都不是「风险」，而是**今天已经成立的事实**，且都直接作废方案的两条铁律。

#### 缺陷 A（致命）：front-matter 解析器不支持嵌套对象 ⇒ 后台保存会**清空全部官方来源链接**

**判断**：`build-fix.cjs:78-97` 的 `parseFrontMatter` 只识别标量、扁平 `[a,b]` 数组和扁平 `- item` 列表；它对 30/30 篇的嵌套 `sources:` 结构**解析错误**——每条的 `title` 被当成字符串元素保留，**每条 `url` 被静默丢弃**。因此「后台写出同样格式的 Markdown」（铁律 2，L27）在当前实现下**不可能 round-trip**；一旦后台按自己解析出的模型序列化保存，30 篇的官方来源 URL 会**全部消失**。

**证据（可复现）**：

**① 原文结构**（`content/fixboxs/wifi-connected-but-no-internet.md:18-28`，其余 29 篇同构）：

```
18| sources:
19|   - title: Microsoft 支持 — 修复 Windows 中的 Wi-Fi 连接问题
20|     url: https://support.microsoft.com/zh-cn/windows/fix-wi-fi-connection-issues-in-windows-...
      ^^^^ 4 空格缩进
```

**② 解析器只认两种形状**：`build-fix.cjs:86` 处理 `/^\s*-\s+(.*)$/`（扁平列表项）；`build-fix.cjs:87` 处理 `/^([A-Za-z_][\w-]*):\s*(.*)$/`——该正则**要求行首无缩进**。第 20 行的 `    url: ...` 有 4 空格缩进，**两条正则都不匹配**，落到 `:88` 的 `if (!kv) return;` 被静默丢弃。

**③ 实测解析结果**（逐字复用 `build-fix.cjs:78-97` 对真实文件求值）：

```
sources 解析结果 = ["title: Microsoft 支持 — 修复 Windows 中的 Wi-Fi 连接问题",
                    "title: Microsoft Learn — netsh winsock 命令",
                    "title: Apple 支持 — 如果 Mac 无法通过 Wi-Fi 接入互联网",
                    "title: Apple 支持 — 在 Mac 上更改 DNS 设置",
                    "title: Apple 支持 — 在 Mac 上使用\"无线诊断\""]
sources[0] typeof = string
sources 首元素形如 'title: ...' 的篇数 = 30 / 30
sources 中存在裸 URL 元素的篇数 = 0 / 30
```

即 **30/30 篇**的 `sources` 都被降级成「`title: ` 开头的字符串数组」，**0 篇**保留任何 URL。

**④ 下游印证**：`demo/fixboxs/data/articles.js` 中 `"sources"` 出现 **0 次**（`build-fix.cjs:356-369` 未取该字段），所以这个错误解析目前**没有暴露到线上**——它是一颗**尚未引爆的雷**，而后台的保存动作就是引信。

**与方案的冲突点**：

| 方案条款 | 位置 | 要求 | 当前能否满足 |
|---|---|---|---|
| 铁律 2 | L27 | 后台只能写出**同样格式**的 Markdown，`build-fix.cjs` 输入契约一行不改 | ❌ 解析器读不出嵌套对象，写出必然丢 url |
| §5.4 V2 | L375 | `sources` **为对象数组** | ❌ 没有代码能把它解析成对象数组 |
| §5.2 | L331 | `sources` 是「结构化行（title/url/type）」控件 | ❌ 同上 |
| §10.1 阶段 0 四项 | L487-490 | ①lint ②失败策略 ③全量校验 ④taxonomy 外置 | ❌ **没有一项覆盖解析器升级** |

⇒ **阶段 0 必须新增「解析器/序列化器升级 + round-trip 回归测试」**，这是方案的净遗漏工作量（估 1–2 人日）。

> 顺带：这个缺陷同时**作废了方案 L560 的对策**。方案说「序列化器与解析器**同源**」——但当前解析器本身是错的，「同源」只会让错误在两端一致地传播。正确表述应是「**同源，且经过 round-trip 回归测试**（parse → serialize → parse 恒等；对存量 30 篇，serialize 结果须与原文逐字节等价）」。

### 3.1 【严重】铁律 2「输入契约一行不改」与 §10.1②「改造 build-fix.cjs 失败策略」自相矛盾

**判断**：不成立，是**同一条约束在执行层被自己推翻**。

- 铁律 2（L27）：「后台只能写出同样格式的 Markdown，`build-fix.cjs` 的**输入契约一行不改**」；
- §10.1 阶段 0 ②（L488）：「`build-fix.cjs` 由『静默跳过』改为『收集错误后统一失败』」——这是**改 `build-fix.cjs` 的行为契约**（`build-fix.cjs:345` 的 `console.warn` + `return` → `console.error` + 非 0 退出）；
- 同一条铁律还被另外两处推翻：§5.4（L370）要求「后台与构建**共用一套** lint」，即新增 `content-lint.cjs` 并接入构建；§10.1 ④（L490）要求 taxonomy 外置**替换** `build-fix.cjs:22-40` 里的常量；
- 更根本的是缺陷 A（§1.3）：`build-fix.cjs:78-97` 的 `parseFrontMatter` **必须改**。

**后果**：把一个「不改」和四个「必须改」放在同一份文档里，会让执行者按字面理解，误以为 `build-fix.cjs` 是只读资产（§3.2 组件清单 L145 也写着「基本不变」），从而**推迟阶段 0**——而阶段 0 恰恰是所有发布路径的共同保险（方案 L534 自述）。

**最小修复**：把铁律 2 改为「**`content/fixboxs/*.md` 的 YAML 契约对外保持稳定；`build-fix.cjs` 的解析、校验、序列化实现允许升级，但必须有 round-trip 回归测试锁死兼容性**」。**把「不改什么」的宾语从「脚本」改为「文件格式」。**

### 3.2 【中】§5.2 声明「10 段」却列出 11 个标题；按字面实现 validator 会使 30/30 篇失败

**判断（a）数量错误**：

- L341：「编辑器打开即预置 **10 段**骨架，并使用实际在用的小节标题」；
- L344-346 的代码块实际列了 **11 项**：

```
一句话结论 / 30 秒快速排查 / 适用 / 不适用 / 开始前确认 /
分步骤 / 怎么确认修好了 / 还是不行？ / 预防 / 相关教程 / 更新日志
```

逐项数：①一句话结论 ②30 秒快速排查 ③适用 ④不适用 ⑤开始前确认 ⑥分步骤 ⑦怎么确认修好了 ⑧还是不行？ ⑨预防 ⑩相关教程 ⑪更新日志 = **11 项**。

**证据（错误根源）**：真实文章的 H2 是 **`适用 / 不适用`（一个标题，含斜杠）**，30/30；方案 L348 自己也写「`适用 / 不适用` 的斜杠两侧有空格」——**它知道这是一个标题，但清单里用 ` /` 当分隔符，把它断成了两项**。

**判断（b）后果严重**：§5.4 V6（L379）写「正文 **10 段**齐全（同义标题白名单）」。若按 L344-346 的字面清单（11 项）实现 validator，**30/30 篇都会失败**——因为没有任何一篇文章有独立的 `## 适用` 或 `## 不适用` 段（探针：全库 H2 分布中不存在这两个标题）。这不是笔误级别的问题，它会**直接卡死发布**。

**判断（c）还有连带影响**：`build-fix.cjs` 用 `##` 前缀分割正文（`:231` `body.split(/^##\s+/m)`），并以名称作字典键（`:240` `blocks["一句话结论"]`）与顺序数组（`:244-246` `rest`）。段落数量或名称一旦改变，会连带改变页面结构与 TOC 输出（`:300`、`:307-312`）。

**最小修复**：§5.2 的骨架改为**逐行带段落序号的表格**（与内容体系 §5.2 的 10 行表对齐），并显式写明「`适用 / 不适用` 是**一个** H2」。

### 3.3 【中】§5.4 V6「10 段齐全」对 `remote-control-scam.md` 的表述有误 —— 它不是 11 个 H2

**判断：需纠正一个流传的说法**——`remote-control-scam.md` **不是 11 个 H2，而是 10 个**。方案 L348 说它「同时含『怎么确认修好了』和『怎么确认处理好了』」，**只说对了一半**：它**没有**『怎么确认修好了』，只有『怎么确认处理好了』。

**证据（实测）**：

```
remote-control-scam.md H2 数 = 10
["一句话结论","30 秒快速排查","适用 / 不适用","开始前确认","分步骤",
 "怎么确认处理好了","还是不行？","预防","相关教程","更新日志"]

全库 H2 计数：怎么确认修好了=29，怎么确认处理好了=1（合计 30）
每篇 H2 数恰好 = 10（探针：H2 数量 != 10 的篇目 = []，30/30 通过）
```

**后果**：只要 V6 实现了「同义标题白名单」（L348 已提出），该篇**能通过**校验；但方案 L348 的表述会让读者以为它是个特例风险点，从而**对一个不存在的问题做加固**。真正值得处理的是另外三件事：

1. 该篇第 6 段的**异名应被统一**（`怎么确认处理好了` → `怎么确认修好了`），否则搜索锚点、TOC、面包屑会出现两套标题；
2. 内容体系 §5.2 规定的第 6 段叫「验证是否解决」（`内容体系:498`），与仓库实际的两个名字**都不一致**——这才是跨文档的真缺陷（见 §2.3）；
3. V6 的白名单应同时包含两个同义标题（方案已提出，采纳）。

**最小修复**：① 更正 L348 的表述；② V6 白名单包含两个同义标题；③ 单列一项内容改动「统一 `remote-control-scam.md` 第 6 段标题」，由内容负责人确认，**不计入后台工期**。

### 3.4 【中】D2 的「目录隔离」依赖一处**偶然正确**，方案称之为「利用这一点」，但没有加锁

**判断**：方案 L171 的推理方向正确，但**把「实现细节的副作用」当成了「契约」**。

- 生效机制：`build-fix.cjs:331` 使用**非递归**的 `fs.readdirSync(SRC)`；
- 方案 L171 的措辞：「**利用这一点**：子目录天然不进构建」；
- D2 表格（L184-188）的整套草稿/归档设计**完全建立在该副作用之上**；`_archive/` 还额外承担「URL 必须保留（归档页或 301）」的**产品承诺**（L366：`archived` 文章 URL 必须保留，严禁直接删除）。

**后果**：把 `readdirSync` 改成递归（或加 `{ recursive: true }`）**是任何一次重构都可能顺手做出的改动**。一旦发生，`_drafts/` 里的**所有草稿会被直接构建并发布到线上**——这是后台方案里**最严重的一次性事故场景**，后果远大于「单篇丢字段」。

**证据链补充**：架构评审 §3.4（`:373`）把「分片倒排索引构建脚本」列为**零破例**；该脚本要遍历 `content/` 生成产物，一旦它按递归方式实现，同样会踩中。⇒ 隔离机制**不能只靠 `_` 前缀的约定**。

**最小修复**：阶段 0 的 lint 加**两条显式断言**并做成回归测试：① 源枚举必须是非递归的（或显式断言 `_` 前缀目录被跳过）；② **构建产物中不得存在来自 `_drafts/` 的 slug**。第二条是真正的安全网——它不关心实现怎么改，只关心结果。

### 3.5 【中】§7.4「两条路径共用同一段原子切换代码」在当前脚本结构下无法实现

**判断**：目标正确，**但方案给出的实现路径不成立**。

- 方案 L439：「**两条路径必须共用同一段原子切换与校验代码**，避免出现『手工部署』和『后台部署』行为不一致」；
- 现实：`deploy-fixboxs.sh:40-51` 的远端段是 **`ssh … 'bash -s' <<REMOTE … REMOTE` 的 heredoc 内联**；`:54-58` 的校验是 **`for p in …; do` 位置硬编码**；`:36-37` 的 `tar`+`scp` 是顶层语句。**全脚本没有任何函数封装，也没有可 `source` 的库文件。**

**附带发现**：方案 L439 提的 `--local` 分支**没有现成开关可挂**——`deploy-fixboxs.sh:29-32` 的 `--check` 分支**位于 `:27` 的 `node deploy-fixboxs.cjs` 之后**，也就是说 `--check` **仍会完整执行产物化**（与 `demo/fixboxs/README.md:158` 的说明「只构建并自检」相符，但**不满足后台 worker「只想校验、不产物化」的诉求**）。

**后果**：若照方案实现，worker 会**复制一份**远端段逻辑到 Node 侧（或反之），两份代码立刻开始漂移——而方案 L566 把「发布把站点改坏」的对策写成「`.prev` 原子回滚 + 全量 URL 校验 + 一键回滚」，三者**都依赖这段代码的唯一性**。

**最小修复**：阶段 0 就把它**抽成独立脚本**（如 `deploy-remote.sh`：只做「解包 → 原子切换 → 全量校验」），由 `deploy-fixboxs.sh` 与后台 worker **共同调用同一个文件**；同时把 `--local` 的语义限定为「跳过上传，直接在本机执行同一段远端逻辑」。这是**阶段 0 的隐藏工作量**（方案 2–3.5 人日中未含）。

### 3.6 【中】§1.2 把「Git 做不到」当成能力问题——实际是便利性问题，且论证反而削弱了自己

**判断**：表格中的 ❌ 标记**与同一行的括注自相矛盾**。

后台方案 §1.2（L47-57）以「内容规范本身就要后台」为最强论据，其中 L49：

> 「代理/VPN 类内容须由第二人复核合规项后才能发布 | 内容体系 §8.2 规则 7 | ❌ 只能靠自觉（**PR review 要对方会 Git**）| ✅ 角色 + 状态机强制」

**矛盾点**：括注写的是「**要对方会 Git**」——这是**门槛/便利性**问题，不是「做不到」。Git 的 PR + Review + required approvals **恰恰就是第二人复核的强制机制**，而且比自建状态机更成熟：

- 架构评审 §3.1 理由 3（`架构评审:305`）明确列出「草稿=branch，审核=PR review，发布=merge，权限=仓库协作者，版本历史=`git log -p`，回滚=`git revert`，审计=commit 签名」；
- 工作流方案 §5.1（`工作流方案:240`）给出可操作配置：「开启 GitHub 分支保护：`main` 需 PR + 1 approval」；
- 工作流方案 §2（`:83`）也把「审核 | Pull Request + Review | ✅ 够，且**留痕更强**」列为 Git 的等价能力。

**后果**：用「做不到」的措辞论证「必须自建后台」，会**误导决策者**——真正需要回答的是「协作者愿不愿意用 Git 网页」。工作流方案 §7 触发条件 #1 的后半句（「**明确拒绝使用 GitHub 网页**」，`工作流方案:280`）正是这个问题的准确表述，**而方案没有引用它**（见 §2.2）。

**同一表格还有第二条被夸大的 ❌**：L53「90 天/季度复核排期 | ❌ 无」。但架构评审 §5.2 P1-⑦（`架构评审:634`）已给出**纯构建期**的实现路径（按 `reviewed_at` 打 `stale` 徽章 + 产出 `stats.json`），成本 0.5–1 人日、**零破例、不需要后台**。方案把一个已被论证为构建期可解的功能，算作了后台的正当性论据。

**最小修复**：把 §1.2 表格的 ❌ 改为「⚠️ 需要协作者会用 Git 网页 / PR（**便利性成本，非能力缺失**）」，并在行内注明「复核排期：架构评审 P1-⑦ 已有构建期替代方案（0.5–1 人日）」。**后台的正当性应重建在「协作者明确拒绝 Git 界面」这一单一前提上**，而不是靠堆砌 ❌。

### 3.7 【中】§5.4 V2「19 个字段」是快照而非约束——新增 `status`/`author` 后立刻自相矛盾

**判断**：不成立，是**同一条规则被同一份文档的两处要求同时违反**。

- V2（L375）：「**19 个字段齐全且类型正确**」；
- §5.3（L365）：「状态与 `author` / `reviewer` / `review_notes` **一并写入草稿 md 的 front-matter**」；
- 实测（§1.2 S-02）：当前恰好 19 个字段，**`status` / `author` / `review_notes` 都不在其中**；
- 内容体系另有要求：§7.5（`:1030`）归档文章须带 `status: archived`；§7.4（`:1018`）过时文章须记 `stale_since`。

⇒ 一旦按 §5.3 落地，front-matter 会变成 **22+ 字段**，V2 的「19 个字段齐全」这条规则**从第一天起就是错的**。

**更深的措辞矛盾**：L152 §3.3 边界写着「**内容格式与字段：不动（阶段 0 只补校验，不新增必填字段）**」，而 §5.3 要加字段、§5.1 要管 19 个字段。（严格说「不新增**必填**字段」与「状态写入 front-matter」不冲突——状态可自动写入、非人工必填——但方案的措辞会让执行者以为字段集是冻结的。）

**最小修复**：把 V2 拆成两条——**V2a「19 个存量字段必须齐全且类型正确」**（硬约束，保护存量）、**V2b「新增的 `status`/`author`/`review_notes`/`stale_since` 必须符合枚举与类型」**（增量约束）。**字段总数不应成为断言**；断言对象应是「**必填字段集合**」，且该集合应定义为数据文件（如 `content/schema.json`）而非硬编码在 validator 里——否则每加一个字段都要改代码，而这正是后台要避免的模式（与 L370「后台的『保存前校验』与构建的『发布前校验』必须是同一个实现」相呼应）。

### 3.9 §3.3 反向纠正：方案在**引用某条缺口时反而比原文保守**（罕见但重要）

后台方案 §2.3（L97）写：「复用成熟 CMS 前端 …… **10 段正文骨架的强制力较弱**，需用『服务端校验 + 预览』兜底」。

这是方案里**少数比前置文档更保守**的判断，也**恰好指向本方案的最优路径**：工作流方案 §3.4（`工作流方案:204`）已断言 Git 后端 CMS 的**关键收益**是「表单里 `domain` / `risk` 是下拉框，`sources` 是结构化列表——**从源头消灭 §1.2 的字段类故障**」；而缺陷 A（§1.3）恰恰说明：**结构化列表这一项在当前解析器下会被写坏**。

⇒ 结论：**「复用 CMS 前端」的真正前置条件不是「是否需要后端」，而是「解析器能否 round-trip」**。方案没有意识到这一点，但它的方向是对的（详见下册 §4）。
