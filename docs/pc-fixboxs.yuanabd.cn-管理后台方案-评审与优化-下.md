## 4. 选型重新决策

> **本节是整个优化方案的核心增量。** 原方案 §2 把选择做成「A（GitHub 账号）vs B（自建 10–14 人日）」二选一，并默认推荐 B。本节先**重建「为什么需要后台」的正当性论证**（§4.0），再证明存在**第三条路线 A′**（§4.1 起），最后给出四路线完整对比与分阶段推荐排序。

### 4.0 先重建正当性：后台的理由不该靠堆砌 ❌

原方案 §1.2 用一张「纯 Git 能做到吗 / 后台能做到吗」的表来论证「必须自建后台」，其中有两处**把便利性问题当成了能力问题**：

| 原方案的说法 | 问题 | 事实 |
|---|---|---|
| 「代理/VPN 类须第二人复核 → 纯 Git ❌，因为 **PR review 要对方会 Git**」 | ❌ 标错性质。**Git 的 PR + required approvals 恰恰就是第二人强制复核的机制**，而且比自建状态机更成熟（它是服务端强制的，改不了、绕不过）。真正的差异只是「要不要学 Git」——这是**便利性**，不是**能力** | 分支保护 + 至少 1 个 approval，就能做到「不经过第二人点头，内容进不了 main」 |
| 「90 天/季度复核排期 → 纯 Git ❌ **无**」 | ❌ 被夸大。架构评审 P1-⑦ 已有**纯构建期**方案：按 `reviewed_at` 距今 >180 天自动打 `stale` 徽章 + `stats.json` 统计（**0.5–1 人日，零破例**）。它不是「无」，只是「尚未做」 | 构建期产出一个「待复核」静态页即可，不需要后台 |
| 「每篇 19 个字段 + 固定 10 段结构 → 纯 Git ⚠️ 靠肉眼」 | ⚠️ 部分成立：Git 确实没有表单约束 | 但这条的替代方案是**可配置的现成 CMS 表单**，而不是「自己写后台」 |
| 「超过 12 个月未更新要显示过期提示 → 纯 Git ⚠️ 需人工统计」 | ⚠️ 措辞偏弱：它**同样已经规划**为纯构建期工作（架构评审 P1-⑦），**与是否上后台无关** | 后台只是让它可视化的一个额外入口，不是它的前置条件 |

**修正后的正当性论证（单一前提，更硬）**：

> **后台的正当性应当且只应当建立在「协作者明确拒绝使用 Git 网页界面」这一条前提上**——即工作流方案 §7 触发条件 #1 的后半句。**不是**「Git 做不到审核 / 复核 / 字段校验」，而是「有人不愿意用 Git 的界面去做这些事」。

**为什么这个重建很重要（它正是推荐 A′ 的关键论据）**：

| 若正当性建立在… | 会推出什么结论 | 后果 |
|---|---|---|
| 「Git **做不到** 审核 / 复核 / 字段约束」（原方案的论证方式） | 必须自建一套状态机 + 表单 + RBAC——因为只有自己写的才能做 | 直接跳到 B（10–14 人日），**并且把「换一个能在 Git 上做这些事的界面」这条路给漏掉了** |
| 「**有人不愿意用 Git 的界面**」（修正后的论证） | 只需要换一个**界面**，底下的审核/复核/权限仍由 Git 与成熟组件承担 | **自然推出 A / A′**：换界面而不换底座 |

> **一句话**：把理由从「Git 不行」改成「人不愿意用 Git」，结论就从「必须自研后台」变成「**必须换界面，不必换底座**」。这正是 A′ 成立的位置——**它换的只是界面**。

### 4.1 原方案的选型错在哪：把「后端选谁」当成了「要不要 CMS」

原方案 §2 的路线表只用两个维度做区分：**协作者要不要 GitHub 账号**、**要不要自建服务端**。这两个维度看起来是二选一，实际上它们**正交**：

| 维度 | 取值 X | 取值 Y |
|---|---|---|
| 编辑器界面从哪来 | **不自建**（用现成 Git 后端 CMS 前端） | **自建**（自己写表单 + Markdown 编辑器） |
| Git 后端在哪 | GitHub / GitLab（第三方托管） | **Gitea / Forgejo（自己托管）** |

原方案只探查了 `(不自建, GitHub)` 与 `(自建, 自己托管)` 两个格子，**漏掉了 `(不自建, 自己托管)`**——而这一格恰好同时满足「协作者不需要 GitHub 账号」和「不需要新写服务端代码」两个诉求。它不是一个新发明的组合，是 Sveltia CMS **官方支持**的配置。

**依据**（Sveltia CMS 官方文档，2026-10-12 抓取）：

| 事实 | 出处 |
|---|---|
| Sveltia 支持的 Git 后端只有三种：GitHub、GitLab、**Gitea/Forgejo** | [Backends](https://sveltiacms.app/en/docs/backends.md)「Supported Backends」 |
| Gitea/Forgejo 后端要求：**一个 Gitea/Forgejo 账号** + 内容仓库 + 仓库写权限（只读用户不能登录）；且需 **Gitea 1.24 / Forgejo 12.0 或更高** | [Gitea/Forgejo Backend](https://sveltiacms.app/en/docs/backends/gitea-forgejo.md)「Requirements」 |
| 自建实例通过 `base_url` + `api_root` 指向自己的服务器（`api_root` 需含 `/api/v1`） | 同上「Instance URL」 |
| 整个 CMS 是浏览器端 SPA，**< 550 KB（minified + brotli）**，可自托管 npm 包，**无服务端进程、无数据库、无需构建工具** | [What is Sveltia CMS?](https://sveltiacms.app/en/docs/intro.md)「Lightweight / Maintenance-Free / Not SaaS」 |
| GitHub 后端的真实门槛：**Write / Maintain / Admin 角色**；只读用户无法登录（除非开 Open Authoring 走 fork） | [GitHub Backend](https://sveltiacms.app/en/docs/backends/github.md)「Requirements」 |

> **一句话纠错**：原方案 §2.2 写的「A 的真实代价：GitHub 的 OAuth 不能纯前端完成，必须有一个 OAuth 中转」——**这句话只在「后端选 GitHub」时成立**。选 Gitea 后端时，官方推荐的方式是 **PKCE authorization code flow**（`app_id` 配一个自建实例上的 OAuth 应用，**脱敏（非机密）客户端，不需要 client secret、不需要任何中转服务**），团队内部还可以直接用 **access token**。见 [Gitea/Forgejo Backend](https://sveltiacms.app/en/docs/backends/gitea-forgejo.md)「Authentication」。所以「OAuth 中转」这笔成本在 A′ 里**不存在**。

### 4.2 路线 A′ 定义（新增路线）

> **A′ = Sveltia CMS（静态 SPA，托管在自己的域名下）+ 自建 Gitea/Forgejo 作为 Git 远端后端。**

它满足的三个「同时」：

1. **协作者只需要一个你自己管理的账号**——在 `106.55.2.197` 的 Gitea 上开号，不需要 GitHub 账号、不需要注册任何第三方服务；
2. **不需要新写一行服务端业务代码**——CMS 是静态资源，Git 服务是成熟开源组件，二者靠 Git 协议对接；
3. **审核流（PR/MR + label）与富文本编辑界面全部白拿**——见 §4.4。

**组成与部署形态**（三块，全部落在现有服务器上）：

| 组成 | 位置 | 新增属性 |
|---|---|---|
| Sveltia CMS 静态资源（`admin/index.html` + `admin/config.yml` + 打包好的 CMS bundle） | 现成 nginx 上新增一个 server 块（建议 `admin.pc-fixboxs.yuanabd.cn`） | 新增静态目录，**无进程** |
| Gitea 容器（Git 服务 + Web UI + PR + 账号 + 2FA + 审计） | `106.55.2.197`，与现有 Docker / nginx 共存，反代一个子域（如 `git.pc-fixboxs.yuanabd.cn`） | **新增一个常驻容器 + 一个库 + 备份** |
| 发布出口（Gitea 合并 → 触发构建 → 部署） | 复用现有 `build-fix.cjs` + `deploy-fixboxs*.sh` | 新增一个触发脚本（阶段 0 已把原子切换抽成可复用函数，见 §6.4） |

**内容真源不变**：仍然是 `content/fixboxs/*.md`，只是这次的「仓库」落在自建 Gitea 上，并由它同步/镜像到 GitHub 作为异地副本。

### 4.3 四路线全维度对比表

| 维度 | **A** Sveltia / GitHub 后端 | **A′** Sveltia / 自建 Gitea（**新增，推荐**） | **B** 原方案自建 Git 写入型后台 | **C** DB-first（Payload/Strapi/Directus） |
|---|---|---|---|---|
| 协作者需要什么账号 | **GitHub 账号** + 被授予仓库 Write/Maintain/Admin 权限 | **你自己在 Gitea 上开的账号**（账号生命周期完全自控） | 你自建后台开的账号 | 你自建 CMS 开的账号 |
| 新增**常驻服务** | 仅 OAuth 中转（Cloudflare Worker 之类）；或改用 access token 则**为零** | **Gitea 一个容器**（成熟开源组件） | 自建 Web 进程 + 发布 worker + SQLite 三件套 | CMS 服务 + 数据库两套常驻 |
| 新增**自研代码量** | 0（只有配置文件 + 一份静态 bundle） | **0**（同上，只多一份 Gitea 部署脚本） | **整个后台**：认证 / RBAC / 编辑器 / 预览 / 队列 / 审计 / 回滚 UI | 少量配置 + 大量数据迁移与管线重写 |
| **审核流是否白拿** | ✅ 白拿（Editorial Workflow） | ✅ **白拿**（同上，Gitea 侧 PR + label） | ❌ 要自写状态机、驳回理由、待办列表 | ⚠️ 有角色但审核流仍需自配 |
| **富文本/表单/媒体界面** | ✅ 白拿 | ✅ **白拿**（含资产库，可上传图片） | ❌ 要自写（或用现成编辑器组件拼） | ✅ 白拿 |
| **中文 19 字段 + 10 段骨架贴合度** | ⚠️ 需自查：字段类型齐全（string/select/list/object/relation/datetime/richtext 均在），但**骨架强制力弱**；`sources` 的嵌套对象要用 `object` + 子字段表达 | ⚠️ **同 A**（同一份 config，与后端无关） | ✅ 可做强约束（保存前必过 `content-lint.cjs`） | ⚠️ 同 A |
| **冲突处理** | simple 模式**官方明确不支持合并冲突处理与同时编辑**；editorial 模式有「保存前比对分支 + 拒绝过期写入」的机制 | ⚠️ **同 A**。且 Gitea/Forgejo **无法告知「基于哪个 commit 构建」**，官方说明其只能在保存前后检查分支是否仍指向该 commit（**比 GitHub 弱一档**） | ✅ 由我们自定义（D5 乐观锁 + 差异视图，按需） | ⚠️ 需自行处理 |
| **工作量（MVP 打通）** | 2–4 人日 | **3–5 人日**（多 1 人日用于 Gitea 部署/证书/备份） | **10–14 人日**（原方案自估） | 25–40 人日 |
| **可逆性** | ✅ 极高：删掉 admin 静态目录即可，内容与流水线不动 | ✅ **极高**：同上；Gitea 停掉也不影响前台，只是暂停发稿 | ⚠️ 中：删掉后台容器，但连带丢掉审计库与角色配置 | ❌ 低：内容进了库，回退要导出 |
| **前台影响** | 无（构建期读文件） | 无（同左） | 无 | 无（但管线要重写） |
| **对本项目的主要代价** | 协作者必须有 GitHub 账号 | **多运维一个 Gitea 容器**；发稿依赖远端 Git 可用 | 10–14 人日自研 + 同样要运维 | 违反铁律 1 |

### 4.4 A′ 的「白拿」到底是什么：逐条对照原方案的采购清单

原方案 §5.1 列了 13 个页面、§5.3 一个状态机、§6 九张表、§8 十四项安全。走 A′ 后，这些需求的归属发生整体迁移：

```yaml
collections:
  - name: tutorials
    folder: content/fixboxs
    publish_mode: editorial_workflow    # 教程：强制走 PR
  - name: settings
    publish_mode: simple                # 站点设置：直接提交
```

> 原方案 §5.1 的页面 8/10/13（版本历史、分类词典、站点设置）在 A′ 里的归属见 §4.7；A′ **不覆盖**的部分必须诚实列出，不能拿「白拿」掩盖。

### 4.5 明确回答原方案 Q1

> **原方案 Q1**：「走路线 B（自建，10–14 人日）还是先用路线 A（2–4 人日，需要协作者有 GitHub 账号）？」

**这个问题的前提是错的，应当这样改写并回答：**

| 修订 | 内容 |
|---|---|
| 原问法 | 「协作者能否持有 GitHub 账号」→ 不能则走 B |
| **改为** | 「协作者能否持有 GitHub 账号？**若不能，你是否接受在 `106.55.2.197` 上多跑一个 Gitea 容器？**」 |
| **答案** | 能接受 GitHub 账号 → 走 **A**（2–4 人日，最快）；不能接受 GitHub、但接受多一个容器 → 走 **A′**（3–5 人日，**推荐**）；两者都不能接受 → 才考虑 **B**，且必须承认 B 同样要运维（还得额外自研）。 |

**为什么「不能接受 GitHub 账号」不应该直接跳到 B**：跳跃的理由隐含假设是「不建自研后台就没有审核流」。这个假设被 Editorial Workflow 证伪——审核流是 CMS 前端 + Git 服务的能力，与「谁托管 Git」无关。B 的 10–14 人日里，**至少 6–8 人日花在重建 Gitea 已经有的东西上**（登录、会话、角色、审核状态机、审计）。

### 4.6 分阶段推荐排序（本次选型的最终结论）

> **A′ 先打通 MVP，B 降级为「当 Sveltia 无法满足时的按需增量」。** 这不是「A′ 更好」，而是「A′ 的投入产出比在阶段 1 显著更优，且完全不阻断 B」。

| 阶段 | 做什么 | 为什么这个顺序 | 人日 |
|---|---|---|---|
| 阶段 -1 | 修解析器/序列化器 + 补 Git 基线 | **与选型无关，无论走哪条路都必须先做**（详见 §8.1） | 0.5 |
| 阶段 0 | 补闸门（lint + 构建失败策略 + 全量 URL 校验 + taxonomy 外置） | **与选型无关**，是所有发布路径的共同保险 | 2–3.5 |
| **阶段 1′** | **A′ 打通**：部署 Gitea → 配 Sveltia → 开 Editorial Workflow → 打通发布出口 | 用最小自研量换来完整编辑/审核能力；**先验证「非技术编辑者真的能用」这个核心假设** | 3–5 |

### 4.7 A′ 的诚实代价与不适用场景（必读）

> **这一节的目的是防止把「避免低估自研」换成「低估运维」。** 下列每一条都是真实的、必须被接受的代价。

| # | 代价 / 不适用场景 | 具体含义 | 是否可缓解 |
|---|---|---|---|
| **C1** | **Gitea 本身就是一个常驻服务** | 要占内存与磁盘、要备份（仓库 + 数据库 + 配置）、要升级（安全补丁）、要证书、要监控。原方案 §9「新增的运维责任，必须写进预算」这句警告**在 A′ 里依然完全适用**，只是对象从「自研后台」换成「成熟开源组件」 | 缓解程度有限但成本低得多：Gitea 有官方备份方式，升级是换镜像；**风险等级从「自己写的代码有洞」降到「跟随上游打补丁」** |
| **C2** | **simple workflow 无冲突处理、无同时编辑** | 官方明文承认。两人同时改同一篇会互相覆盖，**CMS 不会拦** | 阶段 1′ 用「编辑前认领」的流程纪律 + 阶段 2 按需补冲突检测；**注意：选 A′ 并不等于问题消失**，只是默认人数少时概率低 |
| **C3** | **Editorial Workflow 的冲突保护比 GitHub 弱一档** | GitHub 可以让 CMS 指定「基于哪个 commit」，最后一次写入会被服务端拒绝；**Gitea/Forgejo 做不到**，官方只能「保存前检查分支是否仍指向该 commit」——存在极小的竞态窗口 | 接受；或对高频并发集合改用「一人一分支」的纪律 |
| **C4** | **Editorial Workflow 依赖远端可用** | 条目状态（`In Review` / `Ready`）**是 PR label**，PR 在 Gitea 上。**Gitea 不可达时，连看板都打不开，更无法推进审核** | 见 §6.5 的可用性差异分析。缓解手段是「Gitea 高可用/快速恢复」，不是「换路线」 |
| **C5** | **发布出口仍要自己做（且比 B 多一跳）** | Sveltia 只负责把内容提交到 Gitea；**「合并之后怎么上线」不归它管**。官方 Deployment 文档只说「Gitea 支持 CI/CD 可用于自动部署」（[Gitea/Forgejo Backend](https://sveltiacms.app/en/docs/backends/gitea-forgejo.md)「Deployment」） | 这是阶段 1′ 的 ⑯ 项，工作量已计入 3–5 人日 |

| **C8** | **阶段 1′ 交付不了「站点级治理强制」** | 「12 个月未更新自动打过期标记」「90 天复核排期」是**站点行为**，Sveltia 不提供。这两条仍需在构建期（`fx-stats.cjs`，架构评审 P1-⑦）与流程纪律里实现 | 已在阶段 -1/0 与架构评审 P1 的范围内，不额外增加 A′ 的负担 |
| **C9** | **不适用场景（什么时候 A′ 是错的）** | ① 明确拒绝在服务器上多跑任何常驻服务；② 协作者全都在墙内且服务器出口不稳定，但需要频繁发稿；③ 需要「保存即上线」的极低延迟发布；④ 需要 CMS 内部做站点专属硬约束（如「正文必须含 10 段骨架否则不给保存」）而不接受构建期才拦 | ①②③ → 退路线 A 或 B；④ → 阶段 2 的 B 增量，或接受「构建期拦 + 保存时给提示」的折中 |

### 4.8 Schema 表达能力核查（A′ 的硬约束边界）

> **这一节回答「Sveltia 的配置语言能不能表达本站的 19 字段」。** 原文核查结论：**字段类型全部覆盖，但骨架强制力弱于自建后端**——这是 A′ 最实质的一处功能让步。

| 本站字段 | 需要的能力 | Sveltia 字段类型 | 结论 |
|---|---|---|---|
| `title` / `slug` / `time` / `version` / `reviewer` | 单行文本 | `string` | ✅ |
| `domain` / `category` / `difficulty` / `risk` | 枚举下拉（category 随 domain 联动） | `select`（含 options） | ✅（**联动**需用其条件/计算能力或拆集合，属配置工作量） |
| `os` / `symptoms` / `keywords` / `aliases` / `prerequisites` / `tools` / `related` | 字符串数组 | `list`（`related` 还可用 `relation` 做 slug 关联） | ✅（`relation` 还能天然保证 `related` 指向真实条目——**这正是原方案 V8 规则的免费实现**） |
| `sources` | **对象数组** `{title, url, type}` | `list` + `object` 子字段（或 `list` 内嵌 fields） | ✅ 可表达，**但要求解析/序列化侧同源支持嵌套**（见 §8.1） |
| `updated` / `reviewed_at` | 日期 | `datetime`（**注意：`Date` 类型已废弃**） | ✅ |
| 正文（10 段骨架） | 富文本 / Markdown | `richtext`（`markdown` 为其别名） | ⚠️ **能编辑，不能强制骨架**——Sveltia 不提供「预置模板且校验 10 段齐全」的机制 |
| 图片 / alt / 脱敏 | 媒体上传 | 资产库 + `image`/`file` 字段 | ✅（alt 可作为字段定义，脱敏要求只能靠提示与审核） |
| 新增字段 `status` / `author` | 只读或隐藏 | `hidden` / `compute`（只读计算字段） | ✅ **这说明「固定 19 字段」是快照不是约束**（上篇已论证） |

**三条由此推出的硬结论**：

1. **`relation` 字段让原方案 V8（`related` 存在性）几乎免费** —— 但**不要指望它替代构建期校验**（见下条）。
2. **「10 段骨架齐全」这类结构约束，Sveltia 拦不住**。因此原方案 §5.4 的 V6 必须实现在 `content-lint.cjs` 里，并且**必须实现为「带同义标题白名单」的校验**：全库 30 篇每篇恰好 10 个 H2，但其中 **29 篇的第 7 段写作「怎么确认修好了」、1 篇（`remote-control-scam.md`）写作「怎么确认处理好了」**。校验器必须把两种写法都列为合法（并把「适用 / 不适用」的斜杠两侧带空格作为唯一合法形态），否则**一开启强校验就会把现存文章判死**。这是「校验器必须容忍存量内容」的论据，不是「存量内容有缺陷」的论据。
3. **`sources` 是可表达的，但前提是解析器支持嵌套对象** —— 而今天不支持（阶段 -1 的 ①）。**这条把「选型」和「阶段 -1」直接绑在一起：不修解析器，A′ 一保存就毁数据。**

## 5. 架构修正

> 原方案 §3 的目标架构方向正确（编辑器 + 流水线控制器、内容真源不动、前台不依赖后台），本节只做**必要修正**：增加一个可选后端的位置、把审核流从「自建状态机」改为「复用 PR/MR label」、把两处「偶然正确」改成显式契约，并把铁律 2 的宾语从「脚本」改为「文件格式」。

### 5.0 先修正一条铁律：铁律 2 的宾语错了

原方案的三条铁律里，第 2 条写的是：

> 「后台只能『写出同样格式的 Markdown』，`build-fix.cjs` 的输入契约**一行不改**。」

**这条与原方案 §10.1②「改造 `build-fix.cjs` 失败策略」自相矛盾**——② 明确要改 `build-fix.cjs`（把静默跳过改成统一失败），① 又说不改一行。而阶段 0 的实际工作需要**大量**修改构建脚本（失败策略、嵌套解析、目录断言、taxonomy 外置），这条铁律会让执行者无所适从。

**评审给出的正解是：把「不改什么」的宾语从 `build-fix.cjs` 这个*文件/实现*，改为 `content/fixboxs/*.md` 的 `YAML 契约`这个*格式*。**

| 项 | 原铁律 2（错） | 修正后的铁律 2（对） |
|---|---|---|
| 保护对象 | `build-fix.cjs` 的源码（一行不改） | **`content/fixboxs/*.md` 的 YAML 契约对外稳定** |
| 允许什么 | 几乎什么都不许 | **解析、校验、序列化实现允许升级**（这正是阶段 -1/0 要做的） |
| 用什么锁死 | 「不改代码」这个口头承诺 | **round-trip 回归测试**（读入 → 序列化 → 再读入，语义等价）+ 存量 30 篇的字段完整性快照 |
| 好处 | — | 一次性解决「铁律 2 vs §10.1②」的矛盾；且把保护力度从「靠自觉不改代码」升级为「**有测试证明格式没变**」 |

> **这条修正的意义**：它把「保护格式」与「允许改实现」这两个都正确的诉求**同时满足**了。既有的 30 篇文章是契约本身；构建脚本是为了服务这个契约而存在的，它可以（也应该）被改进，只要回归测试证明格式未变。

**与原方案 §3.1 的差异（四处）**：

| # | 原方案 | 修正后 | 理由 |
|---|---|---|---|
| 1 | 一个 `fixboxs-admin` 容器承担 Web + worker + SQLite | **A′ 下改为三块**：静态 CMS 目录 + Gitea 容器 + 发布出口脚本；**只有走 B 时才需要原来的容器形态** | §4.2 |

### 5.2 审核流：从「自建状态机」改为「复用 PR/MR label」

**原方案 §5.3 的工作量被严重低估，且方向可以更省**：

| 对比项 | 原方案：自建状态机 | 修正后：复用 PR/MR label |
|---|---|---|
| 状态载体 | md 的 front-matter（`status: in_review`） | Gitea 的 PR label |
| 定义位置 | 要写枚举、写流转规则、写服务端强校验 | CMS 自动打标签 |
| 状态值 | draft / in_review / changes_requested / published / archived（5 态） | `sveltia-cms/draft` / `pending_review` / `pending_publish` / `pending_deletion`（4 态） |
| 流转触发 | 后台按钮 + 服务端校验 | 看板拖拽 / 编辑器状态按钮 |
| 「驳回意见」 | 要建 `review_notes` 表 + 页面 | **PR 评论**（天然留痕、可 @、可邮件通知） |
| 「谁在什么时候改了什么」 | 要写审计表 + 审计页 | Gitea 操作日志 + `git log` |
| 工作量 | 原方案把审核流放阶段 2（`⑫`），未单独估时 | **配置成本，趋近于 0** |
| 风险 | 自研状态机与 Git 分支状态**漂移**（文件说 in_review，实际没有对应分支） | 状态与 PR 是**同一个东西**，不可能漂移 |

**依据**：[Editorial Workflow](https://sveltiacms.app/en/docs/workflows/editorial.md)「Statuses」给出四个 label；「How It Works」给出动作与 Git 效果的对应表（Save → 建分支 `cms/[COLLECTION]/[SLUG]` + 开 PR；Change status → 改 label；Publish → 合并并删分支；Discard → 关 PR 并删分支）。

**什么时候仍然必须自建审核流（即 B 的价值所在）**：

| 触发条件 | 为什么 PR label 不够 | 归属 |
|---|---|---|
| 需要**按内容维度**的强制复核（如「`risk: 有数据风险` 的条目必须由 X 角色批准」） | PR label 是**条目级**，不感知 front-matter 的值 | 用 Gitea 的分支保护 + 代码所有者机制近似；不够则阶段 2 自建 |
| 需要**站点专属的合规勾选清单**（内容体系 §7.3 的 A–E 五段、§8.2 的 7 条合规要求） | 无对应承载物 | 做成 **PR 模板 / 任务清单**（Gitea 支持），零自研；若要求「不打勾不许合并」，则需要 Gitea Actions 校验或自建 |
| 需要**跨仓库/跨站的统一审核台** | Gitea 只看一个仓库 | 阶段 2 自建 |
| 需要**审核 SLA 与提醒**（如超过 48h 未审升级） | Gitea 的通知机制有限 | 阶段 2 自建，或先用 Gitea Actions 定时任务 |

> **结论**：本站的合规要求（内容体系 §8.2 规则 7「代理/VPN 类须第二人复核合规项」）**可以用「按集合开 Editorial Workflow + PR 模板中的合规勾选清单 + 分支保护 required approvals」满足**，不需自建状态机。但必须承认：**「勾选清单」本身只是流程约束**；真正不可绕过的强约束有三条，且**全部是可配置的现成能力**：① 分支保护要求至少 1 个 approval（这正是原方案 §1.2 表格里被标为 ❌ 的那个「PR review」）；② 构建期 lint；③ 发布出口的闸门。

### 5.3 文件布局修正：把「偶然正确」变成「断言 + 结果校验」

原方案 §D2 用 `_drafts/` `_archive/` 做目录隔离，机制**实测有效**——但成立的原因是一个没人保证的实现细节：

> `build-fix.cjs:331` `fs.readdirSync(SRC).filter(f => f.endsWith(".md"))` —— **非递归**，只扫顶层 `.md`。

**原方案原文写的是「利用这一点」，这是把实现副作用的运气当成了设计。** 它既没有注释说明这是刻意依赖，也没有任何测试锁定。

**最坏情形（这是本方案最严重的一次性事故场景）**：

| 步骤 | 会发生什么 |
|---|---|
| 1 | 某次重构把 `readdirSync(SRC)` 改成递归（理由往往是「支持按年份/主题分子目录」，一个非常自然的改进） |
| 2 | `_drafts/` 里的**全部草稿**、`_archive/` 里的**已下架内容**被当作正常内容构建 |
| 3 | 产物化、打包、原子切换、线上校验**全部通过**——因为校验只看「URL 是否 200」，不看「这个 URL 该不该存在」 |
| 4 | 未审校的稿、退回修改的稿、被判定「内容有误立即下架」的稿**全部上线**，且没有任何告警 |

**修正：两条显式断言（不是一条）**

| # | 断言 | 断言的对象 | 为什么需要它 |
|---|---|---|---|
| **① 源枚举断言** | **源枚举必须非递归**；或显式断言「任何以 `_` 开头的目录都被跳过」 | **实现** | 直接表达设计意图，让「依赖非递归」从运气变成契约；一旦有人改递归，断言立刻以清晰的错误信息失败 |
| **② 产物结果校验（真正的安全网）** | **构建产物中不得存在来自 `_drafts/`（或 `_archive/`）的 slug** | **结果** | **它不关心实现怎么改、只关心结果。** 无论将来是递归、是白名单、是换了个目录结构，甚至是别的脚本参与了构建，只要草稿泄进产物就一定被抓住 |

> **「断言 + 结果校验」两条并存的理由**：① 是**预防**（在错误发生前给出可读的原因），② 是**检测**（在错误发生后无论如何都能兜住）。只做 ① 会漏掉「换了一条实现路径」的情况；只做 ② 会得到一个「能拦住但说不清为什么」的失败。**两者都要，且 ② 必须落在产物上而不是源码上。**

**加固清单（写进代码，不能只写在文档里）**：

| 加固项 | 具体做法 | 验收 |
|---|---|---|
| **A. 显式忽略清单** | 在 `content-lint.cjs` 与 `build-fix.cjs` 都写一份 `IGNORED_DIRS = ["_drafts", "_archive", "_assets"]`，并**优先于任何目录遍历逻辑**判断 | 任何以 `_` 开头的目录/文件都不进构建 |
| **B. 源枚举断言（①）** | 遍历后断言「进入构建集合的每一个文件，其相对路径**不含目录分隔符**」；一旦有人改递归，断言立即失败并给出清晰错误 | 故意改递归 → 构建**失败并说明原因** |
| **C. 产物结果校验（②）** | 构建完成（或产物化完成）后，扫描 `demo/fixboxs/fix/` 与 `dist/fixboxs/fix/`，断言**不存在**任何 slug 属于 `_drafts/`/`_archive/` 的文件 | 放一篇进 `_drafts/` → **产物中必须不存在**该页 |
| **D. 反面断言** | 同时断言「顶层有内容时会正常进构建」——防止有人为了解决 A 而把枚举换成过窄的白名单，误伤正常内容 | 顶层内容照常产出 |
| **E. 回归探针固化** | 把 C、D 做成阶段 0 验收脚本里的常驻探针（每次跑完整构建 + 产物化） | 探针 C/D 通过 |

> **这条加固是「零功能新增、纯风险消除」**，工作量 < 0.5 人日，但它锁死的是一个「一次重构就把所有草稿发上线」的隐患。**这是本节最划算的一条，也是原方案里最该被补上的一条。**

**`_archive/` 的额外要求**（内容体系 §7.5：归档 ≠ 删除，URL 永久保留）：

| 要求 | 现状 | 修正 |
|---|---|---|
| 归档文件必须带 `archived_at` / `superseded_by` | 无 | lint 校验归档文件必须含这两个字段 |
| 归档文章的 URL 必须仍可访问 | 无机制（nginx 无 rewrite 块，架构评审 D9） | 需要一个重定向表（`data/redirects.json` → nginx 片段或构建期生成归档页）——**这是 A′ 与 B 都不覆盖的独立工作项** |
| 已发布文章的 URL 不因归档而 404 | 无 | 见上 |

### 5.4 front-matter 解析 / 序列化必须同源且支持嵌套对象

**这是架构层面必须动的第一件事，理由是致命的（详见总览 P1）**：

| 项 | 实测结果 |
|---|---|
| 解析器位置 | `build-fix.cjs:78-97` `parseFrontMatter` |
| 能力边界 | 只识别「标量」「扁平 `[a, b]` 数组」「扁平 `- item` 列表」 |
| 30/30 篇的 `sources` 形态 | 嵌套 YAML（`- title:` 换行 `  url:`） |
| 实测解析结果 | `sources = ["title: Microsoft 支持 — …", …]` —— **整条来源被降级为一个以 `title:` 开头的字符串，`url` 全部丢失** |
| 根因 | 缩进的 `  url:` 行不匹配 `^([A-Za-z_][\w-]*):`（要求键在第 0 列），被 `if (!kv) return;` 丢弃 |
| **损坏是否已暴露到线上** | **否**。`demo/fixboxs/data/articles.js` 中 `"sources"` 出现 **0 次**（`build-fix.cjs:356-369` 的字段白名单里根本没有它），所以这批数据**今天既没进产物、也没上线上**。它是一颗**尚未引爆的雷**：只要出现任何「读入 → 序列化 → 写出」的写入路径（后台保存、CMS 保存、批量改写脚本），**引信就被点燃**，30 篇的官方来源引用被整批清空，而构建（不看 `sources`）、部署（只查 6 个 URL）、线上校验**没有一道闸门会发现** |

**修正后的契约（三条，缺一不可）**：

| # | 契约 | 为什么 |
|---|---|---|
| 1 | **解析器支持「列表项 + 嵌套映射」**，至少覆盖 `sources: [{title, url, type}]` | 读得进 |
| 2 | **序列化器与解析器同源**：同一份字段定义（名称/类型/顺序/引号规则）同时驱动读与写 | 杜绝「读得进、写不回」 |
| 3 | **round-trip 断言测试**：读入 30 篇 → 序列化 → 再读入，必须**语义等价** | 这是 §5.0 修正后铁律 2 的**执行载体**，也是后台安全性的地基，比任何 UI 工作都优先 |

**同源的具体含义（这是最容易做错的地方）**：

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 解析器一套 YAML 子集、序列化器一套模板字符串，各自演化 | 今天能读、明天写回就变样（`version: "1.0"` 被写成 `version: 1.0`，类型从 string 变 number） | 单一字段描述表 → 同时生成解析与序列化逻辑 |
| 序列化时重新排版（重排字段顺序、改引号风格、统一缩进） | 每次保存都产生巨大 diff，淹没真实改动，`git blame` 失效 | **保留原文件的字段顺序与引号风格**；只改被编辑的值 |
| 序列化丢弃未知字段 | 后台保存一次，第三方新增的字段全没 | **未知字段原样保留**（前向兼容） |

> **验收断言（阶段 -1 的退出标准）**：`sources` 的**裸 `url:` 行数量**在 round-trip 前后一致——**当前实测基线为 109 行**（30 篇合计），而解析结果里的裸 URL 元素为 **0/30**；修完后必须变成 109 行全部可被解析为对象字段。同时 `version` 字段在 round-trip 后仍是字符串。

## 6. 发布流水线修正

> 原方案 §7 的 9 步流水线逻辑正确，但它只描述了**一条入口**（后台点发布）。修正后的目标是把流水线改成**能同时服务「A′ 直连发布」与「手工 Git 通道」两条入口的单一出口**，并把不可复用的内联代码抽成真正可复用的资产。

### 6.1 「单一出口」原则

**两条入口，一个出口，一个闸门。**

```
入口①：Sveltia CMS（A′）  ──┐
                            │  合并到 main（PR merge / 直推）
入口②：手工 Git / 开发者   ──┘
                            │
                            ▼
                 ┌──────────────────────────────────────────────┐
                 │ 统一发布出口 publish-fixboxs（新抽出）          │
                 │  0. 锁定 commit（记录 SHA）                    │
                 │  1. content-lint（V1–V13）——失败即停           │
                 │  2. node build-fix.cjs                         │
                 │  3. node deploy-fixboxs.cjs                    │
                 │  4. 原子切换（调用阶段 0 抽出的独立脚本）       │
                 │  5. 全量 URL 校验（调用同一独立脚本）           │
                 │  6. 写发布记录（commit SHA + 时间 + 结果）      │
                 │  7. 回写 PR 评论                                │
                 └──────────────────────────────────────────────┘
```

**为什么必须「单一出口」**：原方案 §7.4 自己写了「**两条路径必须共用同一段原子切换与校验代码**，避免出现『手工部署』和『后台部署』行为不一致」——但原方案并没有给出实现方式，而现状的原子切换代码**物理上不可复用**（见 §6.4）。**这是原方案内部的一处自我矛盾，必须靠重构解决。**

### 6.2 修正后的流水线（逐步对照原方案 §7.1）

| 步 | 原方案 | 修正后 | 依据 |
|---|---|---|---|
| 1 | 编辑者在后台点「发布」 | **A′：编辑者在 CMS 点 Publish → 合并 PR**（CMS 会做一轮发布前检查） | [Editorial Workflow](https://sveltiacms.app/en/docs/workflows/editorial.md)「Checks Before Publishing」 |
| 2 | 服务端把草稿移出 `_drafts/`、写 `status: published` 等 | **A′：不存在这一步**。合并把工作分支的内容落到 `main`；`status` 不进 front-matter（状态在 PR label 上） | §5.1 差异 2 |
| 3 | `git add` + `commit` | **A′：提交由 CMS/Gitea 完成**。发布出口只需 `git fetch` 到指定 commit | §5.1 差异 3 |
| 4 | `node build-fix.cjs` | ✅ 保留，但**必须在 lint 之后** | 原方案 §7.1 已把 lint 放在第 1 步前置 |
| 5 | `node deploy-fixboxs.cjs` 产物化 | ✅ 保留 | — |
| 6 | `bash deploy-fixboxs.sh`（打包 → 上传 → 原子切换 → 校验） | **A′ 下服务器本机执行，跳过 scp**：必须新增 `--local` 分支（原方案 §7.4 已提，本次确认**必须做**） | 原方案 §7.4 |
| 7 | 线上全量校验（遍历 `dist/fixboxs/fix/*.html`） | ✅ 保留并**升级为硬性要求**：现状只查 6 个 URL（含 1 篇教程），覆盖 1/30 | `deploy-fixboxs.sh:54` 实测 |
| 8 | `git push origin main`（备份，异步） | **A′ 下改为「从 Gitea 单向镜像到 GitHub」**（异地副本），同样不阻塞发布 | §4.2 |
| 9 | 写审计日志 + 通知 | **A′ 下拆成两处**：操作审计在 Gitea（自动）；发布结果需要自己的轻量记录（一个 JSON/文本日志 + 回显到 PR 评论） | §7.3 |

**新增的两步（原方案没有）**：

| 新步 | 内容 | 为什么必须有 |
|---|---|---|
| **0** | **记录并锁定 commit SHA** | 没有它就无法回答「线上跑的是哪个版本」；也无法在失败时精确重放。这是「回滚/审计」从演示变成能力的前提（与阶段 -1 的 Git 基线直接相关） |
| **7.5** | **发布结果回写 PR 评论**（"已上线 commit abc1234，校验 36/36 通过"） | A′ 下审核者与编辑者都在 Gitea 里，**发布结果必须出现在他们看得到的地方**，否则「发布成功与否」只能靠人去别处查。这是 A′ 相对 B 的一处体验缺口，成本很低 |

### 6.3 触发方式：Gitea Actions 还是服务器轮询

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **Gitea Actions** | 合并后由 Gitea Actions 以 SSH 触发服务器脚本 | 与 Gitea 同源、有运行日志视图 | 需在 Gitea 上开 Actions runner（**又一个常驻进程或有资源占用的服务**） | ⚠️ 可用，但要计入 §7.5 的资源账 |
| **Gitea Webhook + 服务器小监听** | Gitea 推 Webhook 到一个极小的 HTTP 端点 | 无 runner 开销 | **又引入一个常驻监听进程**——与「不新增服务」的方向相反 | ❌ 不推荐 |
| **服务器定时轮询（推荐）** | 服务器上一个低频定时任务：`git fetch` → 若 `main` 有新 commit 且上次发布不是这个 SHA → 跑发布出口 | **零新增常驻服务**（用系统已有的 cron/timer）；天然抗「Webhook 丢失」；天然把「自动发布」与「手动补发」统一成同一条路径 | 有轮询延迟（可设 1 分钟，本站发稿频率下完全够） | ✅ **推荐** |
| 手工执行 | 人工 ssh 跑发布脚本 | 零依赖 | 与「非技术编辑者自助发稿」目标冲突 | 仅作应急 |

> **推荐轮询的理由（这是本节一个非显然的结论）**：本站发稿频率是「每周几篇」量级，**1 分钟延迟毫无影响**；而「零新增常驻进程」符合原方案的三条铁律与架构评审 §3.4 的破例总则（该总则要求「任何需要常驻进程的变更，一律需要项目负责人显式批准并重估运维成本」——**Gitea 本身必须走这个批准流程，Actions runner 则应当避免，以免把一次批准变成两次**）。更重要的是：**轮询天然实现了「发布出口可重放」**——Gitea 挂了、Webhook 丢了、服务器重启了，只要 `main` 有未发布的 commit，下一次轮询就会补上。这直接缓解了 §4.7 的 C4 与 §6.5 的可用性问题。

**并发控制**（原方案 §D4 单并发队列的修正）：轮询方案下，「单并发」由一个简单的**文件锁**保证（`flock` 或原子创建锁文件），并在脚本里显式拒绝重入。原方案的 `publish_jobs` 队列表在 A′ 下**不需要**——这是 B 的组件，随 B 后置。

### 6.4 原子切换代码必须从 heredoc 抽出来（阶段 0 就做）

**现状（实测）**：`deploy-fixboxs.sh:40-51` 的远端段是一个 **heredoc 内联**在 `ssh 'bash -s'` 里的脚本（`sudo rm -rf ... .new` → 解包 → `chmod` → `chown` → `.prev` 轮换 → `mv`）。**全脚本无任何函数封装、无可 source 的库文件**；`deploy-fixboxs.sh:54-58` 的 URL 校验是**位置硬编码的 6 行 `for` 循环**。

**因此原方案 §7.4 的「两条路径必须共用同一段原子切换与校验代码」，在现有结构下无法直接实现**——这是评审实测确认的结论，不是推测。

| 问题 | 后果 |
|---|---|
| heredoc 内联、无函数封装、无可 source 的库 | 「发布出口」要复用只能复制粘贴 → **两份代码必然漂移**（正是原方案 §7.4 担心的事） |
| 部署逻辑跑在 `ssh` 的另一端 | **本地无法测试**，任何改动都要在真机上验证 |
| URL 校验的 6 个路径写死 | 篇数从 30 涨到 300 也不会自动跟随（工作流方案 §3.1 已指出） |
| 没有 `--local` | 在服务器本机跑时，`scp` 到同一台机器是绕路（原方案 §7.4 已指出） |
| **`--check` 的语义不符** | `deploy-fixboxs.sh:29-32` 的 `--check` 分支位于 `:27` 的 `node deploy-fixboxs.cjs` **之后**，所以它实际是「产物化 + 不上传」，**不是「只校验不产物化」**。作为闸门使用时它会先重写 `dist/`，与被校验的对象互相影响 |

**修正形态（具体到文件级，这是原方案缺的那一步）**：

阶段 0 就把下列内容抽成**独立脚本**，由 `.sh` 与发布出口**共同调用同一文件**：

| 抽出物 | 职责 | 输入 | 输出 |
|---|---|---|---|
| **`deploy-atomic.sh`** | **解包 → 原子切换**：清理 `.new`、解包、修正权限与属主、`.prev` 轮换、`mv` 就位 | 产物 tar 包路径、目标根目录 | 切换结果 + 文件数；失败非零退出 |
| **`verify-live.sh`** | **全量线上校验**：壳页固定清单 + 教程页遍历 `dist/fixboxs/fix/*.html` 逐条探测 200；收集全部失败后统一退出 | 域名、产物目录 | 通过/失败清单 |
| **`deploy-fixboxs.sh`（改造）** | 只保留编排：`--local` 跳过 scp 与上传，直接调用上面两个脚本；远端模式下先上传再通过 ssh 调用**同一份** `deploy-atomic.sh` | — | — |

**验收**：

| # | 验收项 |
|---|---|
| 1 | `deploy-atomic.sh` 可在服务器本机**单独跑通**，不依赖 ssh |
| 2 | 手工部署与发布出口**逐字节走同一条代码路径**（无复制粘贴的副本） |
| 3 | 篇数增长时，`verify-live.sh` 的校验项**自动跟随** |
| 4 | **`--check` 语义修正**：拆成 `--verify-only`（只校验既有产物，**不产物化**，`dist/` 的 mtime 不变）与 `--local`（跳过上传）两个显式开关 |

> **这条改造的价值不在「省事」，而在「让原方案 §7.4 的承诺成为事实」**。不抽出来，那句要求永远只是文档里的一句话；而 `--check` 的语义错位会在把它接入闸门时立刻变成实际问题。

### 6.5 可用性差异：Gitea 不可达时会发生什么

> **这是 A′ 相对 B 最重要的实质差异，必须写清楚，不能含糊。**

| 场景 | 走 A′ | 走 B（自建后台） | 对读者的影响 |
|---|---|---|---|
| **Gitea 宕机** | **发稿完全停止**：CMS 无法登录、无法读取/提交内容、Editorial Workflow 看板打不开（状态是 PR label，PR 在 Gitea 上）、无法合并 | 不适用 | **无**（前台是纯静态，铁律 3 成立） |
| **服务器整机宕机** | 发稿停 + 站点停 | 发稿停 + 站点停 | **站点不可访问** |
| **发布出口故障**（脚本报错、构建失败） | 内容已合并进 Gitea，但线上未更新；**修复后可重放**（轮询会重试） | 同左 | 无 |
| **网络出口抖动**（服务器连不上 Gitea 所在主机） | 发稿停 | 发稿停 | 无 |
| **Gitea 所在磁盘满 / 数据库损坏** | 发稿停 + **有丢失提交的风险** | 同左（自己的库坏了） | 无 |

**三条缓解措施（写入阶段 1′ 的交付物）**：

| # | 措施 | 说明 |
|---|---|---|
| 1 | **Gitea 与站点同机** | 本项目 Gitea 就跑在 `106.55.2.197`，**同机部署把「网络抖动导致发稿中断」这一类风险基本消除**，只剩整机风险——而整机风险对 A′ 和 B 是一样的 |
| 2 | **单机也要做 Gitea 备份** | 仓库 + 数据库 + 配置三件套的定时备份，与现有 `/var/www/backups/` 的实践一致 |
| 3 | **保留手工 Git 应急通道** | Gitea 挂时，开发者仍可直接改文件 + 跑发布脚本（原方案 §12 风险表已列「保留手工 Git 通道」，A′ 下依然成立且更必要） |

**B 的独立性优势有多大？** 原方案隐含认为「B 只依赖本机所以更可靠」。**但要注意两个对冲事实**：① B 的发布仍依赖同一台服务器上的构建与部署，服务器挂了 B 也发不了；② B 的**内容也在 Git 里**（铁律 1），而 A′ 的内容在 Gitea 里——**两者的「内容存储」单点都只有一个**，除非把 Gitea 指向一个独立磁盘/异地镜像。所以这个差异的**量级是「一个额外容器的可用性」，不是「数量级」**。

### 6.6 预览：修正为「两层预览」

| 层 | 是什么 | 成本 | 建议 |
|---|---|---|---|
| **L1：CMS 内置预览** | Sveltia 编辑器的 RichText 预览 | 零（自带） | ✅ 默认开启 |
| **L2：真实渲染器预览** | 用**真实的** `build-fix.cjs` 渲染草稿，输出到 `admin.` 域下的 `/preview/<slug>`（登录可见、`noindex`、不进产物） | 0.5–1 人日 | ⚠️ 原方案 §D8 把它列为「必须」，**修正为「强烈推荐但可后置」** |

**为什么 L2 仍值得做（尽管 Sveltia 有 L1）**：原方案 §D8 的洞察是对的——「预览好看、线上变形」是最容易发生也最难察觉的内容事故。本站的渲染器**不是通用 Markdown 渲染器**：它有自己的步骤解析（`build-fix.cjs:203-223`）、风险 callout、表格、代码块识别（`:135` 危险命令正则）。**Sveltia 的内置预览不可能模拟这些。** 因此 L2 的价值在于「用真实渲染器看一遍」。但它**不是 MVP 的阻塞项**，因为 L1 + 构建期 lint 已经能拦住大多数问题。

**L2 实现要点**：渲染必须调用真实构建器的**渲染函数**（而不是另写一个 Markdown 预览器）；这是阶段 0 抽取 `scripts/fx-markdown.cjs`（架构评审 §4.4 已规划）的直接收益——**同一份抽取工作同时服务 SEO 升级与预览**，不重复投入。

### 6.7 全量 URL 校验（替代写死的 6 个）

| 项 | 现状 | 修正后 |
|---|---|---|
| 校验范围 | `deploy-fixboxs.sh:54` 固定的 6 条路径：`/`、`/browse.html`、`/search.html`、`/wizard.html`、`/tools.html`、`/fix/wifi-connected-but-no-internet.html` | **壳页固定清单 + 教程页遍历 `dist/fixboxs/fix/*.html` 全量** |
| 覆盖率 | 1/30 教程（3.3%） | 30/30（100%），且篇数增长自动跟随 |
| 失败行为 | 失败即 `exit 1` | 保留非零退出，但**改为「收集全部失败项后统一退出」**并打印失败清单（避免只报第一条就停） |
| 额外校验 | 无 | 加：`sitemap.xml` 条目数 == 教程篇数（架构评审 P1-① 已规划）；资源 `?v=` 版本号存在性 |

**依据**：工作流方案 §3.1 已明确要求「把线上校验从 6 个固定 URL 改为遍历 `dist/fixboxs/fix/*.html`」；架构评审 §1.8-3 称部署链是「全仓最成熟的一环」，但成熟的是**流程**，不是**覆盖度**。

### 6.8 发布失败的处理（原方案 §D4 的修正）

原方案 §D4 写「失败时不回滚已提交的内容（内容可能是对的，问题在部署网络），只回滚线上目录并允许重试发布」——**这个判断正确，修正后保留**。补充两点：

| 补充 | 内容 |
|---|---|
| 失败分类 | 把失败分成「**内容类失败**」（lint 不通过、构建失败）与「**环境类失败**」（打包/上传/切换/校验失败）。前者需要人改内容，后者重试即可；**PR 评论必须说清是哪一类**，否则编辑者会反复点重试 |
| 重放的幂等性 | 发布出口必须**幂等**：重复执行同一个 commit 的结果是「不产生额外变更」。否则轮询重试会造成重复部署（虽然结果相同，但会产生噪声与竞态） |

### 6.9 本节小结（可直接执行）

| 2 | 抽 `deploy-atomic.sh` 与 `verify-live.sh`，`.sh` 与发布出口共同调用；补 `--local`，把 `--check` 拆成 `--verify-only` | 阶段 0 |

| 5 | L2 真实渲染器预览列为「强烈推荐但可后置」，复用 `fx-markdown.cjs` 抽取 | 阶段 1′/2 |

## 7. 安全与运维修正

> 原方案 §8 的 14 项安全要求**逐条都对**，问题不在内容而在**归属**：其中 6 项在 A′ 下由 Gitea 承担，**不需要我们实现**。本节给出两套清单的对照，让读者能直接算出「选 A′ 省掉了哪些安全自建工作」。

### 7.1 安全边界：走 A′ 时的攻击面变化

```
【走 A′】
  公网可访问的写入能力 = Gitea（成熟组件，自带认证/2FA/限流/审计/权限）
  我们自己要保护的东西   = ① Gitea 的配置与数据 ② admin. 静态目录（只读）③ 发布出口的凭据

【走 B】
  公网可访问的写入能力 = 我们自研的 Web 进程（认证/会话/CSRF/限流/RBAC/审计 全部自己写）
  我们自己要保护的东西   = 上面全部 + 自研代码的漏洞 + SQLite 数据
```

**关键结论**：A′ **没有减少「必须保护的资产数量」**（还是那几样），但**大幅减少了「必须自己写、自己审计的安全代码量」**。这是「用成熟组件替换自研」的标准收益，而不是「安全责任消失」。

### 7.2 两套安全清单对照表（原方案 §8 的 14 项）

| # | 原方案要求 | 走 A′（Sveltia + Gitea） | 走 B（自建后台） |
|---|---|---|---|
| 1 | 传输：全站 HTTPS + HSTS；独立证书与 server 块 | ✅ **仍要自己做**（nginx `git.` 与 `admin.` 两个 server 块 + certbot）。Gitea 本身要正确配置 `ROOT_URL` 与代理头 | ✅ 同左 |
| 2 | 认证：argon2id/bcrypt；密码长度；管理员强制 2FA | ✅ **由 Gitea 承担**（成熟实现，可配密码策略与 2FA） | ❌ 要实现：哈希算法、密码策略、2FA（TOTP）、找回密码 |
| 3 | 会话：`HttpOnly`+`Secure`+`SameSite=Lax`；空闲/绝对过期；改密码失效全部会话 | ✅ **由 Gitea 承担** | ❌ 要实现 + 要保证 `SameSite` 等细节不出错 |
| 4 | CSRF：所有写操作校验 token | ✅ **由 Gitea 承担**；**Sveltia 侧无写接口**（它只调 Gitea API） | ❌ 每个写路由都要实现，漏一个就是洞 |
| 5 | 限流：登录 5 次/15 分钟/IP + 锁定；发布接口按用户限流 | ✅ **登录限流由 Gitea 承担**；发布出口的并发由文件锁 + 轮询天然串行化 | ❌ 要自己写限流与锁定 |
| 6 | 权限：RBAC 在**服务端每个路由**强制 | ✅ **由 Gitea 承担**（仓库写权限决定能否登录 CMS；分支保护决定能否合并） | ❌ 要在每个路由上强制，极易遗漏 |
| 7 | 密钥：部署私钥仅发布 worker 可见 | ⚠️ **仍需自己做**，且**新增一项**：Gitea 的 `SECRET_KEY`、数据库口令、OAuth 应用 client id（PKCE 无 secret） | ✅ 同左（原方案的考量成立） |
| 8 | 上传：类型白名单、大小上限、随机文件名、防穿越 | ✅ **由 Sveltia 资产库 + Gitea 承担**（且官方会拒绝对 symlink / submodule 的合并） | ❌ 要自己实现全部校验 |
| 9 | 注入：Markdown 渲染沿用构建器转义；不执行用户 HTML | ✅ **仍要自己做**（预览与正文都不执行 HTML）。**注意：Sveltia 的富文本编辑不改渲染链路，风险仍在构建器上** | ✅ 同左 |
| 10 | 目录：nginx 对 admin 域禁止访问 `.git`/`.md`/`node_modules`/`*.db` | ✅ **仍要自己做**，且要**同时覆盖 `admin.` 与 `git.`**；注意现网已有 `.md`/`.bak`/隐藏文件的 deny 经验可直接复用 | ✅ 同左 |
| 11 | 暴露面：后台 `noindex`；可加 IP 白名单 | ✅ **仍要自己做**（两个子域都要 `noindex`）；**Gitea 建议不开公开注册** | ✅ 同左 |
| 12 | 审计：登录、增删改、发布、回滚、改权限全部入库 | ⚠️ **部分白拿**：Gitea 侧操作与 Git 提交天然有记录；**「发布/部署结果」需要自己的轻量日志** | ❌ 要建审计表 + 页面 |
| 13 | 依赖：依赖白名单与升级节奏 | ⚠️ **形态改变**：不再是 npm 依赖，而是**「Gitea 版本跟进 + Sveltia bundle 的固定与校验」**。仍需白名单与升级节奏 | ❌ npm 依赖管理 + 供应链风险 |
| 14 | 隐私/合规：登录页说明账号信息用途 | ✅ **仍要自己做**（Gitea 登录页 + CMS 说明；Gitea 可自定义页脚，**记得放 ICP 备案号**） | ✅ 同左 |

**统计**：

| 类别 | 项数 | 说明 |
|---|---|---|
| A′ 下**完全白拿**（Gitea/Sveltia 承担） | **6 项**（#2 #3 #4 #5 #6 #8） | 恰好是原方案里最容易写出漏洞的 6 项 |
| A′ 下**部分白拿** | 3 项（#10 #12 #13） | 仍需补自己的部分 |
| A′ 下**仍必须自己做** | **5 项**（#1 #7 #9 #11 #14） | 但这些大多是 nginx 配置与规范，不是自研代码 |
| B 下**必须自己做** | **14 项全部** | 其中 #2–#6 是典型的高风险自研安全代码 |

### 7.3 A′ 新增的安全事项（不能只算省下的）

| # | 新增项 | 要求 |
