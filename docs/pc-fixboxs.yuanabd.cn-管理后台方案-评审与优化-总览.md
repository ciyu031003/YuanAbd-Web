## 0. 一句话结论

**方向对，选型不够优，且被两个方案自己没发现的致命缺陷卡住——三个都要处理，但处理顺序很明确。**

原方案（V1.0）判断「后台必须做」是**正确**的，理由也确实成立：本站内容规范本身要求第二人合规复核（内容体系 §8.2 规则 7）、归档不删 URL（§7.5）、过期标记（§7.4），这些在纯 Git 里只能靠自觉。方案选定的「Git 写入型」形态（内容真源仍是 Markdown + Git，数据库不存正文）也是**正确**的架构判断，应当保留。

但有三个问题让方案**不能按原样开工**：

| # | 问题 | 严重度 | 影响 |
|---|---|---|---|
| **P1** | **front-matter 解析器不支持嵌套对象**，30/30 篇的 `sources` 里的 URL 全部被静默丢弃 | 🔴 致命 | 方案铁律 2 要求「后台写出同样格式的 Markdown」。当前解析器根本做不到 round-trip：**后台一保存，每篇文章的官方来源链接全部清空**。方案 §5.4 把 V2 写成「`sources` 为对象数组」，但现有解析器产不出对象。这是方案完全没算的阶段 0 工作量 |
| **P2** | **整条 fixboxs 流水线未纳入 Git**（`content/`、`build-fix.cjs`、`deploy-fixboxs*` 全是 `??` 未跟踪） | 🔴 致命 | 方案的铁律 1（内容真源 = Markdown + Git）、D3（worker `git commit/push`）、D11（`git revert` 回滚）、D5（content_hash 乐观锁）**全部假设内容已在 Git 里**。今天没有任何已提交基线 → 所有 Git 侧恢复机制都是空转。方案对此零提及 |
| **P3** | **选型漏掉了第三条路线**，把「协作者要不要 GitHub 账号」当成了路线分水岭 | 🟠 高 | 开源生态（Sveltia CMS）已内置编辑器界面 + 富文本 + 媒体库 + **审核工作流（每个条目开一个 PR/MR + label 状态）**，且支持把后端换成**自建的 Gitea/Forgejo**。这意味着「不需要 GitHub 账号」和「不需要自建服务端代码」可以同时成立——原方案 A/B 二分法里没有这个选项，导致它把 10–14 人日的自建后台当成默认答案 |

> **修正后的推荐**：**先修 P1/P2（阶段 -1，必做）→ 补闸门（阶段 0）→ 用 Sveltia + 自建 Gitea 打通网页发稿（阶段 1′，2–4 人日）→ 只有当 Sveltia 确实满足不了时才做自建后台 B（阶段 2，按需）。**
> 即：**原方案的「自建后台 13–17.5 人日」不是错，而是被过早地当成了唯一答案。**

## 1. 三个致命/重大问题：证据与修复动作

### P1 · `sources` 的 URL 被静默吞掉（解析器不支持嵌套对象）

**实测证据**（Lead 已用仓库自带解析器逻辑独立复现）：

| 项 | 实测结果 |
|---|---|
| `content/fixboxs/wifi-connected-but-no-internet.md` 的 `sources` 原始形态 | 嵌套 YAML：`- title: Microsoft 支持 — …` 换行 `  url: https://support.microsoft.com/…` |
| 解析器位置 | `build-fix.cjs:78-97` `parseFrontMatter` |
| 解析器能力边界 | 只识别「标量」「扁平 `[a, b]` 数组」「扁平 `- item` 列表」三种形态 |
| 实测解析结果 | `sources = ["title: Microsoft 支持 — 修复 Windows 中的 Wi-Fi 连接问题", "title: Microsoft Learn — netsh winsock 命令", …]` —— **字符串数组，不是对象数组** |
| URL 是否保留 | `JSON.stringify(sources).includes("http") === false` —— **全部 URL 丢失** |
| **精确口径**（v2-architect 复核） | **109 条 `url:` 行 → 0 条保留**；`type:` 32 条（31 official + 1 opensource）→ 0 条保留。⚠️ 勿用「字符串含 `http`」判定 URL 存活——`keywords` 里的 `netsh winhttp` 单词会造成假阳性 |

**根因**：缩进的 `  url: …` 行不匹配 `^([A-Za-z_][\w-]*):`（要求键在第 0 列），被 `if (!kv) return;` 直接丢弃；而 `- title: …` 行作为扁平列表项被收成整串文本。

**为什么这是致命的**：方案 §5.4 的 V2 规则写的是「`sources` 为对象数组」，方案铁律 2 写的是「后台只能写出同样格式的 Markdown」。**当前解析器既读不出对象，也写不回嵌套结构。** 最坏情况不是构建失败（构建根本不看 `sources`），而是**静默数据损坏**：编辑者在后台点一次保存，30 篇文章的官方来源引用就被清空，而构建、部署、线上校验（`deploy-fixboxs.sh:54` 只查 6 个 URL）**没有任何一道闸门会发现**。这与工作流方案 §1.2 实测的「静默丢文章」是同一类故障，且更隐蔽。

**修复动作**（必须并入阶段 0，方案未计入）：
1. 把 `parseFrontMatter` 升级为支持「列表项 + 嵌套映射」（至少支持 `sources: [{title, url, type}]`）；
2. **新增序列化器**，并与解析器**同源**（同一份字段定义同时驱动读和写），杜绝「读得进、写不回」；
3. 加一条 round-trip 断言测试：**读入 30 篇 → 序列化 → 再读入，必须与原文件语义等价**。这条测试是后台安全性的地基，比任何 UI 工作都优先。

### P2 · 内容流水线不在 Git 里，方案的恢复机制全是空转

**实测证据**：

```
$ git status --porcelain
?? build-fix.cjs
?? content/
?? demo/fixboxs/
?? deploy-fixboxs.cjs
?? deploy-fixboxs.sh

$ git ls-files content        # 已跟踪文件数
0
```

`.gitignore` 只忽略 `.tmp-shots/`、`dist/`、`dist-fixboxs.tgz`，**并未忽略** `content/` 或构建脚本——所以这是「未提交」，不是「被排除」。

**为什么这是致命的**：原方案的三条铁律、D3、D5、D11 全部建立在「内容在 Git 里」之上：

| 方案条目 | 依赖 | 现状 |
|---|---|---|
| 铁律 1「内容真源永远是 Markdown + Git」 | `content/` 已版本化 | ❌ 未跟踪 |
| D3「worker 执行 `git add` / `commit` / `push`」 | 已有可用的仓库基线 | ⚠️ 首次 commit 会是 30 篇 + 全部脚本的巨量新增，没有可回退的历史 |
| D11「一键回滚到历史提交」 | 有历史提交 | ❌ 没有历史 |
| D5「content_hash 乐观锁」 | 哈希可跨版本比较 | ⚠️ 无基线，冲突检测无参照 |

**修复动作**（阶段 -1，1 小时）：
1. 先把现有流水线与 30 篇文章**提交进 Git**，打一个 tag 作为「后台出现之前的基线」；
2. 确认 `.gitignore` 继续忽略 `dist/`、`.tmp-shots/`（产物不入库是正确的），但 `content/fixboxs/*.md` 必须在库；
3. 在后续所有阶段的验收里加一条硬性检查：`git ls-files content | wc -l` 必须等于教程篇数。

> 这一条不解决，后面做的审核流、回滚、审计**全都是演示性质的**——因为它们没有可回滚的对象。

### P3 · 选型漏了「Sveltia + 自建 Gitea」这条路线

原方案的路线表把选择简化为：

- **路线 A**：Git 后端 CMS（Sveltia/Decap + OAuth 中转）→ 需要**协作者持有 GitHub 账号**，工作量 2–4 人日，定为「备选」；
- **路线 B**：自建轻量内容后台 → 协作者只需浏览器 + 账号密码，工作量 10–14 人日，**定为推荐**。

**问题在于**：路线 A 的「需要 GitHub 账号」并不是 Git 后端 CMS 的固有属性，而是**「选 GitHub 当后端」这一选择的后果**。Sveltia CMS 官方后端支持 **GitHub / GitLab / Gitea-Forgejo** 三种，而 **Gitea/Forgejo 可以自建在你自己的服务器上**（本项目的 `106.55.2.197` 上已经有 Docker + nginx 在跑两个项目）。

由此得到原方案没有的第三选项：

| 路线 | 协作者需要 | 新增常驻服务 | 审核流 | 工作量 |
|---|---|---|---|---|
| A | GitHub 账号 + 仓库写权限 | OAuth 中转（极小） | 白拿（Editorial Workflow） | 2–4 人日 |
| **A′（新）** | **你在 Gitea 上开的账号（无需 GitHub）** | **Gitea 一个容器** | **白拿，同上** | **3–5 人日** |
| B（原推荐） | 你在自建后台开的账号 | 自建 Web + worker + 数据库 | 需要自己写状态机 | 10–14 人日 |
| C | — | CMS + DB | — | 25–40 人日（维持否决） |

**A′ 的实质**：用「多运维一个 Gitea 容器」换取「省掉整个自建后台的自研量」。Gitea 是成熟组件（自带账号、密码策略、2FA、权限、审计、PR 审核、Webhook），也就是说原方案 §8 里那 14 项安全要求中的绝大部分（认证、会话、CSRF、限流、RBAC、审计）**由 Gitea 承担，不需要自己实现**。原方案把这些当成自建后台的必要成本，实际是可以外包给成熟组件的。

**A′ 的诚实代价**（必须一并接受，否则会从「低估自建」变成「低估运维」）：
- Gitea 本身就是一个**常驻服务**，要占资源、要备份、要升级、要证书、要监控——原方案 §9 对「新增运维责任」的警告在这里**依然适用**，只是从「维护自研后台」变成「维护一个成熟开源组件」，后者风险低得多；
- **Sveltia 完全依赖远端 Git 可用**：Gitea 挂了就发不了稿（但**读者不受影响**，与方案铁律 3 一致）。自建后台 B 在这方面反而更独立（只依赖本机），这是 A′ 相对 B 的唯一实质性劣势；
- Sveltia 的 simple workflow **官方明确不支持合并冲突处理与同时编辑**——这正好印证原方案 D5（乐观锁）是真实需求，**且说明「复用现成 CMS 前端」并不能绕开冲突处理**。若并发编辑冲突成为实际问题，仍需按 D5 补一层处理，不能假装它不存在。

## 2. 方案判定表（原方案哪些保留、哪些修正、哪些否决）

| 原方案条目 | 判定 | 理由 |
|---|---|---|
| §0 「后台必须做」的结论 | ✅ **保留** | 论据成立：内容体系 §8.2 规则 7（第二人合规复核）、§7.5（归档保留 URL）、§7.4（过期标记）在纯 Git 里确实只能靠自觉 |
| 三条铁律（真源 = MD + Git / 只写同样格式 / 前台不依赖后台） | ✅ **保留并加强** | 方向完全正确。但铁律 2 目前**事实上不成立**（见 P1），必须先把解析/序列化补齐才谈得上「写出同样格式」 |
| 路线 A/B/C 三分法 | ⚠️ **修正** | 漏了 A′（Sveltia + 自建 Gitea）。且「协作者是否有 GitHub 账号」不是路线分水岭 |
| 路线 C（DB-first）否决 | ✅ **保留** | 「正文进库即成唯一副本」的判断正确，且会让现有构建/部署链路作废 |
| D1 内容真源 = Markdown + Git | ✅ 保留 | 但需先补 P2（入 Git 基线） |
| D2 `_drafts/` `_archive/` 目录隔离 | ⚠️ **保留但需加固** | 机制**实测有效**（`build-fix.cjs:331` `readdirSync` 非递归，实测放入 `_drafts/` 的草稿不进构建）。但这是**「偶然正确」而非显式设计**：没有任何断言或测试锁死它。将来若有人把 `readdirSync` 改成递归（一个很自然的「改进」），**所有草稿会被直接发布**。必须加显式断言 + 回归测试 |
| D3 服务器侧工作副本 + push | ✅ 保留 | 但 worker 的存在与否取决于选哪条路线（Sveltia 路线下提交发生在 Gitea 侧，本地工作副本的角色改变） |
| D4 单并发发布队列 | ✅ 保留 | 构建目录共享、部署是整目录切换，串行是正确判断 |
| D5 内容哈希乐观锁 | ✅ **保留，且重要性上调** | Sveltia 官方承认 simple workflow 无冲突处理，说明这不是自研的过度设计，而是任何方案的必需项 |
| D6 4 角色 RBAC | ⚠️ **按路线裁剪** | 走 A′ 时角色由 Gitea 提供（含权限粒度）；只有走 B 才需要自建 |
| D7 会话与安全 | ⚠️ **按路线裁剪** | 同上，走 A′ 时大部分由 Gitea 承担 |
| D8 服务端渲染预览 | ⚠️ **降级为可选** | Sveltia 自带编辑器预览。但「预览必须用真实渲染器，避免预览好看线上变形」这条洞察是对的，可作为增强项保留 |
| D9 图片上传 | ⚠️ 后置 | 与「不做自动压缩」判断一致；Sveltia 自带媒体库（资产库），比自建上传省事 |
| D10 taxonomy 外置 | ✅ **保留，且应提前** | 这是架构评审 P0-4 的工作，与后台解耦，且是编辑器下拉框的前置 |
| D11 两级回滚 | ✅ 保留 | 需要 P2 补基线后才真正可用 |
| §5.4 校验规则 V1–V13 | ⚠️ **保留但需修 V2/V6** | V2 的「19 个字段」是快照而非约束（加入 `status`/`author` 后立刻 >19）；V6 的「10 段齐全」**必须带同义标题白名单**——实测 `remote-control-scam.md` 用的是「怎么确认处理好了」而非「怎么确认修好了」（29 篇用前者写法、1 篇用后者写法，全库每篇恰好 10 个 H2）。若白名单写死单一标题，这篇现在就在线上的文章会被自己的校验器判死 |
| §10 工作量 13–17.5 人日 | ⚠️ **需重估** | 未包含 P1（解析器/序列化器升级）与 P2（Git 基线）；且若选 A′，阶段 1 从 10–14 人日降到 3–5 人日 |
| §11 不做什么（N1–N10） | ✅ 基本保留 | 「不把正文存库」「不替换构建脚本」「前台不依赖后台」「不做实时协同」等边界判断均正确 |

## 4. 修正后的实施顺序（含验收标准）

```
阶段 -1  补基线（必做，约 0.5 人日，与后台选型无关）
   ① 修 front-matter 解析器，支持嵌套对象（sources）
   ② 写同源序列化器 + round-trip 断言测试
   ③ 把 content/ + 构建/部署脚本提交进 Git，打基线 tag
   ✅ 验收：读入 30 篇 → 序列化 → 再读入，语义等价；
           git ls-files content 计数 = 30；
           sources 的 url 数量在 round-trip 前后一致（当前为 0，必须变成 >0）
              │
              ▼
阶段 0  闸门（必做，2–3.5 人日，与后台选型解耦）
   ④ content-lint.cjs（V1–V13，后台与构建共用一套；V2/V6 按上文修正）
   ⑤ build-fix.cjs 由「警告后跳过」改为「收集错误后统一非零退出」
   ⑥ deploy 校验从 6 个 URL 改为全量遍历 dist/fixboxs/fix/*.html
   ⑦ taxonomy 外置（content/taxonomy.json）——同时是编辑器下拉框的前置
   ✅ 验收：三种故障探针（删 title / 加 BOM / 错 related）全部被拦且不发布；
           部署校验覆盖全部教程页；
           故意把草稿放进 _drafts/ 并证明它不会被发布（锁死 D2 的「偶然正确」）
              │
              ▼
```
