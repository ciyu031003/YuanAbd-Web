## 5. 账号体系与 RBAC

> 这一章回答你的原话：「管理员账号由最初始的 root 账号去做分发，然后给到内部人员去做文章、更新、修正和添加文章等各种功能」。
>
> 设计原则一句话：**平台上只有 root 一个「种子账号」，其余所有账号都是 root 分发出去的派生账号，没有自助注册这条路径。**

### 5.1 root 超管账号的定义

#### 5.1.1 root 是什么、不是什么

| 项 | 定义 | 依据/理由 |
|---|---|---|
| 身份 | 系统初始化时由部署流程生成的**唯一**超管账号，`users.is_root = true` | 与你的原话「最初始的 root 账号」一一对应 |
| 数量 | **有且仅有一个**（DB 层唯一部分索引强制，见下） | 有多个 root 就没有「最初始」的语义，也无法追责 |
| 归属 | 你本人持有；**不发放给任何内部人员** | root 的权限集是「能改一切 + 能改别人」，一旦外发就失去兜底身份 |
| 与 admin 的区别 | admin 能管内容和人；root 还能**管 admin、改系统级配置、执行灾难恢复** | 见 §5.4 权限矩阵最后两行 |
| 不可删除 | DB 层 `CHECK` + 应用层双重禁止；删除操作一律 403，无例外 | 唯一的自我恢复入口，删掉就没有输出了 |

**技术落地（给上篇 §4 的补充约束）**：`users` 表需要一个**部分唯一索引**保证「最多一个 root」，而不是靠应用层自觉：

```sql
-- 示意，具体迁移由后台项目的迁移工具管理
CREATE UNIQUE INDEX uq_users_single_root ON users ((is_root)) WHERE is_root;
-- 该索引使「第二条 is_root = true」直接违反唯一约束而失败
```

同时用触发器或应用层事务禁止「把 root 置为 disabled / deleted」（否则等于自锁）。

#### 5.1.2 初始密码怎么生成（**不要硬编码默认密码**）

这是最容易做错的一步。任何「admin/admin123」「首次登录后自行修改」的写法都等价于把后台当作公网开放。

**推荐做法（三选一，按推荐度排序）**：

| 方案 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| **A. 安装期一次性打印（推荐）** | 部署时的 init 任务生成 24 位随机密码（`crypto.randomBytes(18)` 转 base32），**只打印到部署者的终端/安装日志**，DB 里只存 argon2id 哈希，日志文件权限 600 且安装后提示删除 | **必须** | 密码从不出现在任何持久化的、可被他人读到的位置；部署者本人就是 root 持有者，天然是唯一知情人 |
| B. 首次访问引导（bootstrap token） | 部署时写入一个一次性 bootstrap token 到 600 权限文件；访问 `/setup?token=…` 设置 root 密码；设置成功后 token 永久失效 | 建议 | 适合「部署者 ≠ 使用者」的场景；本项目管理后台是你自己用，A 已足够 |
| C. 环境变量注入 | 从 `ADMIN_INITIAL_PASSWORD` 环境变量读取（由部署机注入，不落盘） | 可用 | 需确保变量不出现在 shell history、docker inspect、进程环境列表中（这三点很容易漏） |

**明确禁止**：
- ❌ 任何形式的默认密码、示例密码、`CHANGE_ME` 占位；
- ❌ 把初始密码写进 README、`.env.example`、docker-compose 明文；
- ❌ 把 root 密码作为种子数据（seed）提交进仓库。

> 补充：bootstrap 完成后，**初始化入口必须自动关闭**。若 `/setup` 在已有 root 的情况下仍可访问，就等于开了一个「重置 root」的后门——这条要写进 §8 的验收标准。

#### 5.1.3 首次登录强制改密

| 规则 | 做法 | 级别 |
|---|---|---|
| 强制改密 | 账号带 `must_change_password = true`，登录成功后所有路由（除改密接口与登出）返回 302 跳转改密页 | **必须** |
| 服务端强制 | 不是前端弹窗了事：中间件层面拦截，绕过前端直调 API 同样 403 | **必须** |
| 新密码策略 | 长度 ≥ 12；不与旧密码相同；不命中弱密码表（可内置 top-10000）；argon2id 重算哈希 | **必须** |
| 改密即踢会话 | 改密成功后**该用户全部会话立即失效**（见 §5.7） | **必须** |

> 「必须改密」这个标志位在**每一个** root 分发的账号上都要置位——包括后续所有邀请流程（§5.2）。它保证任何由他人设定过的密码都不会长期存活。

#### 5.1.4 忘记 root 密码的恢复路径

这是必须提前设计好的，不能「到时候再说」。因为 root 不可删除、无法由别人重置，一旦忘记密码且无恢复路径，**后台将永久无法登录**。

**推荐：离线恢复命令（必须）**

| 项 | 规格 |
|---|---|
| 形式 | 服务器上以 `sudo` 执行一条**只在本机可用的 CLI 命令**，例如 `docker compose exec app node tools/reset-root-password.cjs` |
| 凭据 | 该命令需要读取一个**只有服务器 root 可读的文件**（600，如 `/etc/fixboxs-admin/recovery.key`），或要求输入安装时生成的恢复码 |
| 效果 | 重置 root 密码并置 `must_change_password = true`，同时**记录一条不可删除的审计事件** |
| 网络面 | 该命令**不暴露任何 HTTP 接口**——不做「忘记密码」邮件找回（本站没有邮件服务，加邮件服务只为 root 找回是过度设计） |
| 演练 | 每季度演练一次（见 §8 阶段 3 的运维项） |

**为什么不用邮件找回**：引入 SMTP 就引入一个新的凭据、一个新的失败面、一个新的攻击面（邮件劫持 → root 接管）。而 root 持有者就是服务器管理员本人，本机恢复是**更短、更可控**的路径。这是有意的取舍，不是遗漏。

**同时必须有的兜底**：数据库备份中的 `users` 表本身就是最后一道恢复手段（还原备份即可恢复当时的密码哈希）。但备份恢复代价高，不作为首选。

### 5.2 邀请 / 下发账号流程

> 这是「root 分发账号」的完整落地。核心要求：**密码不由 root 设定并口头转达**，而是走一次性激活链接，由被邀请人自己设定。

#### 5.2.1 流程时序

```
① root 在「用户管理」页填：姓名 + 登录名/邮箱 + 角色 + （可选）领域范围
        │
        ▼
② 服务端生成一次性邀请令牌
   · token 明文 = 32 字节随机（crypto.randomBytes(32)）
   · 库里只存 token_hash = sha256(token)，明文绝不留存
   · 记录 expires_at / created_by / role / scope
        │
        ▼
③ root 拿到激活链接（形如 https://admin.<域>/activate?t=<token>）
   · 复制链接，通过内部渠道（当面 / 内部 IM）交给被邀请人
   · 链接只显示这一次；页面刷新即不可再取（可重新生成，见 5.2.3）
        │
        ▼
④ 被邀请人打开链接 → 设置密码（≥12 位，弱密码表校验）
   · 令牌校验：存在 + 未过期 + 未使用 + 未被撤销
   · 设置成功的一瞬间：标记 used_at、绑定账号、写审计
        │
        ▼
⑤ 账号状态变为 active；用户可用登录名 + 自设密码登录后台
        │
        ▼
⑥ 可选：若系统开启 TOTP 强制（§6.6），首次登录引导绑定 2FA
```

#### 5.2.2 「链接有效期、一次性、可撤销」的规格

| 属性 | 规格 | 级别 | 为什么 |
|---|---|---|---|
| 有效期 | **24 小时**（默认），root 可缩短至 1 小时 | **必须** | 内部人员通常当天就激活；窗口越短，链接被转发的风险越小 |
| 一次性 | 激活成功即 `used_at` 落库；**同一令牌二次使用一律拒绝**，且**记录一条告警级审计**（重复使用是典型的链接泄露信号） | **必须** | 一次性是这类令牌的全部意义 |
| 可撤销 | root 可在「待激活邀请」列表里一键撤销（`revoked_at` 落库，立即失效） | **必须** | 发错人、发错角色时必须能收回 |
| 自动失效 | 账号被停用时，其名下所有未使用邀请同步失效 | **必须** | 否则停用后仍能被激活 |
| 存储 | 只存 hash；**审计日志与访问日志均不得记录 token 明文**（URL 里带 token，nginx 的 `$request_uri` 会记录它——必须显式排除该路径的日志或改为 POST 提交） | **必须** | 这是最容易被忽略的凭据泄露口 |
| 传输 | 链接必须 https；激活页 `noindex` | **必须** | 防抓取与中间人 |
| 重发 | root 可「重新生成」——旧令牌立即失效，新令牌重新计 24 小时 | 建议 | 比「延长旧链接」安全 |

> **关于第 5 行（日志泄露 token）的额外说明**：`location /activate` 在 nginx 层应使用 `access_log off;`，或把激活改为「页面加载后由前端 POST 提交 token」。后者更好，因为它同时避免 token 出现在浏览器历史与 Referer 头里。**这一条要写进 §8 的验收项。**

#### 5.2.3 令牌的技术规格（给上篇 §4 表结构的补充）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigserial | 主键 |
| `token_hash` | char(64) | sha256 十六进制，**明文不存** |
| `user_id` | bigint | 预创建的账号（状态 `pending`），激活后转 `active` |
| `role` / `scope_domain` | text / text[] | 邀请时就确定角色与领域范围，激活后不可由被邀请人自改 |
| `created_by` | bigint | 必填，且**必须是 root**（见 §5.4 的 P9 权限） |
| `expires_at` / `used_at` / `revoked_at` | timestamptz | 三态时间戳 |
| `created_ip` | inet | 便于异常排查 |

> 与上篇 §4 的关系：本表与上篇的 `users`/`roles` 表配套，字段名以实际迁移为准。这里给出的是**语义契约**，不是最终 DDL。

### 5.3 角色模型

#### 5.3.1 五个角色

按「**最小权限 + 职责分离**」设计。关键取舍：**写内容的人不能自己发布**（除非他被显式授予发布权），因为本站内容体系有硬性的双人复核要求。

| 角色 | 代号 | 定位 | 谁应该持这个角色 |
|---|---|---|---|
| 超级管理员 | `root` | 种子账号，一切权限的源头 | **仅你本人** |
| 管理员 | `admin` | 日常运营负责人：管内容、管账号（除 root）、发布 | 1 人（可考虑你兼任） |
| 审核者 | `reviewer` | 内容合规与质量把关；**不创作**，只审 | 代理/VPN 类内容的第二人（合规硬要求） |
| 编辑者 | `editor` | 新增 / 更新 / 修正文章；**无权发布** | 内部人员 1–3 人 |
| 只读 | `viewer` | 只读列表与预览；给外部顾问、临时人员 | 按需 |

**为什么把「编辑」与「发布」拆开**：内容体系 §8.2 规则 7 明文写「审核时由第二人复核合规项（§7.3 E 段）后方可发布」，且 §7.3 的 E 段是「发布前逐项打勾」的清单。让创作者自己点发布，这条要求就退化成自觉。拆开之后，「复核过」这件事变成**服务端的硬前置**（§5.5 状态机里体现）。

**为什么叫 `editor` 而不是 `author`**：本项目的内部人员既要新增也要修正别人的文章，用「作者」会误导成「只能碰自己写的」。

#### 5.3.2 领域范围 `scope_domain`（可选的第二维约束）

角色是一个维度，**领域**是正交的第二个维度。`scope_domain` 让「某编辑只能改某些领域的文章」成为可能：

| 取值 | 含义 |
|---|---|
| `NULL` / `*}` | 全领域（admin、reviewer 默认） |
| `['proxy-vpn']` | 只能编辑代理/VPN 领域 |
| `['net-basic','ip-dns','router']` | 网络线编辑 |

**这条能力是自建后台相对现成 CMS 的实质增量之一**：现成的 Git 后端 CMS 只能控制到「仓库/目录级权限」，没法表达「这个人能改 A 领域不能改 B 领域」。

**建议**：MVP 阶段所有编辑者给全领域，等真的出现「需要隔离的领域」（比如让不熟悉合规的实习生不要碰 proxy-vpn）时再启用。**不要为了这个维度推迟 MVP**——但表结构要预留好，否则后期加列要改数据。

**强制位置**：`scope_domain` 的校验在**服务端文章读写层**（同一个中间件里既查角色又查领域），不在前端下拉框里过滤。

### 5.4 权限矩阵（具体到动作）

> 这是本章最需要写扎实的部分。矩阵按「**谁能对什么资源做什么动作**」组织，而不是「谁能看到哪个菜单」。
>
> 记号：✅ 允许 ｜ ❌ 禁止 ｜ ⚠ 有条件允许（条件写在表下） ｜ 🔒 需再认证（见 §6.6）

**A. 内容创作类动作**

| # | 动作 | root | admin | reviewer | editor | viewer | 条件说明 |
|---|---|---|---|---|---|---|---|
| A1 | 查看文章列表 / 详情 | ✅ | ✅ | ✅ | ✅ | ✅ | viewer 只看已发布 |
| A2 | 新建草稿 | ✅ | ✅ | ❌ | ✅ | ❌ | reviewer 不创作，避免自审自批 |
| A3 | 编辑草稿（`draft`/`changes_requested`） | ✅ | ✅ | ⚠ | ✅ | ❌ | ⚠ 仅限被指派审核的那篇，可改但会留痕 |
| A4 | 编辑已发布文章的正文 | ✅ | ✅ | ❌ | ✅ | ❌ | 见 A7「修正」的差异流程；编辑后回到 `in_review` |
| A5 | 修改 front-matter 结构字段 | ✅ | ✅ | ❌ | ✅ | ❌ | `title/slug/domain/category/risk/...`（`slug` 改动受限，见 A13） |
| A6 | 修改 `sources`（官方来源） | ✅ | ✅ | ❌ | ✅ | ❌ | **必须支持可变字段对象数组**，见 §7.3 |
| A7 | 「修正」已发布文章（错别字/排版） | ✅ | ✅ | ❌ | ✅ | ❌ | 按内容体系 §7.4：**不改 `updated`、不升版本**，但仍要写审计 |
| A8 | 「修正」已发布文章（补步骤/改命令） | ✅ | ✅ | ❌ | ✅ | ❌ | 按 §7.4：**必须改 `updated` + 版本 +0.1 + 更新日志加一行** |
| A9 | 提交审核 | ✅ | ✅ | ❌ | ✅ | ❌ | 触发 `draft → in_review` |
| A10 | 撤回自己的提交 | ✅ | ✅ | ❌ | ✅ | ❌ | 仅当仍在 `in_review` 且无人开始审核 |
| A11 | 删除草稿（物理删除） | ✅ | ✅ | ❌ | ⚠ | ❌ | ⚠ editor 只能删**自己创建且从未提交过审核**的草稿；其余走归档 |

**B. 审核与发布类动作**

**矩阵之外的两条硬规则**：

1. **服务端强制（§5.4.1）**：矩阵里每一个 ✅ 都必须在**对应的服务端路由**上校验，而不是在前端隐藏按钮。前端隐藏只影响体验，不构成安全。
2. **默认拒绝**：路由与权限的映射表用**白名单**方式声明；新增路由若未在表中声明，一律拒绝（fail-closed），而不是默认放行。

#### 5.4.1 服务端强制原则（这条要写进代码规范）

| 要求 | 做法 | 级别 |
|---|---|---|
| 每个写路由都有权限声明 | 路由注册时显式声明 `{ action: 'A3', resource: 'article' }`，中间件统一校验 | **必须** |
| 未声明即拒绝 | 白名单机制，缺声明 → 403 + 记一条审计 | **必须** |
| 领域范围在同一处校验 | 与角色校验在**同一个中间件**，避免两处逻辑漂移 | **必须** |
| 对象级校验 | 不仅校验「有没有 A3 权限」，还要校验「对**这一篇**有没有 A3 权限」（含 `scope_domain` 与归属） | **必须** |
| 前端隐藏只是体验 | 前端隐藏按钮用于减少误操作，**不得作为安全措施写进任何验收项** | **必须** |
| 回归测试 | 每个角色 × 每个动作写一条「越权应 403」的自动化测试（5 角色 × ~30 动作 ≈ 150 条，可参数化生成） | **必须** |

> **为什么这一条值得单独成节**：绝大多数后台安全事故不是「加密算法选错了」，而是「某个 API 忘了鉴权」。把权限校验变成**注册路由时不得不填的一个字段**（而不是记得要写的一段代码），才可能长期不腐坏。这 150 条越权测试是所有安全投入里性价比最高的一项。

### 5.5 双人复核（合规硬要求）如何变成代码

内容体系 §8.2 规则 7 原文：**「审核时由第二人复核合规项（§7.3 E 段）后方可发布」**。§7.3 的 E 段是三条勾选：无禁止内容 / 代理VPN 类含合规提示块 / 页脚含 ICP 备案号。

**服务端实现规格**：

| 规则 | 做法 | 级别 |
|---|---|---|
| 适用范围 | 领域为 `proxy-vpn` 的**全部**文章；以及正文中出现「代理 / VPN / PAC / 加速器 / 抓包」的任意文章（按 §8.2 的适用范围原文） | **必须** |
| 提交审核时 | 打标 `compliance_required = true`（自动判定 + 允许 reviewer 手工加标） | **必须** |
| 发布前置 | `compliance_required` 的文章，必须有**一条** `compliance_checks` 记录：`{article_version, checked_by, checked_at, 三个勾选项}`，且 `checked_by ≠ author_id`（**第二人**），且 `checked_by` 的角色 ∈ {reviewer, admin, root} | **必须** |
| 版本绑定 | 复核记录绑定**当时的正文版本号/hash**；复核之后正文若再变动，该记录**自动失效**（必须重新复核） | **必须** |
| 服务端位置 | 在发布路由的**事务内**校验，不通过 → 403 并明确指出缺哪一项 | **必须** |
| 审计 | 每次复核写审计（谁、何时、对哪一版、勾了哪三项） | **必须** |

> **「绑定版本」这一条是整个机制的关键**。如果只记「这篇复核过」，那么复核者看过之后编辑者再改一句话就能带着合规标记上线——复核就变成了橡皮图章。绑定 hash 之后，任何正文改动都会让复核记录失效，**复核者确认的与你发布的是同一份东西**。

**非合规类文章**：默认不强制双人复核（否则 30 篇的日常维护会被拖死），但仍遵循「**不同人审核**」原则——如果你的团队只有 1 个编辑 + 你自己，那就把「编辑 + admin 审核」当作双人流程。**不允许同一账号既提交又审核通过**（B1 的服务端校验）。

### 5.6 账号生命周期

| 事件 | 触发者 | 系统行为 | 级别 |
|---|---|---|---|
| **创建** | root（或 admin 创建非管理角色） | 建 `pending` 账号 + 发一次性邀请；**不设密码** | **必须** |
| **激活** | 被邀请人 | 设密码 → `active` → `must_change_password` 已在激活时满足，无需二次 | **必须** |
| **改密（自己）** | 任意用户 | 校验旧密码 → 更新哈希 → **踢掉该用户全部会话** → 审计 | **必须** |
| **改密（被重置）** | root/admin | 置 `must_change_password = true` → **踢掉全部会话** → 审计；不显示新密码给操作者（由用户自己走邀请链接重置） | **必须** |
| **改角色** | root（admin 仅限低权角色） | 立即生效；**踢掉该用户全部会话**（旧会话可能缓存了旧权限） | **必须** |
| **改领域范围** | root/admin | 立即生效；同样踢会话 | **必须** |
| **停用** | root/admin | `status = disabled`；**立即踢掉全部会话**；其未使用邀请全部失效；已发布内容**保持不变**（内容不随人走） | **必须** |
| **启用** | root/admin | `active`；需重新登录 | **必须** |
| **离职回收** | root/admin | 停用（**不删除**）→ 作者署名保留为历史事实 → 审计记录保留 | **必须** |
| **删除** | 无 | **任何用户都不做物理删除**；仅 root 可在极端情况下... **也不做**。DB 层用 `deleted_at` 软删（且默认查询过滤） | **必须** |

**为什么「不删除用户」**：文章 front-matter 里有 `reviewer` 字段、审计日志里有 `user_id`，删除用户会让这些引用变成悬空 ID，历史就无法追溯。用人成本很低（一行 `disabled`），追溯能力很贵。

**「停用」与「内容」解耦（重要）**：停用一个人**不影响他已发布的文章**。内容体系从未要求「作者离职则内容下线」，相反 §7.5 要求「归档而非删除、URL 永久保留」。这条要在实现时明确，避免把「离职回收」实现成「批量下架」。

### 5.7 会话失效策略

| 场景 | 策略 | 级别 | 为什么 |
|---|---|---|---|
| 改密 | **立即失效该用户全部会话** | **必须** | 改密的常见动机就是「怀疑泄露」，此时不踢等于没改 |
| 改角色 / 改领域范围 | **立即失效该用户全部会话** | **必须** | 会话里可能缓存了权限快照，不踢则降权不生效 |
| 停用 | **立即失效该用户全部会话** | **必须** | 停用后还能用旧 Cookie 操作是不可接受的 |
| 删除邀请 / 撤销邀请 | 使该邀请令牌失效 | **必须** | — |
| 管理员主动「登出某用户全部设备」 | 提供按钮 | 建议 | 应急用 |
| 空闲超时 | 30 分钟无操作即失效 | **必须** | 后台是唯一有写权限的组件，闲置会话是最大暴露面 |
| 绝对超时 | 自登录起最长 12 小时 | **必须** | 防止「一直挂着」的长寿会话 |
| 发布 / 回滚 / 改权限等高危动作 | **再认证**（要求重新输入密码或 TOTP） | 建议 | 见 §6.6；比缩短全局会话更精准 |

**技术实现要点**：

- 会话是**服务端记录**（`sessions` 表：`id, user_id, token_hash, created_at, last_seen_at, expires_at, ip, user_agent, revoked_at`），Cookie 里只放随机 token，**不放 JWT**。
- 理由：JWT 无法即时撤销（除非再建一张黑名单表，那就等于又回到服务端会话，且更复杂）。**「改密即踢全部会话」这个需求本身就宣判了无状态 JWT 不适合本场景。**
- 每次请求校验：token 存在 + 未过期 + 未撤销 + `user.status = active` + `user.password_changed_at < session.created_at`（最后一条就是「改密即踢」的落地方式，无需遍历删除——但显式删除更直观，建议两者都做）。
- Cookie 属性见 §6.3。

## 6. 安全机制（完整清单）

> 你的原话是「有全面的安全机制」。本章按**「做法 + 级别 + 为什么」**逐项列全，并把「为什么」写清楚——因为只写要做什么，过一年就没人知道哪条能动、哪条不能动。
>
> **本章的总纲（先读这一段）**：本站的静态前台是一个「零动态、零数据库、零会话」的产物目录，攻击面几乎为零；**整个系统里唯一有写入能力、唯一有数据库连接、唯一有会话的组件就是这个后台**。因此——
>
> **安全投入应 100% 集中在后台，不要去改已经很好的静态站。**
>
> 这条不是口号，它决定资源分配：前台不需要 WAF、不需要额外的认证、不需要修改任何一行渲染逻辑。

### 6.1 传输层

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 全站 HTTPS | 后台独立子域（建议 `admin.pc-fixboxs.yuanabd.cn`）配 certbot 证书；80 → 301 到 443 | **必须** | 后台传输的是密码与会话 Cookie，明文即失守 |
| HSTS | `Strict-Transport-Security: max-age=31536000; includeSubDomains` | **必须** | 防降级与 SSL 剥离。**注意 `includeSubDomains` 之前要确认所有子域都有 https**，否则会把自己的其他站锁死 |
| TLS 版本与套件 | 复用现有 `/etc/letsencrypt/options-ssl-nginx.conf`（禁 TLS1.0/1.1，优先现代套件） | **必须** | 现成最优实践，无需自研 |
| 安全响应头 | 后台 server 块单独一组，**不要复用静态站的 `fixboxs-sec.conf`** | **必须** | 后台需要更严的 CSP 与 `X-Frame-Options: DENY`；静态站的策略对后台要么过松要么过严 |

**后台专属响应头（建议值）**：

| 头 | 值 | 为什么 |
|---|---|---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'` | 后台是登录态页面，CSP 是 XSS 的最后一道闸 |
| `X-Frame-Options` | `DENY` | 防点击劫持（CSP 的 `frame-ancestors` 已含，双写兼容老浏览器） |
| `X-Content-Type-Options` | `nosniff` | 防 MIME 嗅探 |
| `Referrer-Policy` | `no-referrer` | **激活链接带 token，Referer 外泄会让 token 泄露到第三方** |
| `X-Robots-Tag` | `noindex, nofollow` | 见 §6.11 |
| `Permissions-Policy` | `geolocation=(), camera=(), microphone=()` | 后台不需要这些能力 |

> `referrer-policy: no-referrer` 不是可选优化——激活链接与部分页面的 URL 里带令牌，默认的 Referer 行为会把完整 URL 发给任何被点击的外链。**这一条要写进 §8 的验收项。**

### 6.2 密码存储

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 算法 | **argon2id**（首选）；若运行时受限则 bcrypt `cost ≥ 12` | **必须** | argon2id 是当前密码哈希竞赛的推荐算法，抗 GPU 与抗 ASIC；bcrypt cost 12 是可用下限 |
| argon2id 参数 | 内存 ≥ 19 MiB，迭代 ≥ 2，并行度 1（OWASP 基线）；按服务器实际内存可上调 | **必须** | 参数过低的 argon2 并不比 bcrypt 强 |
| 盐 | 由库自动生成，每用户独立 | **必须** | 库的默认行为，不要自己实现 |
| 长度策略 | 登录密码 **≥ 12 位**；**不强制**大小写/符号混合，但做弱密码表拦截 | **必须** | 长度比复杂度更有效；强制复杂度反而催生 `Password1!` |
| 弱密码拦截 | 内置常见弱密码表 + 与用户名/邮箱相似度检查 | 建议 | 便宜且有效 |
| 失败信息 | 登录失败统一返回「用户名或密码错误」，**不区分账号是否存在** | **必须** | 防用户名枚举 |
| 哈希升级 | 登录成功时若发现哈希参数已过时，**就地重算** | 建议 | 让参数升级平滑发生 |
| 明文 | 任何位置不得记录明文密码：日志、审计、异常堆栈、APM | **必须** | 最常见的密码泄露途径是日志 |

### 6.3 会话与 Cookie

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| Cookie 名 | 用不暴露技术栈的名字（如 `fxa_sid`），避免 `connect.sid`/`JSESSIONID` 之类 | 建议 | 减少指纹信息 |
| `HttpOnly` | **必须开** | **必须** | 任何 XSS 都无法通过 `document.cookie` 窃取会话 |
| `Secure` | **必须开** | **必须** | 防明文信道泄露 |
| `SameSite` | `Lax`（默认）；**若后台完全不需要被外站跳转携带 Cookie，用 `Strict`** | **必须** | `Lax` 已阻断绝大多数 CSRF；`Strict` 更严但会牺牲「从外部链接点进来保持登录」的体验 |
| `Path` | `/` | 建议 | — |
| `Domain` | **不设置**（host-only） | **必须** | 设置 `.yuanabd.cn` 会让 Cookie 发往所有子域，扩大攻击面 |
| 会话 ID | ≥ 128 位密码学随机；**Cookie 只存 token，不存用户信息** | **必须** | 无状态 JWT 已排除，见 §5.7 |
| 登录时重建会话 | 登录成功后**换发新的会话 ID**（防会话固定） | **必须** | 会话固定攻击的标准防线 |
| 空闲超时 | 30 分钟 | **必须** | 见 §5.7 |
| 绝对超时 | 12 小时 | **必须** | 见 §5.7 |
| 登出 | 服务端删除会话记录，不只是清 Cookie | **必须** | 否则被盗 token 仍可用 |

### 6.4 CSRF

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 全写操作覆盖 | 所有 POST/PUT/PATCH/DELETE 校验 CSRF token（含发布、回滚、上传、改权限） | **必须** | 后台每个写操作都是高价值目标 |
| Token 形式 | **双提交 + 服务端会话绑定**：token 存在会话里，同时放到表单隐藏字段或 `X-CSRF-Token` 头 | **必须** | 仅靠 `SameSite` 不够（老浏览器、`Lax` 的边界情况） |
| 校验时机 | 在**权限校验之前**，统一中间件 | **必须** | 避免「越权请求先执行了副作用再报 403」 |
| 只读接口 | GET 一律不得有副作用 | **必须** | 「用 GET 发布」这类设计会绕过全部 CSRF 防护 |
| 额外防线 | 校验 `Origin`/`Sec-Fetch-Site` 头 | 建议 | 低成本高收益 |

### 6.5 登录限流与锁定

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 按 IP 限流 | 5 次/15 分钟，超出返回 429 | **必须** | 阻断暴力破解与撞库 |
| 按账号限流 | 10 次/15 分钟（与 IP 独立计数） | **必须** | 防「换 IP 打同一账号」的分布式破解 |
| 递增延迟 | 第 3 次失败起逐步增加响应延迟（如 1s/2s/4s） | 建议 | 低成本削弱自动化 |
| 账号锁定 | 连续 10 次失败 → 锁定 30 分钟（**临时锁定，非永久**） | **必须** | 永久锁定会成为「用别人用户名就能锁死他」的 DoS |
| 解锁 | 到期自动解锁；root/admin 可手工解锁 | 建议 | — |
| 限流范围 | 登录、邀请激活、重置密码、2FA 校验**四处都要** | **必须** | 只做登录限流等于留了三扇没锁的门 |
| 存储 | 计数放 DB 或 Redis（若引入）；**不要放进程内存** | **必须** | 进程重启即清零，重启后限流失效 |
| 审计 | 每次失败登录写审计（含 IP、UA、时间） | **必须** | 异常排查与入侵发现的主要线索 |

> **锁定策略的取舍**：临时锁定比永久锁定安全。永久锁定看起来更狠，但它把「DoS 某个账号」的能力交给了攻击者，而内部账号的名单往往不难猜。

### 6.6 2FA（TOTP）

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 形式 | TOTP（RFC 6238），30 秒步长，兼容任意认证器 App | **必须（对 root/admin）** | 不依赖短信，无额外成本，离线可用 |
| 强制对象 | **root 与 admin 强制**；reviewer/editor 建议开启 | **必须** | root/admin 一旦失守，整个内容库与账号体系都失守 |
| 绑定流程 | 生成密钥 → 显示二维码 + 明文密钥 → 要求输入一次动态码验证后才生效 → 生成 10 个一次性恢复码 | **必须** | 「未验证就绑定」会导致用户被自己锁在外面 |
| 恢复码 | 10 个，只显示一次，库内存哈希；用掉即失效；剩余数量可查 | **必须** | 手机丢失是必然会发生的事 |
| 校验窗口 | 允许 ±1 个步长（时钟漂移容忍） | 建议 | 过严会让用户频繁失败 |
| 重放防护 | 记录已用过的 TOTP 步长，同一步长不得复用 | 建议 | 防在同一 30 秒窗口内重放 |
| 关闭 2FA | 需要**再认证 + 恢复码或密码**；root/admin 的 2FA **不允许自行关闭** | **必须** | 否则 2FA 只防外人不防自己（被盗号者第一件事就是关 2FA） |
| 高危动作再认证 | 改密、改权限、发布、回滚、导出审计：要求重新输入密码或动态码（5 分钟有效窗口） | 建议 | 比全局缩短会话更精准，见 §5.7 |

> **诚实的成本提示**：2FA 对有 3–5 个内部人员的团队意味着「每人多一个 App + 丢手机时的恢复流程」。如果你只有 1–2 个编辑者，可以**只对 root/admin 强制**，编辑者用强密码 + 限流 + 审计兜底。这个取舍要在 §9 明确拍板。

### 6.7 密钥与数据库凭据管理

> 你明确要求「后台直接接数据库，新建独立库」。这一节就是这条要求的安全后果——**DB 凭据一旦泄露，爆炸半径有多大，完全取决于你给了这个账号多少权限。**

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 凭据存储 | 不写进代码/仓库；放服务器上权限 600 的 `.env`（owner 为运行后台的非 root 用户），或 Docker secret | **必须** | 仓库会被 clone、被备份、被误发 |
| 是否入库 | **不要**把 DB 密码再存进后台自己的 `settings` 表 | **必须** | 循环依赖：读密码需要连库，连库需要密码 |
| 账号分离 | 后台**不使用** `postgres` 超级用户；建专用角色（见 §6.7.1） | **必须** | 超级用户被拿下 = 整台机器所有库失守 |
| 库隔离 | **新建独立库** `yuanabd_pc_fixboxs`，与服务器上已有的其他库物理隔离；逐库 `REVOKE CONNECT`（写法见上篇 §4） | **必须** | 你的原话「不得占用/污染已有数据库」，这条同时是安全边界 |
| 网络面 | PostgreSQL **只监听 `127.0.0.1`**（或 unix socket），不对公网开 5432 | **必须** | 数据库直接暴露在公网是最高频的入侵入口之一 |
| 防火墙 | 云安全组不开放 5432/3306；服务器 `ufw` 同样不放行 | **必须** | 双保险 |
| 应用侧配置 | 连接串里显式指定库名；**不要用「默认库」** | **必须** | 防配置漂移连错库 |
| 轮换 | DB 密码每 6–12 个月轮换一次；换人（有权限的人离开）后立即轮换 | 建议 | — |
| 日志 | 连接串进日志前必须打码 | **必须** | 异常堆栈里带密码是经典事故 |
| 权限授予 | 后台角色**只对 `yuanabd_pc_fixboxs` 库有权限**；不给 `SUPERUSER`、`CREATEDB`、`CREATEROLE` | **必须** | 见下方爆炸半径分析 |

#### 6.7.1 DB 凭据泄露的爆炸半径（专节）

**场景**：后台被 RCE / 配置泄露 / `.env` 被读走，攻击者拿到 `yuanabd_pc_fixboxs` 的连接串。此时他能做什么，**完全由你授予的权限决定**：

| 若你授予的权限 | 泄露后攻击者能做 | 后果 |
|---|---|---|
| ❌ 不推荐：用现有应用的账号，或给 `SUPERUSER` | `DROP DATABASE` 服务器上**任何**库；读取其他应用的业务数据；`COPY … TO PROGRAM` 直接执行系统命令拿到 shell | **整台服务器失守**，且会波及 `learn-workbench` / `travel-notes` |
| ⚠️ 次优：给 `CREATEDB` / `CREATEROLE` | 创建新库与新角色，可作为立足点做进一步提权 | 影响范围超出本库 |
| ✅ 推荐：只对 `yuanabd_pc_fixboxs` 有 `CONNECT` + 表级 DML | **只能读写后台自己的元数据库**（账号、会话、审计、发布任务） | 后台业务数据泄露；但**内容真源在文件系统而不在库里**，30 篇文章本体不受影响；其他应用完全不受影响 |

**这个对比就是「最小权限」的全部意义**。注意最后一行里有一个**架构带来的天然缓冲**：

> **因为正文真源是文件系统上的 Markdown（不是数据库），所以 DB 凭据泄露并不会泄露或篡改文章内容本身。** 这是「DB 只存业务态、不存正文」这一架构选择的**安全红利**——上篇第 2 章从一致性/回滚角度论证了这个选择，而这里它又额外买到了一份隔离。

**但要诚实指出残余风险**：攻击者拿到后台库后，能够**伪造一个 admin 会话**（往 `sessions` 表插一行）或**直接改 `users` 表的角色**，从而绕过登录与 2FA，进而通过后台的发布能力篡改线上内容。所以最小权限**降低但不等价于消除**风险。

**对应的加固要求**（针对这个残余风险，级别均为**必须**）：

| 加固项 | 做法 |
|---|---|
| 会话双层校验 | 会话表被改也无法直接生效：会话 token 需与服务端签名值双重匹配（token = `random` + `HMAC(secret, random)`，secret 只存在于文件系统，不在库里） |
| 数据库侧可审计 | 开启 PostgreSQL 的连接与 DDL 审计日志（`log_connections`、`log_statement = 'ddl'`） |
| 变更告警 | 对 `users`/`sessions`/`invites` 表加审计触发器，写入只增不改的 `audit_log`——攻击者改角色这个动作本身会留下记录 |
| 文件系统独立 | DB 凭据泄露 ≠ 文件系统权限泄露：后台进程以非 root 用户运行，该用户对 `content/` 有写权限，但对 `.env` 的读取权限应与 DB 凭据分离到不同文件 |
| 恢复 | 有每日备份 + 每月恢复演练（§8 阶段 3） |

### 6.8 上传安全

后台的图片上传是**唯一接受外部字节流**的入口，必须最严格。

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 类型白名单 | **只允许** `image/jpeg`、`image/png`、`image/webp`、`image/avif`；**明确拒绝 SVG 与任何 HTML** | **必须** | SVG 可内嵌 `<script>`，是 XSS 的经典载体；HTML 更直接 |
| 类型判定 | 校验**文件魔数（magic bytes）**，不信任 `Content-Type` 与文件扩展名 | **必须** | 两者都是客户端可控的 |
| 大小上限 | 单文件 ≤ 2 MB（与内容体系 §7.2 的「≤200KB」规范并存：2MB 是拒绝线，200KB 是规范线并给出提示） | **必须** | 防磁盘打满与 DoS |
| 文件名 | **服务端重命名为随机名**（如 `<sha256前16位>.<ext>`），丢弃用户提供的文件名 | **必须** | 防路径穿越（`../../`）、防覆盖、防扩展名欺骗 |
| 落盘路径 | 规范化后**必须在允许目录内**（`path.resolve` 后做前缀断言） | **必须** | 这是防路径穿越的最后一道代码级防线 |
| 存储位置 | 落到 `content/fixboxs/_assets/<slug>/`，与内容一起版本化 | 建议 | 与上篇的文件布局一致；图片随内容走，不会「内容在、图片没了」 |
| 元数据 | 记录 sha256（同图去重）、原始文件名（仅作展示，不用于落盘）、上传者、时间 | 建议 | 去重 + 溯源 |
| 图片处理 | **不做**服务端转码/压缩（架构评审 N12：唯一真破例点，暂缓） | 决策 | 引入 `sharp` 等原生依赖会显著增大供应链与构建风险 |
| 内容校验 | 上传时提示脱敏要求（内容体系 §7.2 P6–P8），并**强制填写 alt**（P9） | **必须** | 脱敏是内容规范的硬要求，漏了会泄露真实 MAC/序列号 |
| 提供方式 | 上传的文件由静态目录提供；**必须以 `Content-Disposition: inline` + 正确 MIME 提供，且不得在后台源站以外的路径暴露** | 建议 | 避免「上传的文件被当页面执行」 |
| 图片 URL | 渲染时对路径做白名单前缀校验 | 建议 | 防 `javascript:` 之类协议注入 |

> **关于 alt 的说明**：内容体系 §7.2 P9 要求「每张图必须有 alt 文本，描述这张图要说明什么，不是截图」。把它做成上传时的**必填项**，比事后 lint 有效得多——因为事后再补，编辑者已经不记得图里是什么了。

### 6.9 注入与渲染

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| SQL | **全部使用参数化查询**（预处理语句）；**禁止任何字符串拼接 SQL** | **必须** | 最基础也最有效；配合 §6.7 的最小权限构成双层防护 |
| ORM/查询构造器 | 使用 ORM 的绑定参数能力；若手写 SQL 同样走绑定 | **必须** | ORM 不能替代这条纪律（原生查询常有拼接） |
| Markdown 渲染 | 预览与正文渲染**复用构建脚本的转义逻辑**（`build-fix.cjs` 的 `esc`/`inline`） | **必须** | 避免「预览好看、线上变形」，同时避免另写一套渲染器引入 XSS |
| 原始 HTML | **不允许**在正文里执行用户 HTML（当前构建器本身就会转义，保持这一行为） | **必须** | 编辑者可能从外部粘贴带脚本的内容 |
| 输出转义 | 后台自己的页面（用户列表、审计列表）对用户名/备注等字段做输出转义 | **必须** | 存储型 XSS 的典型入口是「用户名」这种看似无害的字段 |
| 命令执行 | 后台**不得**把用户输入拼进 shell 命令（构建/部署调用必须用参数数组形式，不用 `shell: true` + 拼接） | **必须** | 发布链路会调用 `node build-fix.cjs`，这是命令注入的高危点 |
| 文件路径 | 所有由用户输入参与的路径都做 `path.resolve` + 前缀断言 | **必须** | 防目录穿越读写 |

> **特别提醒 6.9 的第 6 行**：本后台的核心功能之一是**触发构建与部署**，也就是执行外部命令。这是整个系统里最危险的代码路径。**哪怕文件路径已经校验过，也一律用参数数组方式调用，绝不拼字符串**——因为「路径里出现空格或引号」这种事早晚会发生。

### 6.10 nginx 层防护

后台 server 块与静态站 server 块**必须分离**（建议独立子域 + 独立 server 块）。

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 禁止访问源文件 | `location ~ /\.(?!well-known) { deny all; }` —— 覆盖 `.git`、`.env`、`.svn` | **必须** | 静态站现有配置已做（`.tmp-shots/nginx-fixboxs.conf:37`），后台必须同样做且更严 |
| 禁止 Markdown | `location ~* \.(md|bak|sql|log|db|sqlite)$ { deny all; }` | **必须** | `.md` 是内容真源，`*.db` 是可能的备份文件，都不该可下载 |
| 禁止 node_modules | 后台若以静态目录方式暴露前端资源，显式 deny `/node_modules/` | 建议 | 防依赖源码与版本指纹泄露 |
| 限制请求体 | `client_max_body_size 2m;`（与上传上限一致） | **必须** | 防大体积请求耗尽资源 |
| 超时 | `client_body_timeout` / `send_timeout` 设合理值（如 30s） | 建议 | 防慢速攻击 |
| 反代头 | 正确传递 `Host`、`X-Real-IP` / `X-Forwarded-For`、`X-Forwarded-Proto` | **必须** | 限流按 IP 计数、Cookie `Secure` 判定都依赖它；**后台必须只信任来自本机 nginx 的 `X-Forwarded-For`**，否则 IP 限流可被伪头绕过 |
| 日志 | 后台单独 access/error log | **建议** | 与静态站日志分离便于排查；但注意激活路径的 token，见 §5.2.2 |
| 目录列表 | `autoindex off;`（默认即 off，显式声明） | 建议 | — |
| IP 白名单 | 若内部人员 IP 稳定，`allow` 指定网段 + `deny all` | 建议 | 最有效的暴露面削减手段；但移动办公场景会失效，需评估后决定 |

> **一个容易踩的坑（必须写进实施注意）**：nginx 反代后，后台看到的客户端 IP 全部是 `127.0.0.1`，**按 IP 限流会变成「全体共享一个计数器」**，导致一个人失败 5 次就把所有人锁死。必须在后台显式配置「信任的代理跳数/来源」并从中取真实 IP，且要确认这个取值**不被客户端伪造**。

### 6.11 暴露面与可发现性

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 独立子域 | `admin.pc-fixboxs.yuanabd.cn`，而非 `pc-fixboxs.yuanabd.cn/admin/` | **必须** | Cookie 与安全头作用域隔离；后台的 XSS/CSRF 不波及静态站；静态站产物目录保持纯净 |
| noindex | 响应头 `X-Robots-Tag: noindex, nofollow` + 页面 `<meta name="robots" content="noindex">` + `/robots.txt` 的 `Disallow: /` | **必须** | 三条都用，因为不同爬虫遵守不同的那一条 |
| 不暴露技术栈 | 关闭 `X-Powered-By`；错误页不显示框架堆栈；404 与 403 返回统一页面 | 建议 | 减少指纹信息 |
| 错误信息 | 生产环境错误只返回「操作失败，请联系管理员」+ 一个可查的 trace id；**详情只进服务端日志** | **必须** | 堆栈信息常含路径、SQL、库结构 |
| 健康检查 | `/healthz` 只返回 `ok`，不暴露版本、DB 状态、组件清单 | 建议 | 否则这是个免费的情报接口 |
| 独立目录 | 后台代码**不进** `/var/www/fixboxs` | **必须** | 静态站目录保持零动态成分 |

> 现有静态站配置已实现「`.md` 与隐藏文件 deny」这一层（`.tmp-shots/nginx-fixboxs.conf:36-37`），后台应把同一套思路**加强后重写一份**，而不是共用同一个 snippet——因为后台需要更严的 CSP 与 `X-Frame-Options: DENY`。

### 6.12 审计日志

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 必记事件 | 登录成功/失败、登出、改密、重置密码、绑定/解绑 2FA、创建/撤销邀请、激活账号、改角色、停用/启用、文章增改删、提交审核、审核通过/退回、合规复核、发布、回滚、导出、改系统设置 | **必须** | 这是「谁在什么时候改了什么」的唯一答案来源 |
| 记录字段 | `id, ts, user_id, actor_ip, user_agent, action, target_type, target_id, before(jsonb), after(jsonb), result, trace_id` | **必须** | `before/after` 用 jsonb，配合 PostgreSQL 的 GIN 索引可按任意路径检索（这是选 PG 的实际收益之一） |
| 不可篡改 | 审计表**只允许 INSERT**（DB 层收回 UPDATE/DELETE 权限）；后台应用账号也没有这两项权限 | **必须** | 可被修改的审计等于没有审计 |
| 保留期 | ≥ 180 天（建议 1 年） | 建议 | 与内容体系 §7.4 的 12 个月复核周期对齐 |
| 敏感字段 | 审计里**不得**记录密码、令牌明文、2FA 密钥、完整连接串 | **必须** | 审计本身会长期留存，写进去就等于永久泄露 |
| 查看 | 后台「审计日志」页支持按用户/动作/时间过滤；导出需 🔒 再认证 | **建议** | 见 §5.4 D1/D2 |
| 与 Git 的关系 | 内容变更同时有两条记录：**审计日志（业务视角）+ Git 提交（内容视角）** | **必须** | 两者互为佐证；只有一条时，任何一方出问题都无法还原 |

### 6.13 依赖治理与供应链

| 项 | 做法 | 级别 | 为什么 |
|---|---|---|---|
| 锁定版本 | 必须提交 lockfile（`package-lock.json`），**锁定精确版本** | **必须** | 无锁定的依赖树等于每次部署换一份代码 |
| 依赖数量 | 最小化；能用标准库就不引包 | **必须** | 每一个包都是一次信任决策 |

| 已知漏洞扫描 | 定期跑 `npm audit`（或等价工具）；高危漏洞 7 天内升级 | **建议** | 低成本 |
| 升级节奏 | 每月一次，先在非生产端口验证 | **建议** | 与 §8 阶段 3 的运维项一致 |

| 私有 registry | 不引入来路不明的包；包名要逐字核对 | **建议** | 防 typosquatting |

### 6.14 与静态站的安全边界（明确「不做什么」）

| 不做的项 | 理由 |
|---|---|
| ❌ 不给静态站加 WAF / 认证 / 限流 | 静态站是零动态产物，攻击面接近零；投入产出比极低 |
| ❌ 不把后台部署到 `/var/www/fixboxs` 内 | 破坏「静态站产物纯净」这一边界 |

| ❌ 不为「后台挂了」做前台降级逻辑 | 前台压根不知道后台存在 |

## 7. 发布链路与内容真源

> 这一章回答：「编辑在后台点一下保存、再点一下发布，服务器上到底发生了什么」。
>
> **本章的两个硬约束是实测得出的，且必须在写后台第一行代码之前解决**——它们不是优化项，是前置条件。

### 7.0 两个前置硬约束（先读这一节）

#### 约束一：现有 front-matter 解析器不支持嵌套对象，任何写回动作都会毁数据

**实测复现**（用仓库自带解析器逻辑，`build-fix.cjs:78-97` 逐字复现）：

```
$ node -e "<复现 build-fix.cjs 的 parseFrontMatter 逻辑，解析 30 篇中的一篇>"
CURRENT PARSER sources = [
 "title: Microsoft Support - Windows 文件恢复（Windows File Recovery）",
 "title: Apple 支持 - 从备份恢复 Mac",
 "title: Apple 支持 - 恢复已删除的文件（时间机器与本地快照）"
]
contains http: false        ← 全部 URL 丢失
```

**根因**（`build-fix.cjs:87-88`）：

```js
const kv = line.match(/^([A-Za-z_][\w-]*):\s*(.*)$/);   // 要求键在第 0 列
if (!kv) return;                                         // 缩进的 "  url: …" 不匹配 → 被直接丢弃
```

嵌套行的键有缩进，匹配不上这个正则，于是被 `if (!kv) return;` 静默丢掉；而 `- title: …` 行被当成**扁平列表项**收成一整串文本。

**全量实测（本次复核）**：

| 指标 | 实测值 |
|---|---|
| content/fixboxs 篇数 | 30 |
| front-matter 字段数 | 恰好 19（全部 30 篇字段集合完全一致） |
| `sources` 条目总数（`- ` 行） | 217（= 全部列表项数量，说明**只有 sources 使用 YAML 块状列表**） |
| 其中以 `- title:` 开头 | 109 —— 即 109 个 source 条目 |
| `url:` 嵌套键出现次数 | **109** |
| `type:` 嵌套键出现次数 | **32** |
| 无 `type` 的篇数（键集合 = {url}） | 20 篇 |
| 带 `type` 的篇数（键集合 = {type, url}） | 10 篇 |
| `type` 取值分布 | `official` 31 次、`opensource` 1 次 |

> 这 217 这个数字有个额外价值：**它证明 30 篇里除 `sources` 外没有任何字段使用 YAML 块状列表**（其余 18 个字段全是标量或内联 `[a, b]` 数组）。因此「支持块状列表 + 嵌套映射」这个升级的工作量是**有界且很小**的——序列化面只有 `sources` 一处。

**为什么这是致命的**：`build-fix.cjs` **根本不读 `sources`**（它丢弃 8 个字段：`aliases/sources/prerequisites/tools/reviewer/reviewed_at/related/version`，见 `:356-369`）。所以最坏情况**不是构建失败，而是静默数据损坏**：

1. 编辑者在后台打开一篇带 3 条官方来源的文章；
2. 后台用当前解析器读进来 → `sources` 变成 3 个字符串，URL 全没了；
3. 编辑者点保存 → 后台按它读到的内容写回 → **3 条官方来源链接永久消失**；
4. 构建、部署、线上校验（`deploy-fixboxs.sh:54` 只查 6 个 URL）**没有任何一道闸门会发现**。

这与工作流方案实测的「静默丢文章」是同一类故障，且更隐蔽——文章还在，只有可信度证据没了。

#### 约束二：原子切换代码是 heredoc 内联、无函数封装，无法被后台复用

**实测**（`deploy-fixboxs.sh:40-51`）：

```bash
ssh -i "$KEY" -o BatchMode=yes "$HOST" 'bash -s' <<REMOTE
set -e
sudo rm -rf ${REMOTE_ROOT}.new && sudo mkdir -p ${REMOTE_ROOT}.new
sudo tar -xzf /tmp/${TARBALL} -C ${REMOTE_ROOT}.new
...
sudo rm -rf ${REMOTE_ROOT}.prev
if [ -d ${REMOTE_ROOT} ]; then sudo mv ${REMOTE_ROOT} ${REMOTE_ROOT}.prev; fi
sudo mv ${REMOTE_ROOT}.new ${REMOTE_ROOT}
REMOTE
```

这段代码的真实形态是：

1. **写在 heredoc 里**——它是「一段被传给 ssh 的字符串」，不是一个可调用的单元；
2. **没有函数封装**——没有 `atomic_switch()` 这样的入口；
3. **变量靠 heredoc 内插值**——`${REMOTE_ROOT}` 是在**发起端的 shell** 里展开的，不是远端；这意味着调用方必须复制这套变量命名；
4. **整段依赖 scp 上传前置**（`:34-37`）——后台在同机执行时这一步是绕路。

**后果**：如果后台要触发部署，最省事的做法是「把这段代码复制到后台的 worker 里」。一旦复制，就有了**两份原子切换实现**。它们今天看起来一样，但任何一方改动（比如加上「切换前校验产物完整性」）都不会同步到另一方——**「手工部署」与「后台部署」开始漂移，而漂移的表现形式是「线上偶发切换半边」这种最难排查的故障**。

**修复动作**：把原子切换与校验抽成**一个独立脚本**，让手工路径与后台路径**调用同一个文件**。这属于阶段 -1 的工作（见 §8），与后台选型无关。

### 7.1 内容真源策略（本册的决断）

**结论：正文真源 = 文件系统上的 Markdown（`content/fixboxs/*.md`）+ 本地 Git 仓库；数据库只存业务态（账号/会话/审计/审核状态/发布任务/媒体元数据），不存正文。**

| 候选 | 内容 | 判定 |
|---|---|---|
| **方案甲**：DB 存元数据 + 正文在 Markdown | 沿用现有构建链；后台写文件 | ✅ **采用** |
| 方案乙：正文进库，构建时导出 Markdown | 构建前多一道导出 | ❌ 本册否决 |

**为什么否决方案乙**（三条，按重要性排序）：

1. **它会摧毁「可逆性」**。方案乙下，`content/` 变成「产物」而非「真源」。一旦导出逻辑有 bug（而导出逻辑正是最容易写错的一环——它要处理可变字段的嵌套对象、需要保持键顺序、需要处理引号），你得到的不是「构建失败」，而是**内容与库不一致，且无法判断哪边是对的**。
2. **它让现有 30 篇变成一个需要迁移的存量包袱**。30 篇文章要一次性导入数据库，而导入工具本身就要依赖「解析器已经修好」这个前提——**同样的前置依赖，方案甲只需要修解析器，方案乙还需要修完再写一遍导入 + 导出**。
3. **它放弃了 §6.7.1 里那个真实的安全红利**。正文在文件系统上时，DB 凭据泄露**不会泄露或篡改文章内容**。方案乙消灭了这个隔离。

> **与 v2-architect 的结论一致**：他同样主张方案甲，核心理由是**方案乙会新增第二个静默损坏点**（DB → 导出器 → MD 这条链同样没有下游闸门），而不是「DB 不好」。需要强调：**用户原话是「后台直连数据库」，不等于「正文进库」**——连库是为了存账号、审核状态、审计与发布任务，不是为了存正文。

**方案甲的成本，要诚实说**：

| 成本 | 说明 | 缓解 |
|---|---|---|
| 后台必须能**正确读写 Markdown 文件** | 这正是约束一要解决的问题 | 用成熟库（gray-matter + eemeli/yaml），见 §7.3 |
| 并发编辑需要靠内容哈希而非 DB 行锁 | 见 §7.5 | 乐观锁，本来就要做 |
| 审核状态若只写文件，查询效率低 | 需要列表按状态筛选、统计「待我审核」 | **元数据双写**：状态同时写 front-matter（真源）与 DB 索引表（查询用） |
| 文件系统与 DB 可能不一致 | 双写引入一致性风险 | 见 §7.1.1 |

#### 7.1.1 元数据双写的一致性规则（必须写清）

**规则：文件是权威，DB 是可重建索引。**

| 项 | 规则 |
|---|---|
| 写入顺序 | 先写文件（原子写：临时文件 + rename），**成功后再**更新 DB 索引；DB 更新失败只记警告，不回滚文件 |
| 自愈 | 提供「重建索引」命令：扫全部 `content/fixboxs/**/*.md`，重算 DB 索引表。**因为文件是权威，这个命令永远能跑通** |
| 一致性检查 | 每次发布前跑一次索引与文件的对账；不一致则拒绝发布并提示跑重建（fail-closed） |
| 状态字段位置 | `status`/`author`/`review_notes` 写进 **front-matter**（随内容一起被 clone、diff、回滚），DB 索引表只做查询加速 |

> **为什么状态必须写进文件而不是只写 DB**：因为状态与内容会一起漂移。如果状态只在 DB，那么「用 `git revert` 回滚一篇文章」之后，文件回到了旧版但 DB 还认为是已发布——两个真源打架。写进文件后，回滚文件即回滚状态。

#### 7.1.2 与旧方案的差异说明

V1.0 方案 §3/D1 已得出同样的结论（内容真源 = Markdown + Git），本册**沿用该结论并给出独立的重新论证**。差异在于：

| 项 | V1.0 | 本册 V2.0 |
|---|---|---|
| Git 的角色 | 服务器工作副本 + `git push` 到 GitHub 备份 | **只用本地 Git**（用户明确不考虑 GitHub 账号）；远端备份改为服务器本机/异机备份（§7.8） |
| DB | SQLite | **PostgreSQL 独立库 `yuanabd_pc_fixboxs`**（用户要求直连数据库） |
| 已入库的 `sources` 处理 | 未提及 | 明确要求支持**可变字段对象数组**（20 篇 2 键 / 10 篇 3 键），见 §7.3 |

### 7.2 发布链路总体时序

```
【编辑者】
  ① 保存草稿        → 写 content/fixboxs/_drafts/<slug>.md（原子写）
                     → 更新 DB 索引
                     → 写审计
                     → 返回新的 content_hash
  ② 预览             → 走「与 build-fix.cjs 同一套渲染逻辑」出 HTML
                     → 挂在 admin 域 /preview/<slug>，登录可见、noindex
                     → 同时显示校验结果（错误 + 警告）
  ③ 提交审核         → status: in_review（写文件）
                     → 通知 reviewer
【审核者】
  ④ 审核             → 通过：status: approved + reviewer/reviewed_at
                     → 代理/VPN 类：勾选 §7.3 E 段三项 → 写 compliance_checks（绑定版本）
                     → 退回：status: changes_requested + review_notes
【发布者（admin/root 或被授权的 reviewer）】
  ⑤ 点「发布」       → 服务端事务内做完整前置校验（§7.4）
                     → 生成 publish_job（queued）
【发布 worker（单并发，串行消费）】
  ⑥ git commit       → 本次全部文件变更打一个提交
  ⑦ node build-fix.cjs
  ⑧ node deploy-fixboxs.cjs        （产物化 + 自检断链）
  ⑨ bash deploy-fixboxs.sh --local （原子切换，§7.6 抽出的共用脚本）
  ⑩ 全量 URL 校验                    （§7.6，替代现在只查 6 个）
  ⑪ 写审计 + 标记 job 成功
```

**关键设计点**：

| 点 | 设计 | 理由 |
|---|---|---|
| 第 ⑤ 步的事务边界 | 前置校验 + job 入队在一个事务里；**入队成功即返回**，不阻塞 HTTP 请求 | 构建部署耗时远超 HTTP 超时；编辑者应立刻看到「已排队」 |
| 单并发 | 同一时刻只允许 1 个 job 处于 `running` | 构建输出目录共享、部署是整目录切换，并行必然互踩 |
| 第 ⑥ 步先于构建 | 先 commit 再 build | 若构建失败，内容变更仍在 Git 里可追溯（而不是「改了但没记录」） |
| 失败不回滚内容 | 构建/部署失败时**保留已提交的内容**，只回滚线上目录 | 内容可能是对的，问题在网络或磁盘；回滚内容会丢掉编辑者的工作 |
| 幂等 | 同一个 job 重试不得产生重复提交或重复切换 | 重试前检查当前 HEAD 与 job 记录的目标 commit |

### 7.3 解析器与序列化器（本册最硬的技术要求）

**总原则：解析器与序列化器必须同源，且必须覆盖「可变字段的对象数组」。**

#### 7.3.1 为什么必须用成熟库而不是继续手写正则

| 事实 | 说明 |
|---|---|
| 当前手写解析器**正在丢数据** | 109 个 `url` 全部丢失（§7.0 约束一实测） |
| 手写要覆盖的语法面不止「缩进」 | 至少要正确处理：块状列表 + 嵌套映射、引号（`version: "1.0"` 必须保持字符串，否则被解析成数字 1.0）、内联数组里的逗号与特殊字符（`symptoms` 里有 `connected no internet` 这种含空格的项）、值里含中文全角标点、BOM、CRLF |
| 这些正是**成熟库已经解决且经过大量测试**的问题 | gray-matter（MIT）解析 front-matter，eemeli/yaml（ISC）负责真正符合 YAML 规范的读写 |
| 自研的风险不对称 | 自研写对没奖励，写错是**静默数据损坏** |

**结论**：引入 `gray-matter`（MIT）+ `eemeli/yaml`（ISC）。这两个库的许可都是宽松许可，符合用户在「自用/不商用/不违法前提下鼓励复用开源」的要求。

> **与现有「零依赖」约束的关系**：`build-fix.cjs` 目前是零依赖的。引入依赖是有成本的（§6.13 供应链）。但这里的取舍很明确：**零依赖的价值远小于「不损坏数据」的价值**。建议把依赖**限定在解析/序列化这一层**，并单独锁版本；构建脚本的其余部分保持零依赖。

#### 7.3.2 `sources` 的数据模型（必须按可变字段设计）

```
sources: Array<{
  title: string,          // 必有
  url:   string,          // 必有，https
  type?: 'official' | 'opensource' | ...   // 可选，当前实测取值：official(31) / opensource(1)
}>
```

**三条不可违反的规则**：

| # | 规则 | 违反后果 |
|---|---|---|
| 1 | **不要按「固定三字段」建模**。若 DB 列 `type` 设成 `NOT NULL`，20 篇（无 type）写不出来；若序列化器固定输出 `type`，10 篇以外会多出空字段 | 要么报错阻塞，要么静默改变文件 |
| 2 | **`type` 只在原文有时才输出**，不补空值、不写 `type: null` | 会污染 diff，且让 round-trip 不再等价 |
| 3 | **键顺序保持 `title → url → type`** | 否则 30 篇文件全部产生无意义 diff，`git log` 被噪音淹没 |

**DB 侧的对应设计**（给上篇 §4 的补充）：

| 方案 | 做法 | 评价 |
|---|---|---|
| ✅ 推荐 | `sources jsonb NOT NULL DEFAULT '[]'::jsonb` —— **整体存 jsonb**，配合 GIN 索引可按任意路径查询 | 天然支持可变字段；这正是选 PostgreSQL 的实际收益（MySQL 的 JSON 列无法直接为内部字段建二级索引） |
| ⚠️ 次选 | 子表 `article_sources(article_id, ord, title, url, type)`，`type` 允许 NULL | 关系型更规整，但「恢复为原 YAML 形态」需要额外逻辑，且容易在 `type` 为 NULL 时输出多余字段 |
| ❌ 避免 | 子表 + `type NOT NULL` | 直接写不出 20 篇 |

#### 7.3.3 `sources` 编辑控件设计

**必须是「可增删条目的列表」，不是三个固定输入框**：

| 控件 | 字段 | 必填 | 校验 |
|---|---|---|---|
| 条目（可拖拽排序、可删除） | `title` | ✅ | 非空；长度 ≤ 200 |
| | `url` | ✅ | **必须 https**；必须是绝对 URL；发布前可选做联网 HEAD 校验（默认关闭，见 §7.4 V9） |
| | `type` | ❌ | 下拉：`official` / `opensource` / `standard` / `vendor` / 留空；**留空时序列化器不输出该键** |

**UI 上的两条提示**：

- 「**留空即可，不要为了填满而编造 `type`**」——因为 20 篇存量文章没有 type，新文章没有 type 是完全正常的；
- 「至少 1 条 `official` 或 `vendor`」（内容体系 §5.1 的要求），在保存时以**警告**形式提示而非硬拦（存量 30 篇未逐篇复核此项）。

> **这是一处对旧方案的自我修正**：V1.0 的 §5.4 V2 把「`sources` 为对象数组」写成硬校验，但没说清 `type` 可选。若把「至少 1 条 official」做成硬失败，会**判死 20 篇现在就在线上的文章**——这与 V1.0 的 V6「10 段齐全」白名单是同一类坑。

#### 7.3.4 round-trip 验收标准（可直接作为回归基线）

这是「后台不会毁数据」的**唯一可证伪的验证方式**，必须写进阶段 -1 的退出标准。

| # | 断言 | 期望值 |
|---|---|---|
| R1 | 30 篇逐篇 `parse → serialize → parse`，三态语义等价 | 30/30 通过 |
| R2 | `sources` 的**条目数**与原文一致 | 逐篇一致 |
| R3 | `sources` 每条的**键集合**与原文一致（有无 `type` 必须一致） | 逐篇一致 |
| R4 | **`url` 总数** | `= 109`（**当前实测为 0**） |
| R5 | **`type` 总数** | `= 32`（`official` 31 + `opensource` 1） |
| R6 | 键顺序 `title → url → type` | 全部一致 |
| R7 | `version: "1.0"` 往返后仍是**字符串** `"1.0"`，不是数字 `1` | 30/30 |
| R8 | 未改动的字段不产生 diff：`parse → serialize` 后与原文**逐字节比对** | 30/30 字节级一致（含换行符与末尾空行） |
| R9 | 内联数组里的含空格项（如 `connected no internet`）往返后不被拆分 | 30/30 |

> **R8 是最强的一条，也最容易被忽略**。如果序列化器输出与原文有细微差别（比如引号策略不同、换行不同），那么「后台保存一次」就会让 30 篇全部产生 diff——**内容没变但历史全乱**，之后 `git log` 再也无法用来回答「这篇什么时候真的改过」。实现上建议：**序列化时保留原文的原始 front-matter 文本，只在字段真的变更时才重新生成该字段**（即「最小改写」策略），而不是每次整体重新 dump。

### 7.4 发布前置校验规则

**地基原则（沿用 V1.0 §5.4 的正确判断）：后台的「保存前校验」与构建的「发布前校验」必须是同一个实现**，否则必然出现「后台说没问题、构建挂掉」或更糟的「后台放过、构建也放过」。

**同时要修正 V1.0 的两处**：

| V1.0 规则 | 问题 | 本册修正 |
|---|---|---|
| V2「19 个字段齐全」 | 19 是**快照而非约束**——加入 `status`/`author` 后立刻 >19 | 改为「**必填字段集合**」按清单校验 + 允许附加字段（白名单外的新字段给出警告而非失败） |
| V6「正文 10 段齐全」 | 实测 `remote-control-scam.md` 用的是「**怎么确认处理好了**」而非「怎么确认修好了」（29 篇用后者、1 篇用前者；全库每篇恰好 10 个 H2，已复核） | **必须带同义标题白名单**；白名单写死单一标题会让一篇**现在就在线上**的文章被自己的校验器判死 |

**修正后的规则表**：

| # | 规则 | 级别 |
|---|---|---|
| V1 | front-matter 可解析（含 BOM 检测，报错文案可读） | **失败** |
| V2 | 必填字段齐全且类型正确（`os/symptoms/keywords/aliases/prerequisites/tools/related` 必须为数组；**`sources` 为对象数组，每条必有 `title`+`url`，`type` 可选**） | **失败** |
| V3 | `slug` 全局唯一且符合 `^[a-z0-9-]+$` | **失败** |
| V4 | `domain`/`category` 合法且从属关系正确 | **失败** |
| V5 | `risk` ∈ {安全, 需谨慎, 有数据风险}；`difficulty` ∈ {入门, 进阶, 专家} | **失败** |
| V6 | 正文 **10 个 H2**，标题在**同义白名单**内（「怎么确认修好了」/「怎么确认处理好了」二者皆可；「适用 / 不适用」斜杠两侧必须带空格） | **失败** |
| V7 | `## 分步骤` 下至少一个 `### 步骤 N`，每步含「目的 / 操作 / 预期结果 / 失败怎么办」 | 失败（可先警告） |
| V8 | `related` 每个 slug 真实存在 | **失败** |
| V9 | `sources` 非空且 URL 为 https（联网 HEAD 校验默认**关闭**，仅格式校验） | 警告 |
| V10 | 文内锚点 `#...` 有对应标题 | 警告 |
| V11 | `risk` 非「安全」时正文开头有风险提示块 | 警告 |
| V12 | **代理/VPN 类含 §8.2 合规提示块**（自动判定 + 人工复核） | **失败**（合规类）|
| V13 | `reviewed_at` 距今 >180 天 / >12 个月 | 提示（打 `stale`） |
| **V14（新增）** | **序列化 round-trip 断言**：本次保存前后的 `sources` 条目数、键集合、url 数量不得变化（除非编辑者显式编辑了 sources） | **失败** |
| **V15（新增）** | **产物中不得出现草稿 slug**：产物 slug 集合必须与 `content/fixboxs/*.md` 顶层文件集合完全一致（§7.9） | **失败** |

> **V14 是专门为约束一设计的兜底闸门**。即使将来有人误改了序列化器，这条断言会在**保存的那一刻**就拦住，而不是等到 30 篇 URL 全没了才被发现。这是「纵深防御」在数据完整性上的应用。
>
> **V15 是专门为「草稿意外发布」设计的**，见 §7.9。

### 7.5 并发编辑冲突（乐观锁）

**结论：内容哈希乐观锁（沿用 V1.0 D5，且重要性上调）。**

| 项 | 规格 |
|---|---|
| 粒度 | **按文件**：对 `content/fixboxs/**/<slug>.md` 的整体内容取 sha256 |
| 保存请求 | 必须带 `base_hash`（打开编辑器时拿到的哈希） |
| 服务端行为 | `base_hash ≠ 当前文件哈希` → **409**，返回当前版本 + 差异视图 |
| 前端行为 | 提供两个选项：「**基于最新版重新编辑**」（展示 diff，把对方的改动与自己的改动并列）或「**另存为副本**」（新 slug） |
| 禁止 | **绝不做静默覆盖** |
| 哈希之外 | 同时记录 `updated_at` 与 `last_editor_id`，用于 UI 提示「张三 3 分钟前改过这篇」 |
| 发布时 | 发布同样是写操作，也要带 `base_hash`：队列里等待期间若文件被改，**job 失败并提示重新发布**，而不是用旧内容发布 |

**为什么这条在本项目里不是过度设计**：内容是**文件**而不是数据库行，文件没有行锁。而「两个人同时打开同一篇」在 2–10 人的团队里是必然发生的。**更关键的是**：一次静默覆盖丢的不只是文本，而是「哪一版是对的」这个判断依据。

**与「审核中」状态的交互**：`in_review` 状态下，编辑者修改内容会让已有的审核结论失效——实现上让「审核通过」记录绑定 `content_hash`，hash 变了就自动回到 `in_review`。这与 §5.5 的「合规复核绑定版本」是同一个机制，**建议共用同一套版本绑定实现**。

### 7.6 原子切换必须抽成可复用脚本（约束二的修复）

#### 7.6.1 目标形态

把 `deploy-fixboxs.sh:40-51` 的 heredoc 内联段，抽成一个**独立、可单独调用的脚本**：

```
scripts/
├─ atomic-switch.sh        ← 新增：只做「解包 → 原子切换 → 保留 .prev」
├─ verify-site.sh          ← 新增：只做「全量 URL 校验」
├─ deploy-fixboxs.sh       ← 改造：手工路径，调用上面两个
└─ （后台 worker 调用同一对脚本）
```

**规格要求**：

| # | 要求 | 理由 |
|---|---|---|
| 1 | 接受明确入参：产物 tar 路径、目标目录、是否保留 `.prev` | 不再依赖 heredoc 变量内插 |
| 2 | `--local` 与远程两种模式共用**同一个切换实现** | 消除「手工 vs 后台」漂移 |
| 3 | 幂等：重复执行同一份产物不产生额外副作用 | 重试安全 |
| 4 | 失败时**不破坏现有线上目录**（先解包到 `.new`，校验通过才 `mv`） | 现有实现已具备这个性质，必须保留 |
| 5 | 切换前校验 `.new` 的完整性（文件数 > 0、关键文件存在如 `index.html`） | 现有实现缺失；防「解包不完整就切换」 |
| 6 | 输出**机器可读**的结果（如最后一行 JSON：`{"ok":true,"files":42,"bytes":...}`） | 后台 worker 要据此判断，不能靠 grep 中文文本 |
| 7 | 切换后写一个「当前版本标记」（如 `/var/www/fixboxs/.release` 含 commit sha + 时间） | 便于「线上跑的是哪一版」这个问题的回答 |

> **第 6 条特别重要**：如果后台靠解析脚本的中文输出判断成功与否，那么任何人改一句提示文案就会静默破坏发布链路。**机器接口必须与人类输出分离。**

#### 7.6.2 现有实现的资产评估

要保留的（现有脚本做对了的地方）：

| 现有做法 | 出处 | 评价 |
|---|---|---|
| 先解包到 `.new`，最后才 `mv` | `deploy-fixboxs.sh:42-49` | ✅ 正确的原子语义，保留 |
| 切换前 `rm -rf .prev`，再把当前目录 `mv` 成 `.prev` | `:47-48` | ✅ 保留一版回滚点，保留 |
| 统一 `chmod`（目录 755 / 文件 644）与 `chown` | `:44-46` | ✅ 避免权限漂移导致的 403 |
| `set -euo pipefail` | `:16` | ✅ 保留 |
| `--check` 干跑模式 | `:29-32` | ✅ 概念保留并扩展到新脚本 |

**要改的**：

| 现有做法 | 问题 | 改法 |
|---|---|---|
| 原子切换写在 heredoc 里 | 不可复用（约束二） | 抽成 `atomic-switch.sh` |
| 只校验 6 个 URL（`:54`） | 30 篇里只覆盖 1 篇教程 | 改为全量遍历（§7.6.3） |

| 依赖 `curl` 逐个串行 | 全量校验 42 个文件会变慢 | 见 §7.6.3 的并发策略 |

#### 7.6.3 发布后全量 URL 校验

**现状**：`deploy-fixboxs.sh:54` 的循环只检查 6 个路径，其中只有 **1 篇**教程页。也就是说 **29/30 的教程页从未被部署校验覆盖过**。而 `build-fix.cjs:345` 是「缺 title 就 `warn + return`，构建仍 `exit 0`」——两者叠加的结果是：**一篇文章可以静默地从线上消失，而部署流程一路绿灯**。

**新做法**：

| 步骤 | 做法 | 级别 |
|---|---|---|
| 1 | 从 `dist/fixboxs/` **实际存在的文件**生成待校验清单（不手工维护列表） | **必须** |
| 2 | 覆盖全部 `.html`（当前 42 个文件规模，含 30 篇教程 + 6 壳页 + 其他） | **必须** |
| 3 | 并发探测（如 8 并发），控制总耗时 | 建议 |
| 4 | 校验 **200** + 关键响应头（HSTS、安全头） | **必须** |
| 5 | **产物 ↔ 源文件对账**：`content/fixboxs/*.md` 顶层文件数 = 产物中 `fix/*.html` 数 | **必须** |
| 6 | **反向校验**：线上每个 `fix/*.html` 都能在源文件里找到对应 slug | **必须** |
| 7 | 任一失败 → 触发告警，提示「一键回滚」 | **必须** |
| 8 | 校验通过后落一条「发布成功」记录（含文件数、耗时、commit sha） | 建议 |

> 第 5、6 条是**双向对账**，比单向计数强得多：单向只能发现「少了」，双向还能发现「多了」（即不该上线的草稿被发布了——见 §7.9）。

### 7.7 回滚

**两个层级，互不替代**：

| 层级 | 手段 | 覆盖场景 | 耗时 | 触发方式 |
|---|---|---|---|---|
| **产物级** | 把 `/var/www/fixboxs.prev` 切回 | 部署出问题（产物坏、切换半边、线上白屏） | **秒级** | 后台「紧急回滚」按钮（🔒 需再认证）；也可手工 ssh |
| **内容级** | 回退到某个历史版本（`git revert` 或检出某版文件）→ 重新构建部署 | 内容写错（发了错误命令、误导性结论） | 分钟级 | 后台「版本历史」里一键回滚 |

**二者必须都有**，因为它们解决的是不同问题：

- 只做产物级：内容真源仍是错的，下次发布错误内容会**再次上线**；
- 只做内容级：修内容 + 重新构建部署要几分钟，而线上正在白屏。

**回滚的规格**：

| 项 | 规格 |
|---|---|
| 产物级回滚 | 切换前先把当前（坏的）目录保留为 `.broken-<时间戳>` 而不是丢弃——**故障现场是最好的证据** |
| 产物级回滚的作用域 | **只回滚静态产物，不影响后台自身**（后台独立部署，见 §7.10） |
| 内容级回滚 | 用 `git revert`（**不**用 `git reset --hard`，后者会改写历史）；revert 后自动走一次完整发布流程 |
| 回滚也要校验 | 回滚后同样跑 §7.6.3 的全量校验，不能假设「旧的一定是对的」 |
| 回滚入审计 | 谁、何时、从哪一版回滚到哪一版、原因（必填） |
| 演练 | 每季度演练一次产物级回滚（§8 阶段 3） |

> **注意 `.prev` 只有一层**：连续发布两次之后，第一次的版本就不可回滚了。这在「一次坏的发布 + 一次更坏的发布」的连续事故场景下会失去保护。**建议**：把 `.prev` 保留 3 版（`.prev-1`/`.prev-2`/`.prev-3`）而不是 1 版——代价只是几十 MB 磁盘。这是本册相对现有实现的一处**新增建议**。

### 7.8 备份策略（本地 Git 的补充）

因为不再有 GitHub 作为异地副本，备份必须自己补上。

| 对象 | 方式 | 频率 | 保留 |
|---|---|---|---|
| 内容（Markdown + 附件） | **本地 Git 仓库**（服务器上的工作副本本身就是一个完整副本） | 每次发布自动 commit | 全部历史 |
| 内容异地副本 | 服务器上做一次 `git clone --mirror` 到另一目录；**再定期打包下载到你自己的机器** | 每日 / 每周 | 30 天 / 12 周 |
| 后台数据库 | `pg_dump yuanabd_pc_fixboxs` 单库导出（**不要用 `pg_dumpall`**） | 每日 | 14 天 |
| 线上产物 | `/var/www/fixboxs.prev-*` 保留 3 版 | 每次发布 | 3 版 |
| 密钥/配置 | `.env`、nginx 配置、后台的 `RECOVERY_KEY` 单独备份**到加密介质** | 变更时 | — |

**三条硬规则**：

1. **只备份自己的库**：`pg_dump yuanabd_pc_fixboxs`（按库），**绝不用 `pg_dumpall`**——后者会把服务器上所有库一起导出，而**回灌时它也会一起覆盖**，这是共享机上最危险的误伤习惯。
2. **恢复演练必须做**：没演练过的备份不算备份。每季度从备份恢复一次到临时库，验证行数与最新时间戳。
3. **备份文件本身要防泄露**：DB 备份含密码哈希与会话记录，放 `/var/www/backups/` 时必须**不在任何 web 可访问路径下**（nginx `deny` + 放到 `/var/www` 之外更稳妥）。

### 7.9 草稿隔离（「偶然正确」必须变成显式断言）

**现状**：`build-fix.cjs:331` 是 `fs.readdirSync(SRC).filter(f => f.endsWith(".md"))`——**非递归**，因此子目录里的 `_drafts/`、`_archive/` 天然不进构建。实测有效。

**但这是「偶然正确」而非显式设计**：

| 风险 | 说明 |
|---|---|
| 有人把 `readdirSync` 改成递归 | 这是一个非常自然的「改进」（比如为了支持按领域分目录），改完**所有草稿会被直接发布**，而且构建输出是正常的、没有任何报错 |
| 有人把草稿误存到顶层 | 同样直接发布 |
| 当前的部署校验只有 6 个 URL | 覆盖率 1/30，**发现不了多出来的页面** |

**修复：三道锁**

| # | 锁 | 具体做法 | 级别 |
|---|---|---|---|
| 1 | **构建期显式断言** | 在 `build-fix.cjs` 里显式声明「只枚举顶层 `.md`」，并在发现子目录里存在 `.md` 且非 `_assets` 时打印提示（例如 `_drafts/` 有 5 篇草稿未参与构建）——**把隐式行为变成显式声明** | **必须** |
| 2 | **产物侧结果校验** | 发布校验时断言：产物 `fix/*.html` 的 slug 集合 == 源目录顶层 `*.md` 的 slug 集合（双向对账，见 §7.6.3 第 5/6 条） | **必须** |
| 3 | **回归测试** | 放一篇带唯一标识 slug 的假草稿进 `_drafts/`，跑一次构建，断言产物中**不存在**该 slug | **必须** |

> 第 3 条要写进 §8 阶段 -1 的退出标准。它是一个**成本 10 分钟、能挡住一次全站事故**的测试。

**目录布局（沿用 V1.0 D2，实测机制有效）**：

```
content/fixboxs/
├─ *.md                    已发布（构建输入，30 篇）
├─ _drafts/                草稿 / 审核中 / 退回修改（不构建）
├─ _archive/               归档（不构建；URL 由归档页保留）
└─ _assets/<slug>/         图片（不构建；由构建或部署复制进产物）
```

**附带说明**：`_assets/` 的图片要进产物，需要构建/部署脚本显式复制（现有脚本没有这一步）。这是阶段 2 媒体功能的前置，不在 MVP 范围内。

### 7.10 后台自身与站点产物的部署隔离

| 项 | 规则 | 理由 |
|---|---|---|
| 目录隔离 | 后台代码/进程**不在** `/var/www/fixboxs` 内 | 站产物的原子切换会整个替换该目录，后台代码放里面会被「切换」掉 |
| 回滚隔离 | 产物级回滚**不影响后台可用性** | 后台挂了就无法再回滚，形成死锁 |
| 端口 | 后台监听 `127.0.0.1:<port>`，由 nginx 反代 | 不直接暴露端口 |
| 资源 | 后台容器设内存上限（如 512MB）；构建是短任务 | 服务器上已有两个 Next.js 应用（:3000/:3001）与 nginx，不能挤占 |
| 依赖 | 后台依赖与站点构建依赖**分开** | 站点构建的零依赖特性应尽量保持（§7.3.1 只引入解析层依赖） |

### 7.11 后台故障时的手工通道（应急）

**必须保留一条不走后台的发布路径**，因为后台故障时最需要的就是「能改内容」。

| 项 | 要求 |
|---|---|
| 通道 | 手工 `git commit` + 调用**同一对脚本**（`atomic-switch.sh` / `verify-site.sh`） |
| 一致性 | 手工路径与后台路径**调用同一个脚本**——这正是 §7.6 抽出脚本的第二个理由 |
| 验收 | 阶段 -1 之后就要验证：在后台尚未开发的情况下，手工路径能独立完成一次完整发布 |
| 文档 | 写一份「后台不可用时的应急发布步骤」（≤10 行命令），放在服务器上而不只在仓库里 |

> 这一条的价值在于：它让「后台」变成**加速器**而不是**单点依赖**。后台第一天就挂，你仍然能发稿。

## 8. 分阶段实施计划

> 每阶段都给出**可验收的退出标准**。验收标准写成可执行的判断，而不是「做完了」这种描述。

### 8.0 验收判据的三条总原则（先读，否则后面的验收都是无效的）

**原则一：数据完整性验收必须解析成结构化字段、逐条比对键集合与值，不得用字符串包含关系判断。**

反例（已实测为**假阳性**）：用 `JSON.stringify(sources).includes("http")` 判断 URL 是否存活 —— 会得出「有 2 篇保留了 URL」的错误结论（`proxy-server-not-responding.md`、`proxy-tool-broke-network.md`）。实际命中的是 `keywords` 里的 **`netsh winhttp`** 这个单词，不是 URL。

**正确口径**：`url:` 行 **109 条 → 保留 0 条**；`type:` 行 **32 条 → 保留 0 条**。保留率 **0/109**。

**原则二：只比条目数 / 字段总数是无效验收。**

现状是「**条目数 30/30 都对，但内容 30/30 都错**」——解析器把每条 source 压成了一个字符串，条目数是**对的**（3 条还是 3 条），但每条的 URL 都没了。所以：

| 验收写法 | 有效性 |
|---|---|
| ❌ 「`sources` 长度不变」 | **无效**，当前就能通过 |
| ❌ 「`sources` 是数组」 | **无效**，当前就能通过 |
| ❌ 「字段总数为 19」 | **无效**，当前就能通过 |
| ✅ 「逐条比对**键集合**（有无 `type` 必须一致）与**值**（url 字符串完全相等）」 | **有效** |

**原则三：回归断言必须用硬基线数字，而不是「看起来对」。**

| 断言 | 基线值 | 当前值 |
|---|---|---|
| `url` 条数 | **109** | 0 ❌ |
| `type` 条数 | **32**（`official` 31 + `opensource` 1） | 0 ❌ |
| `sources` 条目数 | 109 | 109 ✅（**这条当前就通过，所以它不能单独作为验收**） |
| 键序 | 恒为 `title → url → type` | 不适用 |
| `type` 输出 | **仅在原文存在时输出**（20 篇无 type 则不得出现该键） | 不适用 |
| 每篇 H2 数 | 10（30/30） | 10 ✅ |

> 这三条原则会贯穿下面每个阶段的验收标准。**它们存在的意义是：这个项目已经吃过一次「校验通过但数据已损坏」的亏，不能再吃第二次。**

### 9.3 本册的核心结论（一页纸）

| # | 结论 | 一句话理由 |
|---|---|---|
| 1 | **后台要做，且要做成「自建后台 + 独立登录 + root 分发账号」** | 用户原话即完整规格；且本站内容规范（内容体系 §7.3/§7.4/§8.2）本就要求后台级治理——第二人合规复核、归档保留 URL、12 个月过期标记，在纯 Git 里只能靠自觉 |
| 2 | **正文真源仍在文件系统 Markdown，DB 只存业务态** | 用户说「后台直连数据库」≠「正文进库」；方案乙会新增第二个静默损坏点 |
| 3 | **root 是唯一账号源头，没有自助注册** | 与用户原话一致；admin 也由 root 造，形成两级授权 |
| 4 | **「编辑」与「发布」必须分离** | 内容体系 §8.2 规则 7 明文要求第二人复核合规项——让创作者自己点发布，这条要求就退化成自觉 |
| 5 | **两个前置缺陷必须先修，且与后台无关** | 解析器毁数据（109 条 URL）、原子切换不可复用（双份实现漂移） |
| 6 | **安全投入 100% 集中在后台** | 前台是零动态静态产物，攻击面接近零；后台是唯一有写入能力、有 DB 连接、有会话的组件 |
| 7 | **阶段 -1 + 0 + 1 ≈ 13.5–19.5 人日** | 比 V1.0 的 13–17.5 多，因为补上了 V1.0 没算的解析器升级、脚本抽取与安全落地 |
| 8 | **最小可开工集是 ①③④** | 这三件事不需要等任何决策，今天就能开始，且做完站点即比现状安全得多 |
