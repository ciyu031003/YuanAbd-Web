## 3. 架构决策：正文真源放哪里

这是本方案最关键的一个设计问题。两个候选：

| 维度 | 方案甲：**DB 存业务态 + markdown 是构建输入**（推荐） | 方案乙：正文进 DB，构建时导出 markdown |
|---|---|---|
| 内容真源 | `content/fixboxs/*.md`（可 diff、可 review） | 数据库（唯一副本） |
| 与现有构建链 | **完全兼容**，`build-fix.cjs` 读文件即可 | 需要先导出再构建，多一步且易不同步 |
| 回滚 | `git revert` 逐行可追溯 | 需自建版本表 + 差异 UI |
| 双人复核 | DB 里的状态机 + git 历史双重留痕 | 仅 DB |
| 备份 | git 远端 + DB 双份 | 仅 DB（单点） |
| 迁移成本 | 低（现有 30 篇不动） | 高（要导入 30 篇并保证格式一致） |
| 主要风险 | 需保证 DB 与 git 文件一致（可用事务 + 发布时统一落盘） | **DB 成为唯一副本，git/构建/部署链路失去意义** |

**推荐方案甲的核心理由**：本项目的构建链（`build-fix.cjs` → `deploy-fixboxs.cjs` → 原子切换）是经过验证的成熟资产，且**只有 30 篇、总产物 1MB**。把正文搬进库并不能带来收益，却会让「git 版本历史」「人工编辑 md」「离线批处理」三项现有能力同时失效。

> **与 V1.0 的区别**：V1.0 把这写成不可让步的「铁律」，本方案承认它是一条**可辩论的工程取舍**，并给出理由。若将来内容规模到数千篇、或需要富文本结构化编辑，再重新评估方案乙。

### 3.1 明确的职责划分

| 数据 | 存放位置 | 理由 |
|---|---|---|
| 文章正文 + front-matter | `content/fixboxs/*.md`（git） | 可 diff、可回滚、构建输入 |
| 文章状态（草稿/审核中/已发布/归档） | **DB** | 需要查询与流转 |
| 账号 / 角色 / 会话 | **DB** | 后台业务数据 |
| 审计日志 | **DB** | 需检索与保留策略 |
| 发布任务与日志 | **DB** | 需要状态与重试 |
| 审核意见 | **DB** | 不污染正文 |
| 媒体元数据 | **DB**（文件本体在磁盘/git） | 需检索 |

### 3.2 ⚠️ 前置缺陷③详解：解析器正在丢数据

**实测证据**（Lead 已用仓库自带解析器逻辑独立复现）：

| 项 | 实测结果 |
|---|---|
| `sources` 的原始形态 | 嵌套 YAML：`- title: …` 换行 `  url: …`，其中 **10 篇还有第三行 `type: official`** |
| 解析器位置 | `build-fix.cjs:78-97` |
| 解析器能力 | 只识别「标量」「扁平 `[a,b]` 数组」「扁平 `- item` 列表」 |
| 实测解析结果 | `sources = ["title: Microsoft 支持 — …", …]` —— **字符串数组** |
| URL 是否保留 | **109 条 `url:` 行 → 0 条保留**；`type:` 32 条 → 0 条保留（保留率 **0/109**） |

> ⚠️ **判据警告（v2-architect 实测发现）**：不要用「字符串里有没有 `http`」判断 URL 存活——`proxy-server-not-responding.md` 等篇的 `keywords` 含 **`netsh winhttp`** 这个**单词**，会被误判为「保留了 URL」。必须**解析成结构化字段、逐条比对键集合**。`winhttp` 子串 ≠ URL。

**为什么这是致命的**：用户要求「后台能新增/更新/修正文章」。**后台一旦保存，30 篇的官方来源链接会被整体清空**，而构建、部署、线上校验没有任何一道闸门会发现（`sources` 根本不进 `articles.js`）。这是**静默数据损坏**，不是构建失败。

**修复方式**：用成熟的 `gray-matter`（MIT）替换手写正则解析器（其正是丢 url 的根因），并配套写序列化器 + **round-trip 回归测试**。

**round-trip 验收基线**（可直接作为断言）：

| 断言 | 期望值 |
|---|---|
| 30 篇逐篇 `parse → serialize → parse` | 三态语义等价 |
| `sources` 条目数 | 与原文逐篇一致（**注意：当前条目数 30/30 都对，但内容 30/30 都错——只比条目数是无效验收**） |
| `url` 出现总数 | **109** |
| `type` 出现总数 | **32**（其中 `official` 31 条、`opensource` 1 条） |
| 键顺序 | `title → url → type`，且 `type` 仅在原文存在时输出 |

> 注意 `sources` 是**可变字段的对象数组**：`title`/`url` 必有，`type` 可选。若按「固定三字段」建模，20 篇会写不出，或 10 篇的 `type` 会静默丢失。

## 4. 数据库选型：PostgreSQL

### 4.1 为什么选 PostgreSQL

| # | 理由 | 依据 |
|---|---|---|
| 1 | **事务性 DDL**：迁移失败可回滚；MySQL 的 DDL 隐式提交会留半成品 schema | [PostgreSQL 事务](https://www.postgresql.org/docs/current/tutorial-transactions.html) / [MySQL 隐式提交](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html) |
| 2 | **jsonb + GIN 可对任意路径建索引**，适配审计 detail 与发布 step logs；MySQL **无法为 JSON 内部字段建二级索引** | [PG jsonb](https://www.postgresql.org/docs/current/datatype-json.html) / [PG JSON 函数](https://www.postgresql.org/docs/current/functions-json.html) |
| 3 | **Payload v3 官方无 MySQL 适配器**（仅 MongoDB / Postgres / SQLite）——选 MySQL 会锁死未来换 Node 后台框架的路 | [Payload Database Overview](https://payloadcms.com/docs/v3/database/overview) |
| 4 | **PostgreSQL License**（类 BSD）无 copyleft；MySQL 为 GPLv2 | [PG License](https://www.postgresql.org/about/licence/) |
| 5 | 共享机上 `pg_restore` 可按库还原；而 `mysqldump --all-databases` / `pg_dumpall` 回灌是最危险的误伤习惯 | [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html) |

### 4.2 开跑前必做：用数据而不是直觉确认

```bash
# ① 谁在连哪个库
sudo -u postgres psql -c "\l"
sudo mysql -e "SHOW DATABASES;"
# ② 活跃连接数（最强信号）
sudo -u postgres psql -c "SELECT datname, count(*), state FROM pg_stat_activity GROUP BY 1,2;"
sudo mysql -e "SELECT db, COUNT(*) FROM information_schema.processlist GROUP BY db;"
# ③ 端口归属
sudo ss -lntp | grep -E '5432|3306'
```

**决策规则**：**活跃连接数为 0 的引擎就是你的选择**。若两者都空闲 → 按 §4.1 选 PostgreSQL。

> **唯一翻转条件**：若探查发现 PostgreSQL 正被现有应用占用且负载较高，而 MySQL 完全空闲 → **改选 MySQL**。理由不是「哪个更好」，而是「选错的代价不对称」：选空闲库最坏是多占一点闲置资源，选被占用的库最坏是拖慢线上应用。

### 4.3 隔离硬保证（绝不触碰已有库）

必须做到三条，缺一不可：

1. **独立库 + 独立登录角色**，且**逐库 `REVOKE CONNECT ... FROM PUBLIC`**（PostgreSQL 的 PUBLIC 默认对所有库有 CONNECT，必须逐库收回）；
2. **独立连接串**（独立 `DATABASE_URL`），不复用任何现有应用的环境文件；
3. **备份脚本严格限定库名**，禁止 `pg_dumpall` 回灌、禁止 `mysqldump --all-databases`。

**必做的隔离验证**（这是验收项，不是可选项）：

```bash
# 用后台账号去连别的库，必须报权限错误
PGPASSWORD=... psql -h 127.0.0.1 -U admin_app -d some_other_db -c "select 1"
# 期望：FATAL: permission denied for database "some_other_db"
```

## 6. 账号体系（用户最关心的部分）

用户原话：「**管理员账号由最初始的 root 账号去做分发**，然后给到内部人员去做文章、更新、修正和添加文章」。据此设计：

### 6.1 root 超管

| 项 | 设计 |
|---|---|
| 定义 | 系统初始化时创建的唯一超管，**不可删除、不可降级** |
| 初始密码 | **由初始化脚本随机生成并打印一次**，绝不硬编码默认密码 |
| 首次登录 | **强制改密** |
| 2FA | 建议强制开启 |
| 忘记密码 | 提供离线恢复路径（服务器侧命令行重置），不依赖邮件 |

### 6.2 账号分发流程

```
root 创建账号（指定角色+可选领域范围）
   ↓  生成【一次性激活链接】（有时效、可撤销）
内部人员打开链接 → 设置自己的密码 → 首次登录
   ↓
按角色获得对应权限
```

**规格要求**：激活链接**一次性**、**有有效期**、**可由 root 撤销**；不通过明文密码邮件分发。

### 6.3 角色与权限矩阵

| 角色 | 新建/编辑草稿 | 提交审核 | 审核/发布 | 归档 | 管用户 | 看审计 |
|---|---|---|---|---|---|---|
| **root** 超管 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| **admin** 管理员 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| **reviewer** 审核 | 可改退回稿 | ✅ | ✅ | ✅ | ❌ | ✅ |
| **editor** 编辑 | ✅ | ✅ | ❌ | ❌ | ❌ | 仅自己 |
| **viewer** 只读 | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |

可选细粒度：编辑者按 **领域（domain）** 限定范围（如「网络线编辑」只能改 `net-basic`/`ip-dns`/`router`）。

### 6.4 两条铁律

1. **权限在服务端每个路由强制校验**，不能只在前端隐藏按钮；
2. **改密即失效该用户全部会话**；停用账号立即踢下线。

## 7. 实施顺序（先修缺陷，再建后台）

```
阶段 0  前置修复（必做，与是否建后台无关）
  ① 修 front-matter 解析器（gray-matter）+ 序列化器 + round-trip 测试
     → 验收：url 总数=109、type 总数=32，30 篇逐篇语义等价
  ② 把 content/ 与构建/部署脚本提交进 Git，打基线 tag
     → 验收：git ls-files content 计数 = 30
  ③ 构建闸门：build-fix.cjs 由「警告后跳过」改为「收集错误后非零退出」
  ④ 部署闸门：校验从 6 个 URL 改为全量遍历 dist/fixboxs/fix/*.html
  ⑤ 原子切换代码从 heredoc 抽成可复用脚本（否则后台无法复用）
              │
              ▼
阶段 1  后台 MVP（登录 + 账号 + 文章 CRUD + 预览 + 发布）
              │
              ▼
阶段 2  协作完善（审核流 / 版本历史 / 媒体库 / 审计查询）
              │
              ▼
阶段 3  增强（按需：定时发布、批量操作、通知）
```

> **为什么阶段 0 不能跳过**：①② 不修，后台一保存就在毁数据（§3.2）；③④ 不修，错误内容会静默上线；⑤ 不修，「手工部署」与「后台部署」会各写一份并开始漂移。**这五项的成本远低于后台本身。**
