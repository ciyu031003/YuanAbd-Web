## 0. 文档目标与交付边界

本文档解决「怎么搭、用什么技术、长什么样、怎么部署」四大问题，目标产出是一份**可评审、可开发的完整设计方案**。按你的要求，本阶段**不写代码**，只输出方案；评审通过后再进入实现。

**本方案要覆盖的三块站点：**

| 站点 | 域名 | 定位 |
|---|---|---|
| 门户主站 | `yuanabd.cn` | 个人/品牌简介 + 双项目导流入口 |
| 行迹落地页 | `travel-notes.yuanabd.cn` | 项目简介 + 登录入口 + 下载入口 |
| 学习工作台落地页 | `learn.yuanabd.cn` | 项目简介 + 登录入口 + 下载入口 |

**核心诉求对齐：** 主站向下滑能看到两个项目的跳转链接；两个子域名的「首页」是**项目简介页（非登录页）**；每个简介页**右上角「登录」按钮**才跳转到该项目 Web 端登录页；简介页必须提供**桌面端与移动端下载链接**。

## 1. 现状盘点（决策基础）

| 维度 | 行迹 Travel-Notes | 学习工作台 Learn-Workbench |
|---|---|---|
| Web 框架 | Next.js 15 App Router、React 19 | Next.js 16 App Router、React 19 |
| 数据层 | MySQL + Prisma（自研 mysql2 适配器） | PostgreSQL + `db/schema.sql` + 迁移 |
| 移动端 | Capacitor 8 → Android（`android/` + `www/` 已存在）；无 iOS 工程 | Expo/RN（`apps/mobile`，Expo 57 / RN 0.86）；iOS+Android 可 EAS Build |
| 桌面端 | **无** | **无** |
| 部署 | Ubuntu 106.55.2.197、Docker、Nginx 80/443 | Ubuntu 106.55.2.197、Docker（`web:3001` + `db:5432`）、Nginx |
| 认证 | 有登录（JWT/middleware），有 CSRF（IP 直连会 403） | 有登录（/login），未登录访问 /jobs 返回 307 |
| 品牌 | 「行迹」，暖陶土 `#A85F3A`，旅行/记忆氛围 | 「学习工作台」，求职/学习工具，偏专业（`packages/ui` 有 token） |

**关键技术结论：**
1. 两个项目**都没有桌面端**。落地页要放「桌面端下载」，方案里必须明确桌面打包策略（建议 Tauri，见 §8）。
2. 两个项目**各自已有同域名的 App 根路由**。把「简介落地页」放哪、如何与现有登录中间件共存，是本文档重点（见 §7.4）。
3. 全链路都在 `106.55.2.197` 同一台服务器 + Docker + Nginx 上，**架构应尽量复用现有基础设施**，节省成本并减少新坑。

## 2. 目标与非目标

### 2.1 目标
- 建立统一品牌入口，让两个项目从「孤岛」变成「产品矩阵」。
- 主站承担个人/品牌简介 + 项目导流；子域落地页承担「介绍→使用（登录）→下载客户端」的转化闭环。
- 下载分发真正做到位（区分平台、版本、校验和、二维码等）。
- 满足国内备案与合规要求（ICP 备案号、公安备案、隐私政策占位）。

### 2.2 非目标（本期不做）
- **不做门户自己的登录体系**——三个站点都是公开营销/介绍页，无需账号。
- **不做复杂 CMS 后台**——文案走代码/静态配置或轻量 markdown，够用即可。
- **不迁移/重构两个已有项目**——只在各自项目上「增加」落地页路由与下载区，不动核心业务。
- **不替换现有登录**——登录仍由各项目 Web 端负责。

## 3. 域名、备案与 DNS 规划

### 3.1 域名拓扑

```
yuanabd.cn                    ← 门户主站（备案主域）
├─ travel-notes.yuanabd.cn    ← 行迹落地页
├─ learn.yuanabd.cn           ← 学习工作台落地页
└─ www.yuanabd.cn             ← 建议 301 → 根域（可选，防重复收录）
```

建议**只做主域 `yuanabd.cn` 的 ICP 备案**，子域名属于同一主体、同一服务器，通常随主域覆盖（以当地管局要求为准）。备案通过后再配置 DNS。

### 3.2 备案与合规要点
- **主体一致性**：三个子域对应内容均为「你/你的团队」产品，与备案主体一致，避免跨主体内容被抽查。
- **页脚展示**：每个站点页脚放 ICP 备案号 + 公安联网备案号（可点击跳转工信部/公安查询页）。
- **隐私/用户协议**：落地页有「下载客户端」，建议在页脚放《隐私政策》《用户协议》占位页，尤其移动端 APK 涉及权限声明。
- **备案期间**：先不要对外正式解析域名；开发/预览用服务器 IP 或临时域名，备案通过后切换。

### 3.3 DNS
- 3 条 A/AAAA 记录指向 `106.55.2.197`（或上 CDN 后指向 CDN IP）。
- 若走 CDN，注意 ICP 备案需与 CDN 厂商、源站一致，部分 CDN 会复审备案。

## 5. 视觉设计方向（Design Direction）

> 依据设计系统「三层 token 架构（Primitive → Semantic → Component）」，主站与两个落地页共用**品payer token + 各站 sub-brand accent**，保证「一家人、各有性格」。

### 5.1 主站 `yuanabd.cn` 设计方向
- **风格关键词**：现代极简 / 科技创作者 / 大留白 / 细腻渐变 / 轻微玻璃质感。
- **模式**：Persuade（主站是导流+个人品牌，设计即产品）。
- **视觉层次**：用「留白 + 字号/粗细 + 对比」建立层级，不用纯色块堆布局；以大量白底 + 一处点缀色打造高级感。

### 5.2 色彩系统
主站作为「父品牌」，用**中性冷暖底 + 一个区别于两个子项目的冷色点缀**，与孩子（行迹=陶土暖色、学习工作台=专业蓝）拉开区分，形成父子层次。

| 层 | Token | 值（默认 Light） | 说明 |
|---|---|---|---|
| Primitive | `--c-stone-50/100/900` | `#FAFAF9/#F5F5F4/#18181B` | 中性冷暖基底 |
| Primitive | `--c-accent-500` | `#4F46E5`（靛蓝紫） | 父品牌主色（与孩子冷/暖区分） |
| Primitive | `--c-accent-600` | `#4338CA` | hover/active |
| Primitive | `--c-warm-500` | `#A85F3A`（陶土） | 呼应行迹（仅子域/卡片用） |
| Primitive | `--c-tech-500` | `#0EA5E9`（天青） | 呼应学习工作台（仅子域/卡片用） |
| Semantic | `--bg` | `var(--c-stone-100)` | 页面背景 |
| Semantic | `--surface` | `#FFFFFF` | 卡片/导航 |
| Semantic | `--fg` / `--fg-muted` | `var(--c-stone-900)` / `#71717A`(zinc-500) | 正文/次要 |
| Semantic | `--border` | `#E4E4E7`(zinc-200) | 分隔 |
| Semantic | `--brand` | `var(--c-accent-500)` | 主按钮/链接/焦点 |
| Component | `--btn-primary-bg` | `var(--brand)` | 主按钮 |
| Component | `--card-bg` / `--card-border` | `--surface` / `var(--border)` | 卡片 |
| Semantic | `--sub-brand-trans` | `#A85F3A` | 行迹子品牌 chip |
| Semantic | `--sub-brand-learn` | `#0EA5E9` | 学习工作台子品牌 chip |

- **深色模式**：Light 出发，深色用降饱和、提亮（不用纯黑反转）；每个子品牌色在深色下单独测对比度（≥4.5:1）。
- **指示不靠单一颜色**：子品牌通过 icon/文字 + 颜色共同表达。

### 5.3 字体
| 用途 | 字体（Latin） | 中文回退 | 说明 |
|---|---|---|---|
| 标题/展示 | **Sora** / Space Grotesk | Noto Sans SC（600/700） | 现代几何、有品牌感 |
| 正文 | Inter | Noto Sans SC（400/500） | 易读、中文匹配好 |
| 数字/表格 | Inter（`font-variant-numeric: tabular-nums`） | — | 版本号/数据列防抖动 |

- 加载策略：`font-display: swap`；只预加载关键字体；中文用系统回退或子集化，避免整包 CJK 拖慢首屏。
- **最小正文 16px**，行高 1.6–1.75，段落行长 65–75 字符。

### 5.4 效果、圆角、间距
| 项 | 规范 |
|---|---|
| 圆角 | 卡片 `rounded-2xl`(16px)、按钮 `rounded-lg`(8px)、chip `rounded-full` |
| 阴影 | 统一：`shadow-sm/md` 两档；不用随机阴影 |
| 边框 | 1px `var(--border)`（卡片、页脚分隔） |
| 玻璃导航 | sticky nav 用 `backdrop-blur` + 半透明 surface |
| 渐变 | Hero 用 1–2 处细微径向渐变/光斑，不铺满 |
| 间距 | 4/8 基模；区块 `py-24`(桌面)/`py-16`(移动)；容器 `max-w-6xl`；栅格 gap `gap-6/8` |
| 动效 | 只在 1–2 个核心元素做（卡片 hover 抬升、滚动 reveal 交错 30–50ms）；尊重 `prefers-reduced-motion`；只用 transform/opacity |

### 5.5 图标与组件
- 图标：统一 `lucide-react` 或 `@phosphor-icons/react`（SVG，**禁用 emoji 当图标**）；单线性、stroke 一致。
- 组件：`shadcn/ui`（Radix + Tailwind）作为底座 + 少量自研（下载卡片、项目卡、扫码模块）。
- 每个交互元素：焦点环（2–4px）、hover/pressed/disabled 三态、触控目标 ≥44×44px。

## 7. 技术架构（重点）

### 7.1 总体选型原则
- **复用现有基础设施**：都跑在 `106.55.2.197` + Docker + Nginx + 域名，统一用 `Next.js + TypeScript + Tailwind` 生态——与两个已有项目同构，团队最熟、token/组件可复用、部署形态一致。
- **门户与落地页保持「轻、静态优先、无认证」**：公开内容尽量 SSG/预渲染，提升 LCP/SEO，无需后端逻辑。

### 7.2 架构方案对比

**方案 A：单一 Next.js 应用 + 「host 感知」路由（推荐）**
- 一个仓库（即当前工作区 `YuanAbd-Web`）、一个 Next.js 应用、一次构建/部署。
- 通过 `middleware.ts` 读取请求 host（或 Nginx 注入的 header），判定当前访问的是哪个站点，映射到对应 route group：`app/(portal)/`、`app/(travel)/`、`app/(learn)/`；三个域名都反代到同一 Next 实例端口（如 3000）。
- Nginx 侧：三个 server 块分别把对应子域 `proxy_pass` 到 Next，并透传 Host；可选把子域路径 rewrite 到 `/travel-notes/*`、`/learn/*`，Next 用 route group 承载。

*优点*：一次构建/部署/缓存；共享 design token、品牌、组件、下载配置、备案号；新增项目只加一个 route group；成本最低、运维最少。
*缺点*：三个站点在同一构建里，需用 `canonical` + 各自 sitemap + 页面 `metadata` 做好 SEO 隔离；host 判断逻辑要在 Next 与 Nginx 两侧保持一致。

**方案 B：三站独立（主站一仓库 + 两个落地页分别并入各项目）**
- `yuanabd.cn` 主站独立轻量 Next 应用；`travel-notes.yuanabd.cn` 与 `learn.yuanabd.cn` 落地页作为各自项目仓库里的公开路由（如 `/intro`）承担。

*优点*：落地页天然可复用该项目的品牌 token、真实截图、版本号、真实安装包元数据（数据驱动，不用手维护）；与「现有登录中间件」同源，跳转/鉴权边界最清晰。
*缺点*：3 个部署单元（3 套构建/部署/监控），下载配置与主站视觉需要跨仓库同步，维护面更大。

**推荐：方案 A 起步**（一个应用管三个站，最省、最聚焦），**方案 B 作为未来演进**（当某落地页需要深度读取自身项目真实数据时，再将其下沉到对应仓库）。主站与两个落地页视觉统一，正是方案 A 的强项。

### 7.4 落地页与「现有登录/中间件」共存（关键细节）
现状：两个项目已有**登录态 Auth middleware**（例：Learn-Workbench 未登录访问 `/jobs` 返回 307；Travel-Notes 有 CSRF，**IP 直连会 403**）。

落地页新增后必须处理：
1. **放行**：落地页路由（`/`（公开版）/`/intro`）必须列入 Auth middleware 的**免鉴权白名单**，否则会 307 弹回登录。
2. **登录跳转用域名而非 IP**：登录按钮指向 `https://travel-notes.yuanabd.cn/login`、`https://learn.yuanabd.cn/login`，避免 IP 直连触发 CSRF 403。
3. **路由归属**：建议落地页占用项目「公开首页」，把原有 App 入口收敛为登录后功能页；或新增 `/intro` 公开路由 + `/` 对未登录用户重定向到 `/intro`，对已登录用户保留 App 首页。落地页落地前需和你确认采用哪种。

### 7.5 部署与运维
- **容器**：Next 应用到 Docker（多阶段构建，同现有项目风格）；`docker-compose` 与现有项目共存于 `106.55.2.197`。
- **反代**：Nginx 或 Caddy（Caddy 自动 HTTPS 更省心）。80/443 监听三个域名分别反代到各自 upstream；强制 HTTPS + HSTS。
- **版本控制/交付**：`git archive` 或镜像构建推送（现有项目是非 git 服务器，用 `git archive HEAD` scp + compose 重建，见现有经验）；建议后续接 GitHub Actions + 镜像仓库。
- **安装包托管**：APK/Tauri 安装包放云 OSS/S3（或服务器 `www` 目录），带 `version.json`（含各平台版本号、体积、SHA256、下载 URL），落地页构建时拉取渲染，保证「下载链接不过期、版本可校验」。
- **埋点/统计**：自托管 **Umami** 或 **Plausible**（隐私友好、轻量），埋点：访问量、下载点击（按平台）、到登录转化。
- **监控**：`/health` 健康探查（现有项目已有 health/login 冒烟习惯）；可选 Sentry。
- **安全头**：CSP、`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options`、Cookie `SameSite`；三站公开、无用户输入，风险面小，但安全头必须齐。

## 8. 下载分包与客户端策略（桌面 + 移动）

> 关键判断：**两个项目当前只有 Web + 移动端，尚未做桌面端。** 落地页「桌面端下载」要么先占位、要么按下面方案补齐桌面打包。

### 8.1 移动端
| 项目 | 形态 | 分发方式 | 落地页落地 |
|---|---|---|---|
| 行迹 Travel-Notes | Capacitor 8 已建 Android 工程 | Android 签名 APK 直下；iOS 需 Apple 开发者证书（TestFlight/企业签/App Store） | 给 Android APK 真实链接 + 二维码；iOS 显示「敬请期待」或 TestFlight |
| 学习工作台 | Expo/RN（`apps/mobile`） | EAS Build → Android APK / iOS TestFlight | 同上，Android 真实 + iOS 状态 |

- 移动端下载区：**扫码**（手机扫码直接装 APK）+ **平台按钮**；显示版本、体积、更新日期；Android 提示未知来源安装授权；iOS 给 TestFlight 引导。

### 8.2 桌面端（建议新增，采用 Tauri v2）
- **为什么 Tauri 而非 Electron**：两个项目前端都是 Web 技术（Next.js / Expo Web），用 **Tauri v2** 壳封装、复用现有 Web 首页 + 调登录 API，产物小（几 MB~几十 MB vs Electron 上百 MB）、内存低、性能好，一套 Rust 壳可同时出 **Windows / macOS / Linux**。
- **能力边界**：MVP 桌面端做「原生窗口 + 加载 Web + 自动更新 + 系统通知」即可；核心业务仍在 Web 端。
- **方案 B 下沉路径**：若走方案 B，Tauri 可分别接入两个项目仓库，共享已有前端。
- **建议节奏**：先用 Tauri 打通打包链路，落地页桌面区即可给真实链接；未完成前明确占位「桌面端开发中，先用 Web 版」，**不放死链**。

### 8.3 下载区设计（关键组件）
- 卡片区分：**移动端**（Android/iOS）、**桌面端**（Windows/macOS/Linux）、**Web 直接使用**。
- 每张卡：平台图标 + 名称 + 版本号 + 体积 + 更新时间 + 校验和（可选）+ 主按钮。
- 明确「**也可以在浏览器直接使用**」作为兜底 CTA，避免用户因下载而流失。

## 10. 可访问性（A11y）、性能、SEO

### 10.1 可访问性
- 对比度：正文 ≥4.5:1，大文本/非文本 ≥3:1；**深浅模式分别测**，不假设互通。
- 焦点：所有可交互元素 2–4px 焦点环；Tab 顺序与视觉顺序一致。
- 语义：`lang="zh-CN"`、标题层级不跳级、`main`/`section` 语义、skip link。
- 图标：装饰性图标 `aria-hidden`；有语义的图标带文本替代；按钮/链接有可访问名。
- 触控：目标 ≥44×44px；不用 hover 作唯一交互。
- 动效：尊重 `prefers-reduced-motion`；内容不因动画而不可读。
- 下载：版本号/体积用表格 or tabular 数字；平台图标+文字双重表达（不靠颜色/图标单一表意）。

### 10.2 性能
- 首屏静态化/预渲染；图片 AVIF/WebP + `loading=lazy` + 尺寸占位（防 CLS）。
- 字体 `swap` + 只预加载关键；中文子集化；不整包 CJK。
- CSS 用 token + 关键 CSS 内联；JS 按路由分包；无第三方脚本（除自托管统计）。
- Core Web Vitals：LCP、CLS<0.1、INP<200ms；滚动只用 transform/opacity。

### 10.3 SEO
- 每站独立 `sitemap.xml` + `robots.txt` + `canonical` + `metadata`（title/description/OG/Twitter）。
- 结构化数据 JSON-LD：主站 `Organization`/`Person`；落地页 `SoftwareApplication`（含下载地址/平台/版本）。
- 中文关键词合理布局；三站域名不同，做清晰的数据隔离（不用同一份 sitemap 混排）。
